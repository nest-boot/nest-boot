---
title: "Schedule"
description: "Persistent cron and interval scheduling for NestJS using BullMQ job schedulers."
---

The `@nest-boot/schedule` module discovers decorated providers and controllers, registers persistent [BullMQ job schedulers](https://docs.bullmq.io/guide/job-schedulers), and executes their handlers through a dedicated `schedule` worker. It supports cron patterns and millisecond intervals.

## Installation

```bash
pnpm add @nest-boot/schedule @nest-boot/bullmq @nestjs/bullmq bullmq
```

## Module Registration

```typescript
import { BullModule } from "@nest-boot/bullmq";
import { ScheduleModule } from "@nest-boot/schedule";
import { Module } from "@nestjs/common";

@Module({
  imports: [
    BullModule,
    ScheduleModule.forRoot({
      concurrency: 5,
    }),
  ],
})
export class AppModule {}
```

`BullModule` reads and parses the Redis connection from `REDIS_URL`. `ScheduleModule` also accepts an explicit BullMQ `connection`, `concurrency`, and `autorun`. The worker starts automatically unless `autorun` is `false`.

## Defining Scheduled Tasks

Use `@Cron()` for a cron pattern and `@Interval()` for a millisecond interval. Cron schedules default to the `UTC` timezone.

```typescript
import { Cron, Interval } from "@nest-boot/schedule";
import { Injectable, Logger } from "@nestjs/common";

@Injectable()
export class CleanupService {
  private readonly logger = new Logger(CleanupService.name);

  @Cron("0 0 * * *", { timezone: "UTC", removeOnComplete: true })
  async cleanupExpiredSessions(): Promise<void> {
    this.logger.log("Cleaning up expired sessions");
    // ...cleanup logic
  }

  @Interval(5 * 60 * 1000, { removeOnComplete: true })
  async syncMetrics(): Promise<void> {
    this.logger.log("Syncing metrics");
    // ...sync logic
  }
}
```

Each schedule is named `<ClassName>.<methodName>`. At application bootstrap, the registry upserts the discovered schedules and removes stale schedulers that no longer exist in the codebase. Additional decorator options are forwarded as BullMQ job template options.

## Long-running Tasks

All scheduled handlers run through the shared `schedule` queue and compete for that queue's worker concurrency. A long-running handler holds a concurrency slot, which can delay other due schedules and make their effective frequency lower than configured. When the queue has more than one available worker slot—for example, a worker configured with `concurrency > 1` or multiple application replicas—a handler that runs longer than its scheduling interval may overlap with a later invocation of the same schedule. BullMQ job locks prevent the same job instance from being processed twice; they do not serialize distinct jobs produced by the same Job Scheduler.

Keep scheduled handlers short and use them primarily as triggers. Move long-running or resource-intensive work, and work requiring separate concurrency, retry, backoff, or scaling policies, to a [dedicated BullMQ queue and worker](/docs/tutorial/bullmq). The scheduled handler should only enqueue the job.

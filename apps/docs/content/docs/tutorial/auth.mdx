---
title: "Auth"
description: "Add session and API-key authentication, workspace identity, and CASL-based authorization with one unified guard."
---

`@nest-boot/auth` provides authentication powered by [better-auth](https://www.better-auth.com/), workspace-aware API keys, and CASL-based authorization. It includes MikroORM persistence, automatic request-context middleware, and one `AuthGuard` for authentication and route permission checks.

## Installation

```bash
pnpm add @nest-boot/auth @nest-boot/hash @nest-boot/mailer better-auth @casl/ability nodemailer
```

## Module Registration

### Basic Registration

```typescript
import { AuthModule } from "@nest-boot/auth";
import { HashModule } from "@nest-boot/hash";
import { MailerModule } from "@nest-boot/mailer";
import { Global, Module } from "@nestjs/common";
import { User } from "./user.entity";
import { Account } from "./account.entity";
import { ApiKey } from "./api-key.entity";
import { Session } from "./session.entity";
import { Verification } from "./verification.entity";
import { Workspace } from "./workspace.entity";
import { WorkspaceInvitation } from "./workspace-invitation.entity";
import { WorkspaceMember } from "./workspace-member.entity";

export const AuthDynamicModule = AuthModule.forRoot({
  emailAndPassword: {
    enabled: true,
    requireEmailVerification: true,
  },
  entities: {
    user: User,
    account: Account,
    session: Session,
    verification: Verification,
    workspace: Workspace,
    workspaceInvitation: WorkspaceInvitation,
    workspaceMember: WorkspaceMember,
    apiKey: ApiKey,
  },
});

@Global()
@Module({
  imports: [HashModule, MailerModule, AuthDynamicModule],
})
export class CommonModule {}
```

The module automatically:

- Creates a better-auth instance with MikroORM adapter
- Hashes and verifies credential passwords through the globally registered `HashModule`
- Sends verification emails through the globally registered `MailerModule`
- Registers auth API routes at `/api/auth/` (configurable via `basePath`)
- Resolves sessions, selected workspaces, workspace members, and API keys into `RequestContext`
- Provides workspace and API-key lifecycle services
- Reads common auth settings from environment variables

### Environment Variables

`AuthModule` can configure the default better-auth instance from environment variables. Values passed through `AuthModule.forRoot()` or `AuthModule.forRootAsync()` are merged with these defaults; environment variables can still override nested provider flags where noted below.

By default, email/password auth is enabled, email verification is required, Google/GitHub/OIDC auth are disabled, and signup is allowed. Set `AUTH_DISABLE_SIGN_UP=true` when you want to stop new signups for every configured method at once.

#### Common

Set these once for the whole auth instance.

| Variable               | Purpose                                                                                                                            | Default                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `AUTH_SECRET`          | Secret used to sign and encrypt auth data. Falls back to `APP_SECRET`. Must be at least 32 characters and high entropy.            | Required                             |
| `HASH_SECRET`          | Pepper used by `HashModule` for credential passwords. Falls back to `APP_SECRET`. Must be at least 32 characters and high entropy. | Required when `APP_SECRET` is unset  |
| `APP_SECRET`           | Fallback secret when `AUTH_SECRET` is not set.                                                                                     | Required when `AUTH_SECRET` is unset |
| `APP_NAME`             | App name passed to better-auth.                                                                                                    | unset                                |
| `AUTH_URL`             | Public auth base URL. Falls back to `APP_URL`.                                                                                     | unset                                |
| `APP_URL`              | Fallback public base URL when `AUTH_URL` is not set.                                                                               | unset                                |
| `AUTH_DISABLE_SIGN_UP` | Set to `true` to disable signup for every configured auth method. Sign-in still works for existing users.                          | signup enabled                       |
| `API_KEY_PREFIX`       | Prefix used when creating workspace API keys.                                                                                      | `sk-`                                |

#### Email

Email/password auth is on and requires email verification by default. Set `AUTH_EMAIL_REQUIRE_VERIFICATION=false` if an application does not require verification. To disable email/password auth, set `AUTH_EMAIL_ENABLED=false`. To keep email sign-in but block new email signups, set `AUTH_EMAIL_DISABLE_SIGN_UP=true`.

| Variable                          | Purpose                                               | Default        |
| --------------------------------- | ----------------------------------------------------- | -------------- |
| `AUTH_EMAIL_ENABLED`              | Enables email/password auth unless set to `false`.    | enabled        |
| `AUTH_EMAIL_REQUIRE_VERIFICATION` | Requires verified email unless set to `false`.        | required       |
| `AUTH_EMAIL_DISABLE_SIGN_UP`      | Blocks new email/password signups when set to `true`. | signup enabled |

#### Google

Google auth is off until `AUTH_GOOGLE_ENABLED=true`. When enabled, both Google credentials are required. Leaving `AUTH_GOOGLE_ENABLED` unset keeps Google disabled even if credentials are present.

| Variable                      | Purpose                                          | Default               |
| ----------------------------- | ------------------------------------------------ | --------------------- |
| `AUTH_GOOGLE_ENABLED`         | Enables Google auth from env when set to `true`. | disabled              |
| `AUTH_GOOGLE_CLIENT_ID`       | Google OAuth client ID.                          | Required when enabled |
| `AUTH_GOOGLE_CLIENT_SECRET`   | Google OAuth client secret.                      | Required when enabled |
| `AUTH_GOOGLE_DISABLE_SIGN_UP` | Blocks new Google signups when set to `true`.    | signup enabled        |

#### GitHub

GitHub auth is off until `AUTH_GITHUB_ENABLED=true`. When enabled, both GitHub credentials are required. Leaving `AUTH_GITHUB_ENABLED` unset keeps GitHub disabled even if credentials are present.

| Variable                      | Purpose                                          | Default               |
| ----------------------------- | ------------------------------------------------ | --------------------- |
| `AUTH_GITHUB_ENABLED`         | Enables GitHub auth from env when set to `true`. | disabled              |
| `AUTH_GITHUB_CLIENT_ID`       | GitHub OAuth client ID.                          | Required when enabled |
| `AUTH_GITHUB_CLIENT_SECRET`   | GitHub OAuth client secret.                      | Required when enabled |
| `AUTH_GITHUB_DISABLE_SIGN_UP` | Blocks new GitHub signups when set to `true`.    | signup enabled        |

If you pass `socialProviders.google` or `socialProviders.github` manually, explicit `*_ENABLED=false` and signup-disable env flags are still merged into the nested provider config without requiring credentials to move into env.

#### OIDC

Generic OIDC is off until `AUTH_OIDC_ENABLED=true`. When enabled, `AuthModule` registers a `genericOAuth` provider with `providerId: "oidc"` and validates the required OIDC settings at startup.

| Variable                    | Purpose                                                                                                                                    | Default                |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------- |
| `AUTH_OIDC_ENABLED`         | Enables generic OIDC auth from env when set to `true`.                                                                                     | disabled               |
| `AUTH_OIDC_CLIENT_ID`       | OIDC client ID.                                                                                                                            | Required when enabled  |
| `AUTH_OIDC_CLIENT_SECRET`   | OIDC client secret.                                                                                                                        | Required when enabled  |
| `AUTH_OIDC_DISCOVERY_URL`   | OIDC discovery document URL.                                                                                                               | Required when enabled  |
| `AUTH_OIDC_PROMPT`          | Optional OIDC prompt. Supported values: `none`, `login`, `create`, `consent`, `select_account`, `select_account consent`, `login consent`. | unset                  |
| `AUTH_OIDC_SCOPES`          | Comma-separated OIDC scopes. Whitespace is trimmed and empty entries are ignored.                                                          | `openid,profile,email` |
| `AUTH_OIDC_DISABLE_SIGN_UP` | Blocks new OIDC signups when set to `true`.                                                                                                | signup enabled         |

If OIDC is not needed, leave `AUTH_OIDC_ENABLED` unset. If you need multiple generic OIDC providers or custom provider behavior, configure `plugins` manually; `AUTH_OIDC_*` cannot be combined with a custom `genericOAuth` plugin because better-auth registers one shared set of OAuth2 endpoints for that plugin.

### Async Registration with OIDC

In real-world applications, use `forRootAsync` to inject `ConfigService` and configure OAuth/OIDC providers:

```typescript
import { AuthModule } from "@nest-boot/auth";
import { ConfigService } from "@nestjs/config";
import { bearer, genericOAuth } from "better-auth/plugins";

import { User } from "./user.entity";
import { Account } from "./account.entity";
import { ApiKey } from "./api-key.entity";
import { Session } from "./session.entity";
import { Verification } from "./verification.entity";
import { Workspace } from "./workspace.entity";
import { WorkspaceInvitation } from "./workspace-invitation.entity";
import { WorkspaceMember } from "./workspace-member.entity";

const AuthDynamicModule = AuthModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (configService: ConfigService) => ({
    trustedOrigins: ["*"],
    entities: {
      user: User,
      account: Account,
      session: Session,
      verification: Verification,
      workspace: Workspace,
      workspaceInvitation: WorkspaceInvitation,
      workspaceMember: WorkspaceMember,
      apiKey: ApiKey,
    },
    plugins: [
      bearer(),
      genericOAuth({
        config: [
          {
            providerId: "oidc",
            clientId: configService.getOrThrow("AUTH_OIDC_CLIENT_ID"),
            clientSecret: configService.getOrThrow("AUTH_OIDC_CLIENT_SECRET"),
            discoveryUrl: configService.getOrThrow("AUTH_OIDC_DISCOVERY_URL"),
            prompt: "login",
            scopes: ["openid", "profile", "email"],
          },
        ],
      }),
    ],
  }),
});
```

Key options:

- **`entities`** — Map the user, account, session, verification, workspace, workspace-invitation, workspace-member, and API-key MikroORM entity classes
- **`emailAndPassword.enabled`** — Enable or disable email/password authentication; defaults to `true`
- **`emailAndPassword.requireEmailVerification`** — Require a verified email before sign-in; defaults to `true`
- **`emailAndPassword.password`** — Override password hashing; by default both `hash` and `verify` use the injected `HashService`
- **`emailAndPassword.sendResetPassword`** — Override password-reset delivery; the default implementation uses the injected `Mailer`
- **`emailVerification.sendVerificationEmail`** — Override verification delivery; the default implementation uses the injected `Mailer`
- **`onAuthenticated`** — Optional callback invoked after successful session resolution for additional application context
- **`plugins`** — better-auth plugins (e.g., `genericOAuth`, `twoFactor`, etc.)
- **`basePath`** — Customize the auth API path (default: `/api/auth/`)
- **`trustedOrigins`** — Allowed CORS origins

## Auth Guard

Register `AuthGuard` as a global guard to protect all routes by default. Import the configured dynamic module rather than the unconfigured `AuthModule` class:

```typescript
import { AuthGuard } from "@nest-boot/auth";
import { APP_GUARD } from "@nestjs/core";

@Global()
@Module({
  imports: [AuthDynamicModule],
  providers: [
    {
      provide: APP_GUARD,
      useExisting: AuthGuard,
    },
  ],
})
export class CommonModule {}
```

The guard accepts either a valid session or API key in `RequestContext`. If neither identity is available, the request is rejected.

### Public Routes

Use the `@Public()` decorator to bypass the auth guard on specific routes:

```typescript
import { Public } from "@nest-boot/auth";
import { Query, Resolver } from "@nest-boot/graphql";

@Resolver()
export class HealthResolver {
  @Public()
  @Query(() => String)
  health(): string {
    return "ok";
  }
}
```

## Workspace Context

`AuthModule` resolves the selected workspace before authentication middleware runs. Clients select a workspace with the `x-workspace-id` header or the `workspace_id` cookie. The module then resolves the authenticated user's membership in that workspace and stores both objects in `RequestContext`.

Use the built-in decorators to access this identity without coupling transport code to `RequestContext`:

```typescript
import {
  CurrentWorkspace,
  CurrentWorkspaceMember,
} from "@nest-boot/auth";

currentWorkspace(
  @CurrentWorkspace() workspace: Workspace,
  @CurrentWorkspaceMember() member: WorkspaceMember,
) {
  return { workspace, member };
}
```

`WorkspaceService` owns the transport-independent workspace lifecycle:

- `findOne(where)`
- `createWorkspace(user, { name })`
- `updateWorkspace(workspace, { name })`
- `deleteWorkspace(workspace, currentMember)`

Creating a workspace also creates an active owner membership. Deletion is a soft delete and is restricted to the owner. GraphQL resolvers or HTTP controllers should only map their input/output types and delegate these rules to the service.

## API Keys

`ApiKeyService` manages API keys owned by either a user or a workspace. A user key restores its owning user and may access a selected workspace only while that user remains a member. A workspace key is an independent service identity: it restores its owning workspace but does not create a current user or workspace member. Only the workspace owner can manage workspace keys; users manage their own user keys.

The service provides:

- `getUserApiKey`, `createUserKey`, `updateUserKey`, and `deleteUserKey`
- `getWorkspaceApiKey`, `createWorkspaceKey`, `updateWorkspaceKey`, and `deleteWorkspaceKey`
- `getUserListFilter` and `getWorkspaceListFilter`
- `validate(plaintextKey)` and `recordUsage(apiKey)`

The create methods return the plaintext key only once. The database stores a SHA-256 hash of the complete key, the display-safe `start` and `prefix`, its enabled state, permissions, expiration, and usage timestamps. Successful authenticated requests update `lastUsedAt` automatically.

`@nest-boot/auth` stores and evaluates permissions as strings. Define the closed
permission catalog in the application so each product can use its own resources
and actions:

```typescript
import { UserPermission } from "./auth/enums/user-permission.enum";
import { WorkspacePermission } from "./auth/enums/workspace-permission.enum";

const workspacePermissions: WorkspacePermission[] = [
  WorkspacePermission.WORKSPACE_UPDATE,
  WorkspacePermission.WORKSPACE_MEMBER_CREATE,
];

const userKeyPermissions: (UserPermission | WorkspacePermission)[] = [
  UserPermission.USER_GET,
  WorkspacePermission.WORKSPACE_UPDATE,
];
```

In the example application, `User.permissions` stores `UserPermission[]`,
`WorkspaceMember.permissions` stores `WorkspacePermission[]`, and an API key
stores `(UserPermission | WorkspacePermission)[]`. A workspace-owned key only
accepts workspace permissions, while a user-owned key may contain both domains.
The database persists these values in `text[]` columns, and the application
validates every value before writing it. The auth module itself always exposes
these fields as `string[]`.

Send API keys with the Bearer scheme:

```http
Authorization: Bearer sk-4tR9s...
```

`x-api-key` is not supported. Add better-auth's `bearer()` plugin when clients also need Bearer Session authentication, as shown in the async registration example. Session authentication runs first: if the Bearer credential resolves to a valid session, API-key validation is skipped. Otherwise, the same Bearer credential is treated as an API key.

Use `@CurrentApiKey()` when a handler needs the key entity that authenticated the request:

```typescript
import { CurrentApiKey } from "@nest-boot/auth";

audit(@CurrentApiKey() apiKey: ApiKey | null) {
  return apiKey;
}
```

## Authorization

Configure `buildWorkspaceAbility` and `buildUserAbility` on `AuthModule`. Each callback runs at most once per request when a route checks its authorization domain, and each resulting CASL ability is cached separately in `RequestContext`. A callback may return `null`, in which case its permission check fails with `ForbiddenException`.

```typescript
import { AuthModule, PermissionAbilityBuilder } from "@nest-boot/auth";
import { RequestContext } from "@nest-boot/request-context";

import { User } from "./user.entity";
import { Post } from "./post.entity";

export const AuthDynamicModule = AuthModule.forRoot({
  entities: {
    user: User,
    account: Account,
    session: Session,
    verification: Verification,
    workspace: Workspace,
    workspaceInvitation: WorkspaceInvitation,
    workspaceMember: WorkspaceMember,
    apiKey: ApiKey,
  },
  buildWorkspaceAbility: () => {
    const { can, build } = new PermissionAbilityBuilder();

    can("read", Post);

    return build();
  },
  buildUserAbility: () => {
    const user = RequestContext.get(User);

    if (!user) {
      return null;
    }

    const { can, build } = new PermissionAbilityBuilder();

    can("read", Post);
    can("update", Post, { authorId: user.id });

    return build();
  },
});
```

The same globally registered `AuthGuard` first enforces authentication and then evaluates `@Can` metadata. No second permission guard or module is required. `@Public()` only skips the authentication requirement; if a public route also declares `@Can`, its permission is still checked.

`@Can` checks the workspace ability by default. Pass `{ scope: "user" }` as its third argument for routes that belong to the authenticated user rather than the selected workspace. Workspace API keys can only pass workspace checks. User API keys can pass user checks. The application decides how `User.permissions` contributes to `buildUserAbility`; API-key requests then intersect that ability with the key permissions. Workspace checks additionally require a live workspace membership and intersect the workspace ability with the key permissions. Read operations remain baseline authenticated access; application-defined permission strings gate the catalogued management operations.

### Protect Routes

Use a subject class when authorization only depends on the resource type.

```typescript
import { Can } from "@nest-boot/auth";
import { Query, Resolver } from "@nestjs/graphql";

import { Post } from "./post.entity";

@Resolver(() => Post)
export class PostResolver {
  @Can("read", Post)
  @Query(() => [Post])
  posts() {
    return this.postService.findAll();
  }
}
```

Use the user scope for personal or application-level operations:

```typescript
import { Can } from "@nest-boot/auth";

@Can("read", User, { scope: "user" })
@Query(() => User)
me(@CurrentUser() user: User) {
  return user;
}
```

Use a subject factory when the ability needs a concrete resource instance. The factory receives the controller or resolver instance first, followed by its decorated method parameters. HTTP, GraphQL, and custom parameter decorators are supported.

```typescript
import { Can } from "@nest-boot/auth";
import { Args, Mutation, Resolver } from "@nestjs/graphql";

@Resolver(() => Post)
export class PostResolver {
  constructor(private readonly postService: PostService) {}

  @Can("update", (self: PostResolver, id: string) =>
    self.postService.findOneOrFail({ id }),
  )
  @Mutation(() => Post)
  updatePost(@Args("id") id: string) {
    return this.postService.update(id);
  }
}
```

### Check Permissions in Services

After `AuthGuard` prepares the request ability, use `can` for synchronous checks in lower-level code or `getPermissionAbility()` for direct CASL access. Both helpers default to the workspace scope and accept the same explicit user scope when needed.

```typescript
import { can } from "@nest-boot/auth";
import { ForbiddenException, Injectable } from "@nestjs/common";

@Injectable()
export class PostService {
  update(post: Post) {
    if (!can("update", post)) {
      throw new ForbiddenException();
    }

    // Update the post.
  }
}
```

Both helpers require the ability to have been prepared by a route-level `@Can` check. They throw `ForbiddenException` when no ability is available.

```typescript
can("read", user, { scope: "user" });
getPermissionAbility("user");
```

## Entity Setup

Extend the base entity classes provided by the module to define your auth entities:

```typescript
import { Entity, PrimaryKey, Property, t } from "@mikro-orm/postgresql";
import { BaseUser } from "@nest-boot/auth";
import { Field, ID, ObjectType } from "@nest-boot/graphql";

@ObjectType()
@Entity()
export class User extends BaseUser {
  @Field(() => ID)
  @PrimaryKey({ type: t.bigint })
  id!: string;

  @Field(() => String)
  @Property({ type: t.string })
  name!: string;

  @Field(() => String)
  @Property({ type: t.string })
  email!: string;
}
```

The module also provides `BaseAccount`, `BaseSession`, `BaseVerification`, `BaseWorkspace`, `BaseWorkspaceInvitation`, `BaseWorkspaceMember`, and `BaseApiKey`. Extend the corresponding base class for every configured entity. The base classes define the fields and relations required by the authentication services; subclasses can redeclare fields with application-specific column types, GraphQL annotations, indexes, and additional properties.

Better Auth 1.7 identifies an account by the required `issuer` and `accountId` pair. `BaseAccount` includes both fields and a compound unique constraint; it also includes the user index required by Better Auth. `BaseSession` indexes `userId`, and `BaseVerification` indexes `identifier`. Generate or update the application migration after upgrading. Do not add a required `issuer` column directly to a populated pre-1.7 account table: backfill a stable issuer for every existing account and resolve duplicate `(issuer, accountId)` pairs before enforcing the constraint.

## NestJS Integration

The underlying Better Auth instance and its injection token are internal implementation details and are not exported. Inject the service that owns the required domain instead:

| Service            | Responsibility                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `AuthService`      | Email/password authentication, verification, password recovery, current-user profile, and linked accounts            |
| `SessionService`   | Resolve the current application session, list active sessions, and revoke sessions                                   |
| `AdminService`     | User creation and administration, permissions, bans, impersonation, passwords, and administrative session management |
| `WorkspaceService` | Workspace lifecycle, memberships, invitations, and workspace permission checks                                       |
| `ApiKeyService`    | Personal and workspace API-key lifecycle and validation                                                              |

`AdminService` and `WorkspaceService` operate directly on the MikroORM entities configured in `AuthModule`. They do not require the Better Auth admin or organization plugins. `AuthService` can start email-verification and password-reset flows, while the verification links and reset callbacks remain available through the auth endpoint mounted by `AuthModule`.

```typescript
import {
  AdminService,
  AuthService,
  SessionService,
  WorkspaceService,
} from "@nest-boot/auth";
import { Injectable } from "@nestjs/common";

@Injectable()
export class AccountApplicationService {
  constructor(
    private readonly authService: AuthService,
    private readonly sessionService: SessionService,
    private readonly adminService: AdminService,
    private readonly workspaceService: WorkspaceService,
  ) {}
}
```

`SessionService.getSession()` resolves the configured application `User` and `Session` entities rather than returning Better Auth transport objects. The other session methods are `listSessions()`, `revokeSession()`, `revokeOtherSessions()`, and `revokeSessions()`.

`AuthService` exposes `signUp()`, `signIn()`, `signOut()`, `sendVerificationEmail()`, `requestPasswordReset()`, `resetPassword()`, `verifyPassword()`, `changePassword()`, `updateUser()`, `changeEmail()`, `setPassword()`, `deleteUser()`, `listAccounts()`, and `unlinkAccount()`. `sendVerificationEmail()` manually starts email verification, `requestPasswordReset()` sends an enumeration-safe reset request, and `resetPassword()` consumes the token delivered to the configured reset page. `verifyPassword()` validates the current user's credential without exposing password hashes. `listAccounts()` returns each account's local `id`, `issuer`, provider identifier, and provider-side account identifier; pass that local `id` as `accountId` to `unlinkAccount()`. Their inputs and results are declared by `@nest-boot/auth`, so application code does not depend on Better Auth's inferred API types. Operations that require request validation or session authorization accept Fetch-standard `HeadersInit`; in particular, `verifyPassword()` and `changePassword()` require the current session headers.

`AdminService` exposes user CRUD, search and offset pagination, permission replacement and checks, banning, password replacement, impersonation, and per-user session management. Impersonation creates a normal persisted session and returns its token; the transport layer decides whether to deliver it as a Bearer token or session cookie.

`WorkspaceService` exposes workspace CRUD, user workspace listing, full workspace details, member lifecycle, invitations, and permission checks. Invitations use a dedicated entity with `pending`, `accepted`, `rejected`, and `canceled` states. Accepting an invitation creates a separate workspace member, while the invitation remains available as a lifecycle record.

A complete `main.ts` setup with auth:

```typescript
import { Logger } from "@nest-boot/logger";
import { ValidationPipe } from "@nestjs/common";
import { NestFactory } from "@nestjs/core";
import { AppModule } from "./app/app.module";

async function bootstrap() {
  const app = await NestFactory.create(AppModule, {
    bufferLogs: true,
    cors: true,
  });

  app.useLogger(await app.resolve(Logger));
  app.useGlobalPipes(
    new ValidationPipe({ transform: true, forbidUnknownValues: false }),
  );
  app.enableShutdownHooks();

  await app.listen(process.env.PORT ?? 4000);
}

void bootstrap();
```

## Best Practices

1. **Global Guard** — Always register `AuthGuard` as `APP_GUARD` and use `@Public()` for exceptions, rather than adding guards per-route.

2. **Stable Context Decorators** — Use `CurrentWorkspace`, `CurrentWorkspaceMember`, and `CurrentApiKey` instead of reaching into the application entity tokens from transport code.

3. **Environment Variables** — Store `AUTH_SECRET` in environment variables and ensure it's at least 32 characters with high entropy.

4. **RLS Context** — When combining auth with PostgreSQL RLS, derive database context from the workspace and member already stored in `RequestContext`. See the [Row-Level Security tutorial](/docs/tutorial/row-level-security).

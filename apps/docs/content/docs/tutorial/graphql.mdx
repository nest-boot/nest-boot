The `@nest-boot/graphql` module provides a preconfigured [Apollo Server](https://www.apollographql.com/docs/apollo-server/) GraphQL layer for NestJS, with code-first schema generation, global exception filtering, and an optional local landing page. Companion modules provide [operation logging](#graphql-logger), [query complexity rate limiting](#graphql-rate-limiting), and [cursor-based pagination](#graphql-connection).

To expose staged upload creation as a GraphQL mutation, see
[GraphQL Integration in the Staged Upload guide](/docs/tutorial/staged-upload#graphql-integration).

## Installation

```bash
pnpm add @nest-boot/graphql @nestjs/graphql @nestjs/apollo @apollo/server graphql
```

For the Zod input validation shown below, also install:

```bash
pnpm add @nest-boot/validator zod
```

## Module Registration

### Basic Registration

```typescript
import { Module } from "@nestjs/common";
import { GraphQLModule } from "@nest-boot/graphql";

@Module({
  imports: [GraphQLModule.forRoot({})],
})
export class AppModule {}
```

The module auto-configures Apollo Server with sensible defaults:

- Endpoint at `/graphql`, following the NestJS global prefix by default
- Code-first auto-generated schema (`schema.gql`)
- Sorted schema output
- Global `GraphQLExceptionFilter` for error handling
- GraphiQL unless `graphiql` is explicitly `false`

### Async Registration

```typescript
import { GraphQLModule } from "@nest-boot/graphql";
import { ConfigService } from "@nestjs/config";

const GraphQLDynamicModule = GraphQLModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (configService: ConfigService) => ({
    graphiql: configService.get("NODE_ENV") !== "production",
  }),
});
```

### Global Prefix

Nest Boot defaults to `path: "/graphql"` and `useGlobalPrefix: true`. The official
`@nestjs/graphql` driver applies the application prefix; no manual prefix
concatenation is needed. Without a global prefix, the endpoint is `/graphql`.

```typescript
GraphQLModule.forRoot({});
// In bootstrap:
app.setGlobalPrefix("api");
// Endpoint: /api/graphql
```

Both defaults can be overridden with `forRoot` or `forRootAsync`. Set
`useGlobalPrefix: false` to serve GraphQL outside the application prefix, or
configure `path` to change its relative route. Unlike Nest Boot, upstream
`@nestjs/graphql` requires explicitly enabling `useGlobalPrefix`.

When upgrading an application without a global prefix, update clients to use
`/graphql`. To preserve the previous fixed endpoint, configure
`{ path: "/api/graphql", useGlobalPrefix: false }`.

## Defining Types

`@nest-boot/graphql` re-exports everything from `@nestjs/graphql`, so you can define GraphQL types and entity models using a single set of decorators:

The entity example also uses MikroORM. Complete the [MikroORM installation](./database#installation), including `@mikro-orm/decorators`, first.

```typescript
import { t } from "@mikro-orm/core";
import { Entity, PrimaryKey, Property } from "@mikro-orm/decorators/legacy";
import { Field, ID, ObjectType } from "@nest-boot/graphql";

@ObjectType()
@Entity()
export class User {
  @Field(() => ID)
  @PrimaryKey({ type: t.bigint })
  id!: string;

  @Field(() => String)
  @Property({ type: t.string })
  name!: string;

  @Field(() => String)
  @Property({ type: t.string })
  email!: string;

  @Field(() => Date)
  @Property({ type: t.datetime, defaultRaw: "now()" })
  createdAt: Date = new Date();
}
```

### Input Types

Use `@InputType()` to define mutation inputs, and combine it with
`@nest-boot/validator` for Zod validation:

```typescript
import { Field, InputType, ID } from "@nest-boot/graphql";
import { ZodField } from "@nest-boot/validator";
import { z } from "zod";

@InputType()
export class CreateUserInput {
  @ZodField(z.string().min(1))
  @Field(() => String)
  name!: string;

  @ZodField(z.email())
  @Field(() => String)
  email!: string;

  @ZodField(z.string().optional())
  @Field(() => ID, { nullable: true })
  workspaceId?: string;
}
```

Wrap GraphQL mapped types with the matching validator helper so both GraphQL
field metadata and Zod schemas reach the derived class:

```typescript
import { PartialType } from "@nestjs/graphql";
import { ZodPartialType } from "@nest-boot/validator";

@InputType()
export class UpdateUserInput extends ZodPartialType(
  CreateUserInput,
  PartialType,
) {}
```

Register `ZodValidationPipe` globally as described in the
[Validator guide](/docs/tutorial/validator#enable-nestjs-validation). When
validation fails, `GraphQLExceptionFilter` returns an Apollo-style user input
error while keeping field-level details in `extensions`:

```json
{
  "errors": [
    {
      "message": "Validation failed",
      "path": ["createUser"],
      "extensions": {
        "code": "BAD_USER_INPUT",
        "validationErrors": [
          {
            "code": "invalid_format",
            "field": ["email"],
            "message": "Invalid email address"
          }
        ]
      }
    }
  ]
}
```

The top-level `path` is GraphQL's resolver response path. Each `field` is the
path to the invalid input value and can include numeric array indexes.

## Resolvers

```typescript
import {
  Args,
  ID,
  Mutation,
  Parent,
  Query,
  ResolveField,
  Resolver,
} from "@nest-boot/graphql";
import { NotFoundException } from "@nestjs/common";

import { User } from "./user.entity";
import { UserService } from "./user.service";
import { CreateUserInput } from "./inputs/create-user.input";

@Resolver(() => User)
export class UserResolver {
  constructor(private readonly userService: UserService) {}

  @Query(() => User)
  async user(@Args("id", { type: () => ID }) id: string): Promise<User> {
    const user = await this.userService.findOne({ id });

    if (!user) {
      throw new NotFoundException("User not found");
    }

    return user;
  }

  @Mutation(() => User)
  async createUser(@Args("input") input: CreateUserInput): Promise<User> {
    return await this.userService.create(input);
  }

  @ResolveField(() => String)
  displayName(@Parent() user: User): string {
    return user.name;
  }
}
```

## GraphQL Connection

The `@nest-boot/graphql-connection` module provides cursor-based pagination following the [Relay Connection specification](https://relay.dev/graphql/connections.htm). It integrates with MikroORM to generate type-safe, paginated queries with filtering, sorting, and full-text search.

### Installation

```bash
pnpm add @nest-boot/graphql-connection @mikro-orm/core
```

Register the module in your `CommonModule` (or root module):

```typescript
import { GraphQLConnectionModule } from "@nest-boot/graphql-connection";

@Global()
@Module({
  imports: [GraphQLConnectionModule],
})
export class CommonModule {}
```

### Defining a Connection

Use `ConnectionBuilder` to define which fields are filterable, sortable, and searchable:

```typescript
import { ArgsType, ObjectType } from "@nest-boot/graphql";
import { ConnectionBuilder } from "@nest-boot/graphql-connection";
import { User } from "./user.entity";

export const { Connection, ConnectionArgs } = new ConnectionBuilder(User)
  .addField({
    field: "id",
    type: "string",
    filterable: true,
  })
  .addField({
    field: "name",
    type: "string",
    filterable: true,
    sortable: true,
    searchable: true,
  })
  .addField({
    field: "email",
    type: "string",
    filterable: true,
    searchable: true,
  })
  .addField({
    field: "created_at",
    replacement: "createdAt",
    type: "date",
    filterable: true,
    sortable: true,
  })
  .addField({
    field: "is_active",
    replacement: "isActive",
    type: "boolean",
    filterable: true,
  })
  .build();

@ArgsType()
export class UserConnectionArgs extends ConnectionArgs {}

@ObjectType()
export class UserConnection extends Connection {}
```

Key features of `addField`:

- **`replacement`** — Map a client-facing field name to a different entity property (e.g., `created_at` → `createdAt`)
- **`filterable`** — Enable MongoDB-style filtering (`$eq`, `$ne`, `$gt`, `$in`, etc.)
- **`sortable`** — Enable ordering by this field
- **`searchable`** — Enable human-friendly search syntax (`field:value`)
- **`fulltext`** — Use PostgreSQL full-text search for this field

### Using in Resolvers

Inject `ConnectionManager` to execute paginated queries:

```typescript
import {
  Args,
  Query,
  Resolver,
  ResolveField,
  Parent,
} from "@nest-boot/graphql";
import { ConnectionManager } from "@nest-boot/graphql-connection";

import { User } from "./user.entity";
import {
  UserConnection,
  UserConnectionArgs,
} from "./user.connection-definition.js";
import {
  PostConnection,
  PostConnectionArgs,
} from "./post.connection-definition.js";

@Resolver(() => User)
export class UserResolver {
  constructor(private readonly cm: ConnectionManager) {}

  @Query(() => UserConnection)
  async users(@Args() args: UserConnectionArgs): Promise<UserConnection> {
    return await this.cm.find(UserConnection, args);
  }

  // Nested connection: resolve a user's posts
  @ResolveField(() => PostConnection)
  async posts(
    @Parent() user: User,
    @Args() args: PostConnectionArgs,
  ): Promise<PostConnection> {
    return await this.cm.find(PostConnection, args, {
      where: { author: user },
    });
  }
}
```

The third argument to `cm.find()` accepts additional `where` filters that are merged with the client's filter/query arguments. This is useful for:

- Scoping queries to the current workspace or user
- Implementing soft-delete (e.g., `where: { deletedAt: null }`)
- Nested connection fields

### Pagination

Supply exactly one of `first` and `last` with an integer from 1 to 100. Use `after` with `first` or `before` with `last`. Missing, conflicting, or out-of-range paging arguments return `BAD_USER_INPUT`.

```graphql
# Forward pagination
query {
  users(first: 10, after: "cursor_abc") {
    edges {
      node {
        id
        name
      }
      cursor
    }
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}

# Backward pagination
query {
  users(last: 10, before: "cursor_xyz") {
    edges {
      node {
        id
        name
      }
    }
    pageInfo {
      hasPreviousPage
      startCursor
    }
  }
}
```

### Filtering

MongoDB-style filter syntax with operators: `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`, `$and`, `$or`, `$regex`.

```graphql
query {
  users(filter: { name: { $regex: "john" }, is_active: { $eq: true } }) {
    edges { node { id name } }
  }
}
```

### Search Query

Human-friendly search syntax that maps to filterable/searchable fields:

```graphql
query {
  users(query: "john email:john@example.com") {
    edges {
      node {
        id
        name
        email
      }
    }
  }
}
```

## GraphQL Logger

The `@nest-boot/graphql-logger` module provides an Apollo Server plugin that adds the resolved operation ID, name, and type to the current structured logger bindings. Logs written after operation resolution automatically include that metadata; the plugin does not record the raw query or variables.

### Installation

```bash
pnpm add @nest-boot/graphql-logger @nest-boot/logger
```

### Registration

```typescript
import { GraphQLLoggerModule } from "@nest-boot/graphql-logger";

@Module({
  imports: [GraphQLLoggerModule],
})
export class CommonModule {}
```

## GraphQL Rate Limiting

The `@nest-boot/graphql-rate-limit` module provides Shopify-style query complexity rate limiting using a pluggable leaky bucket storage driver.

### Installation

```bash
pnpm add @nest-boot/graphql-rate-limit @nest-boot/redis ioredis
```

### Registration

```typescript
import { GraphQLRateLimitModule } from "@nest-boot/graphql-rate-limit";
import { RedisModule } from "@nest-boot/redis";

@Module({
  imports: [RedisModule.forRoot({}), GraphQLRateLimitModule],
})
export class CommonModule {}
```

The rate limit module is directly importable without dynamic registration. By default, it reuses the Redis client provided by `RedisModule`; `@nest-boot/redis` handles connection configuration and `REDIS_URL` parsing. `RedisModule` closes the shared connection, and the rate limit driver leaves it open.

Driver selection follows this order:

1. An explicit custom `driver`.
2. Explicit `connection` options, which create a separate connection owned and closed by the rate limit driver.
3. The shared client from a registered `RedisModule`.
4. Process-local memory when no shared client is available.

**Migration:** The rate limit module no longer reads `REDIS_URL`. Applications that previously set only this variable must register `RedisModule` to keep Redis-backed rate limiting. Explicit `connection` options are also no longer merged with environment configuration. To use environment or shared configuration, move connection options to `RedisModule.forRoot()` or `forRootAsync()` and omit the rate limit module's `connection`.

The memory driver is convenient for local development and single-process applications, but its buckets are not shared across processes or replicas. Use Redis or a custom distributed driver when limits must be global.

Use `forRoot()` when you need to change the bucket thresholds or provide an explicit driver. By default, the bucket holds 2,000 points and restores 100 points per second. The plugin rejects requests whose estimated cost exceeds 1,000 points.

```typescript
import {
  GraphQLRateLimitDriver,
  GraphQLRateLimitModule,
  MemoryGraphQLRateLimitDriver,
} from "@nest-boot/graphql-rate-limit";

const driver: GraphQLRateLimitDriver = new MemoryGraphQLRateLimitDriver();

@Module({
  imports: [
    GraphQLRateLimitModule.forRoot({
      driver,
      maximumAvailable: 2000, // Bucket capacity
      restoreRate: 100, // Points restored per second
    }),
  ],
})
export class CommonModule {}
```

Custom drivers extend `GraphQLRateLimitDriver` and implement its atomic `update()` method. Positive `points` consume capacity and negative `points` restore it. `forRootAsync()` can be used when creating a driver requires injected dependencies.

To supply a custom Redis instance managed outside the rate limit module, pass `new RedisGraphQLRateLimitDriver(redis, false)` as the `driver`. The second argument disables connection ownership, so the caller is responsible for closing it. Omitting that argument preserves the driver's default behavior of closing its client.

### Custom Complexity

With `GraphQLModule` from `@nest-boot/graphql`, `Query`, `Mutation`, `ResolveField`, and `Field` use the return type's static `complexity` as the default for fields that return a single concrete object. Generated Connections and their subclasses provide this callback. Use the explicit `complexity` option to customize list costs or override an inferred default, including setting it to zero.

The rate limiter reserves one point per requested edge and settles that part of the cost using the number of edges returned by the resolver. This applies to cursor-only selections as well. Generated `Edge.node` fields have zero base cost. Fields selected under `node` use their own costs. The callback charges once for the normalized `query` and `filter`. Each comparison and logical group costs one point. Array comparisons such as `$in` cost one point per value, with a minimum of one.

Standalone fields returning `Count` use the filters in their generated `CountArgs` to calculate complexity automatically. Each count costs 10 base points plus one charge for the filters using the list rules. The child fields of `Count` cost zero.

Custom `complexity` callbacks receive the resolver's value before GraphQL serialization through `resolved.result` during settlement. The result can be `null` or `undefined`. With `Query`, `Mutation`, `ResolveField`, or `Field` from `@nest-boot/graphql`, result inference follows NestJS's `@Field` default-value types. Scalar references such as `ID` and `Int` infer `unknown`.

Use `defineComplexity` to export a reusable callback. Pass the return type reference directly and use the callback as the field's `complexity` option.

```typescript
import { defineComplexity } from "@nest-boot/graphql";

export const booksComplexity = defineComplexity(
  [Book],
  ({ childComplexity, resolved }) =>
    resolved ? (resolved.result?.length ?? 0) : 10 * (1 + childComplexity),
);
```

Each root mutation field adds 10 points by default to its result cost. Set `mutationComplexity` on `@Mutation` to change that field's base cost, including setting it to zero. The result cost can come from explicit field complexity, the return type's static complexity, or the selected child fields. A numeric `complexity` adds to the child cost, and a callback uses the same rules as for queries.

Use the `@Complexity()` decorator to emit a `@complexity` schema directive. Set a base value and optional argument names that multiply that value:

```typescript
import { Complexity } from "@nest-boot/graphql-rate-limit";

@Resolver(() => User)
export class UserResolver {
  @Complexity({ value: 2, multipliers: ["first"] })
  @Query(() => UserConnection)
  async users(@Args() args: UserConnectionArgs) {
    return this.cm.find(UserConnection, args);
  }
}
```

The query cost is reported in the response `extensions`, giving clients full transparency over their API usage budget.

## Best Practices

1. **Global CommonModule** — Register `GraphQLModule`, `GraphQLConnectionModule`, and companion modules in a single `@Global()` `CommonModule` that all feature modules share.

2. **Dual Decorators** — Use `@ObjectType()` + `@Entity()` on the same class so your GraphQL schema and database schema are always in sync.

3. **Connection Definitions** — Keep connection builder definitions in a dedicated `*.connection-definition.ts` file next to the entity.

4. **Field Replacement** — Use the `replacement` option in `addField` to expose client-friendly snake_case field names while mapping to camelCase entity properties internally.

5. **Scoped Queries** — Always pass a `where` filter to scope connection queries to the current workspace or tenant.

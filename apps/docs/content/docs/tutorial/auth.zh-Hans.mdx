title: "Auth"
description: "通过会话、API Key、工作区身份与统一守卫提供认证和基于 CASL 的授权。"
---

`@nest-boot/auth` 提供基于 [better-auth](https://www.better-auth.com/) 的身份认证、工作区 API Key 与基于 CASL 的授权，包括 MikroORM 持久化、自动请求上下文中间件，以及同时负责认证和路由权限检查的统一 `AuthGuard`。

## 安装

```bash
pnpm add @nest-boot/auth better-auth @casl/ability
```

## 模块注册

### 基本注册

```typescript
import { AuthModule } from "@nest-boot/auth";
import { Global, Module } from "@nestjs/common";
import { User } from "./user.entity";
import { Account } from "./account.entity";
import { ApiKey } from "./api-key.entity";
import { Session } from "./session.entity";
import { Verification } from "./verification.entity";
import { Workspace } from "./workspace.entity";
import { WorkspaceMember } from "./workspace-member.entity";

export const AuthDynamicModule = AuthModule.forRoot({
  entities: {
    user: User,
    account: Account,
    session: Session,
    verification: Verification,
    workspace: Workspace,
    workspaceMember: WorkspaceMember,
    apiKey: ApiKey,
  },
});

@Global()
@Module({
  imports: [AuthDynamicModule],
})
export class CommonModule {}
```

模块自动完成：

- 使用 MikroORM 适配器创建 better-auth 实例
- 在 `/api/auth/` 注册认证 API 路由（可通过 `basePath` 配置）
- 将会话、选中的工作区、工作区成员和 API Key 解析到 `RequestContext`
- 提供工作区和 API Key 生命周期服务
- 从环境变量读取常用认证配置

### 环境变量

`AuthModule` 可以从环境变量配置默认的 better-auth 实例。通过 `AuthModule.forRoot()` 或 `AuthModule.forRootAsync()` 传入的选项会与这些默认值合并；下方特别说明的环境变量仍可以覆盖嵌套 provider 里的开关。

默认情况下，邮箱密码认证启用，Google、GitHub 和 OIDC 认证禁用，注册允许。需要一次性停止所有已配置登录方式的新用户注册时，设置 `AUTH_DISABLE_SIGN_UP=true`。

#### 通用

这些变量作用于整个 auth 实例。

| 变量                   | 用途                                                                                        | 默认值                     |
| ---------------------- | ------------------------------------------------------------------------------------------- | -------------------------- |
| `AUTH_SECRET`          | 用于签名和加密认证数据的密钥。未设置时回退到 `APP_SECRET`。必须至少 32 个字符且具有高熵值。 | 必填                       |
| `APP_SECRET`           | 未设置 `AUTH_SECRET` 时使用的备用认证密钥。                                                 | `AUTH_SECRET` 未设置时必填 |
| `APP_NAME`             | 传给 better-auth 的应用名称。                                                               | 未设置                     |
| `AUTH_URL`             | 公开的认证基础 URL。未设置时回退到 `APP_URL`。                                              | 未设置                     |
| `APP_URL`              | 未设置 `AUTH_URL` 时使用的备用公开基础 URL。                                                | 未设置                     |
| `AUTH_DISABLE_SIGN_UP` | 设置为 `true` 时，禁止所有已配置登录方式的新用户注册。已有用户仍可登录。                    | 允许注册                   |
| `API_KEY_PREFIX`       | 创建工作区 API Key 时使用的前缀。                                                           | `sk-`                      |

#### Email

邮箱密码认证默认启用。设置 `AUTH_EMAIL_ENABLED=false` 时才会关闭邮箱密码认证。想保留邮箱登录但禁止新用户用邮箱注册时，设置 `AUTH_EMAIL_DISABLE_SIGN_UP=true`。

| 变量                         | 用途                                       | 默认值   |
| ---------------------------- | ------------------------------------------ | -------- |
| `AUTH_EMAIL_ENABLED`         | 除非设置为 `false`，否则启用邮箱密码认证。 | 启用     |
| `AUTH_EMAIL_DISABLE_SIGN_UP` | 设置为 `true` 时禁止新的邮箱密码注册。     | 允许注册 |

#### Google

Google 认证默认禁用。设置 `AUTH_GOOGLE_ENABLED=true` 后，模块会从环境变量配置 better-auth `socialProviders.google`，并在启动时校验 Google 凭据。即使配置了凭据，只要没有设置 `AUTH_GOOGLE_ENABLED=true`，Google 仍保持禁用。

| 变量                          | 用途                                         | 默认值     |
| ----------------------------- | -------------------------------------------- | ---------- |
| `AUTH_GOOGLE_ENABLED`         | 设置为 `true` 时从环境变量启用 Google 认证。 | 禁用       |
| `AUTH_GOOGLE_CLIENT_ID`       | Google OAuth 客户端 ID。                     | 启用时必填 |
| `AUTH_GOOGLE_CLIENT_SECRET`   | Google OAuth 客户端密钥。                    | 启用时必填 |
| `AUTH_GOOGLE_DISABLE_SIGN_UP` | 设置为 `true` 时禁止新的 Google 注册。       | 允许注册   |

#### GitHub

GitHub 认证默认禁用。设置 `AUTH_GITHUB_ENABLED=true` 后，模块会从环境变量配置 better-auth `socialProviders.github`，并在启动时校验 GitHub 凭据。即使配置了凭据，只要没有设置 `AUTH_GITHUB_ENABLED=true`，GitHub 仍保持禁用。

| 变量                          | 用途                                         | 默认值     |
| ----------------------------- | -------------------------------------------- | ---------- |
| `AUTH_GITHUB_ENABLED`         | 设置为 `true` 时从环境变量启用 GitHub 认证。 | 禁用       |
| `AUTH_GITHUB_CLIENT_ID`       | GitHub OAuth 客户端 ID。                     | 启用时必填 |
| `AUTH_GITHUB_CLIENT_SECRET`   | GitHub OAuth 客户端密钥。                    | 启用时必填 |
| `AUTH_GITHUB_DISABLE_SIGN_UP` | 设置为 `true` 时禁止新的 GitHub 注册。       | 允许注册   |

如果手动传入了 `socialProviders.google` 或 `socialProviders.github`，显式的 `*_ENABLED=false` 和禁用注册相关环境变量仍会合并到对应的嵌套 provider 配置中，不需要把凭据也移动到环境变量里。

#### OIDC

Generic OIDC 默认禁用。设置 `AUTH_OIDC_ENABLED=true` 后，模块会注册一个 `providerId: "oidc"` 的 `genericOAuth` provider，并在启动时校验 OIDC 必需配置。

| 变量                        | 用途                                                                                                                            | 默认值                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `AUTH_OIDC_ENABLED`         | 设置为 `true` 时从环境变量启用 generic OIDC 认证。                                                                              | 禁用                   |
| `AUTH_OIDC_CLIENT_ID`       | OIDC 客户端 ID。                                                                                                                | 启用时必填             |
| `AUTH_OIDC_CLIENT_SECRET`   | OIDC 客户端密钥。                                                                                                               | 启用时必填             |
| `AUTH_OIDC_DISCOVERY_URL`   | OIDC discovery 文档 URL。                                                                                                       | 启用时必填             |
| `AUTH_OIDC_PROMPT`          | 可选的 OIDC prompt。支持值：`none`、`login`、`create`、`consent`、`select_account`、`select_account consent`、`login consent`。 | 未设置                 |
| `AUTH_OIDC_SCOPES`          | 逗号分隔的 OIDC scopes。会 trim 空白并忽略空项。                                                                                | `openid,profile,email` |
| `AUTH_OIDC_DISABLE_SIGN_UP` | 设置为 `true` 时禁止新的 OIDC 注册。                                                                                            | 允许注册               |

如果不需要 OIDC，保持 `AUTH_OIDC_ENABLED` 未设置即可。如果需要多个 generic OIDC provider 或自定义 provider 行为，可以手动配置 `plugins`；`AUTH_OIDC_*` 不能和自定义 `genericOAuth` 插件组合使用，因为 better-auth 会为该插件注册同一组 OAuth2 endpoints。

### 异步注册（含 OIDC）

在实际应用中，使用 `forRootAsync` 注入 `ConfigService` 并配置 OAuth/OIDC 提供商：

```typescript
import { AuthModule } from "@nest-boot/auth";
import { ConfigService } from "@nestjs/config";
import { bearer, genericOAuth } from "better-auth/plugins";

import { User } from "./user.entity";
import { Account } from "./account.entity";
import { ApiKey } from "./api-key.entity";
import { Session } from "./session.entity";
import { Verification } from "./verification.entity";
import { Workspace } from "./workspace.entity";
import { WorkspaceMember } from "./workspace-member.entity";

const AuthDynamicModule = AuthModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (configService: ConfigService) => ({
    trustedOrigins: ["*"],
    entities: {
      user: User,
      account: Account,
      session: Session,
      verification: Verification,
      workspace: Workspace,
      workspaceMember: WorkspaceMember,
      apiKey: ApiKey,
    },
    plugins: [
      bearer(),
      genericOAuth({
        config: [
          {
            providerId: "oidc",
            clientId: configService.getOrThrow("AUTH_OIDC_CLIENT_ID"),
            clientSecret: configService.getOrThrow("AUTH_OIDC_CLIENT_SECRET"),
            discoveryUrl: configService.getOrThrow("AUTH_OIDC_DISCOVERY_URL"),
            prompt: "login",
            scopes: ["openid", "profile", "email"],
          },
        ],
      }),
    ],
  }),
});
```

关键选项：

- **`entities`** — 映射 user、account、session、verification、workspace、workspace-member 和 API key 的 MikroORM 实体类
- **`onAuthenticated`** — 会话解析成功后的可选回调，用于补充应用自己的上下文
- **`plugins`** — better-auth 插件（如 `genericOAuth`、`twoFactor` 等）
- **`basePath`** — 自定义认证 API 路径（默认：`/api/auth/`）
- **`trustedOrigins`** — 允许的 CORS 来源

## 认证守卫

将 `AuthGuard` 注册为全局守卫，默认保护所有路由。应导入已配置的动态模块，而不是未配置的 `AuthModule` 类：

```typescript
import { AuthGuard } from "@nest-boot/auth";
import { APP_GUARD } from "@nestjs/core";

@Global()
@Module({
  imports: [AuthDynamicModule],
  providers: [
    {
      provide: APP_GUARD,
      useExisting: AuthGuard,
    },
  ],
})
export class CommonModule {}
```

守卫接受 `RequestContext` 中的有效会话或 API Key。两种身份都不存在时，请求会被拒绝。

### 公开路由

使用 `@Public()` 装饰器跳过特定路由的认证守卫：

```typescript
import { Public } from "@nest-boot/auth";
import { Query, Resolver } from "@nest-boot/graphql";

@Resolver()
export class HealthResolver {
  @Public()
  @Query(() => String)
  health(): string {
    return "ok";
  }
}
```

## 工作区上下文

`AuthModule` 会在认证中间件前解析请求选择的工作区。客户端通过 `x-workspace-id` 请求头或 `workspace_id` Cookie 选择工作区；模块随后解析已认证用户在该工作区中的成员身份，并将两个对象写入 `RequestContext`。

使用内置装饰器读取身份，可以让传输层代码不直接依赖 `RequestContext`：

```typescript
import {
  CurrentWorkspace,
  CurrentWorkspaceMember,
} from "@nest-boot/auth";

currentWorkspace(
  @CurrentWorkspace() workspace: Workspace,
  @CurrentWorkspaceMember() member: WorkspaceMember,
) {
  return { workspace, member };
}
```

`WorkspaceService` 负责与传输协议无关的工作区生命周期：

- `findOne(where)`
- `createWorkspace(user, { name })`
- `updateWorkspace(workspace, { name })`
- `deleteWorkspace(workspace, currentMember)`

创建工作区时会同时创建一个已激活的所有者成员。删除操作是软删除，并且只允许所有者执行。GraphQL Resolver 或 HTTP Controller 只需映射输入输出，并把这些规则委托给服务。

## API Key

`ApiKeyService` 同时管理 User 与 Workspace 所有的 API Key。User Key 会恢复所属用户；只有该用户仍是所选工作区的成员时，才能访问工作区资源。Workspace Key 是独立服务身份，只恢复所属工作区，不会创建当前用户或工作区成员。用户管理自己的 User Key，只有工作区所有者可以管理 Workspace Key。

服务提供：

- `getUserApiKey`、`createUserKey`、`updateUserKey` 与 `deleteUserKey`
- `getWorkspaceApiKey`、`createWorkspaceKey`、`updateWorkspaceKey` 与 `deleteWorkspaceKey`
- `getUserListFilter` 与 `getWorkspaceListFilter`
- `validate(plaintextKey)` 与 `recordUsage(apiKey)`

创建方法只会返回一次明文 Key。数据库会保存完整 Key 的 SHA-256 哈希、可安全展示的 `start` 与 `prefix`、启用状态、权限、过期时间和使用时间。认证成功的请求会自动更新 `lastUsedAt`。

`@nest-boot/auth` 使用字符串存储和判断权限。封闭的权限目录由应用定义，
因此每个产品都可以使用自己的资源和操作：

```typescript
import { UserPermission } from "./auth/enums/user-permission.enum";
import { WorkspacePermission } from "./auth/enums/workspace-permission.enum";

const workspacePermissions: WorkspacePermission[] = [
  WorkspacePermission.WORKSPACE_UPDATE,
  WorkspacePermission.WORKSPACE_MEMBER_CREATE,
];

const userKeyPermissions: (UserPermission | WorkspacePermission)[] = [
  UserPermission.USER_GET,
  WorkspacePermission.WORKSPACE_UPDATE,
];
```

在示例应用中，`User.permissions` 保存 `UserPermission[]`，
`WorkspaceMember.permissions` 保存 `WorkspacePermission[]`，API Key 保存
`(UserPermission | WorkspacePermission)[]`。Workspace Key 只接受工作区域权限，
User Key 可以同时包含两个权限域。数据库使用 `text[]` 列保存权限，应用在写入前
校验每一个值；auth 模块自身始终将这些字段公开为 `string[]`。

API Key 使用 Bearer 方式发送：

```http
Authorization: Bearer sk-4tR9s...
```

不支持 `x-api-key`。客户端还需要 Bearer Session 认证时，按异步注册示例加入 better-auth 的 `bearer()` 插件。Session 认证优先执行：如果 Bearer 凭证能解析为有效 Session，API Key 校验会跳过；否则同一个 Bearer 凭证会作为 API Key 校验。

处理器需要知道当前使用的 Key 实体时，可以使用 `@CurrentApiKey()`：

```typescript
import { CurrentApiKey } from "@nest-boot/auth";

audit(@CurrentApiKey() apiKey: ApiKey | null) {
  return apiKey;
}
```

## 权限授权

通过 `AuthModule` 的 `buildWorkspaceAbility` 和 `buildUserAbility` 分别配置工作区权限与用户权限。路由检查对应权限域时，每个回调在一次请求中最多执行一次，两套 CASL ability 会分别缓存在 `RequestContext` 中。回调可以返回 `null`，此时对应的权限检查会抛出 `ForbiddenException`。

```typescript
import { AuthModule, PermissionAbilityBuilder } from "@nest-boot/auth";
import { RequestContext } from "@nest-boot/request-context";

import { User } from "./user.entity";
import { Post } from "./post.entity";

export const AuthDynamicModule = AuthModule.forRoot({
  entities: {
    user: User,
    account: Account,
    session: Session,
    verification: Verification,
    workspace: Workspace,
    workspaceMember: WorkspaceMember,
    apiKey: ApiKey,
  },
  buildWorkspaceAbility: () => {
    const { can, build } = new PermissionAbilityBuilder();

    can("read", Post);

    return build();
  },
  buildUserAbility: () => {
    const user = RequestContext.get(User);

    if (!user) {
      return null;
    }

    const { can, build } = new PermissionAbilityBuilder();

    can("read", Post);
    can("update", Post, { authorId: user.id });

    return build();
  },
});
```

同一个全局 `AuthGuard` 会先检查身份认证，再执行 `@Can` 权限元数据，不需要注册第二个权限模块或守卫。`@Public()` 只跳过认证要求；如果公开路由同时声明了 `@Can`，权限检查仍会执行。

`@Can` 默认检查工作区 Ability。对于属于已认证用户、而非当前工作区的接口，在第三个参数中传入 `{ scope: "user" }`。Workspace API Key 只能通过工作区权限检查；User API Key 可以通过用户权限检查。应用自行决定 `User.permissions` 如何参与 `buildUserAbility`，API Key 请求再将该 Ability 与 Key permissions 取交集。访问工作区时还必须拥有实时有效的成员身份，并将工作区 Ability 与 Key permissions 取交集。读取操作属于认证后的基础访问，应用定义的权限字符串用于限制权限目录中声明的管理操作。

### 保护路由

当权限只依赖资源类型时，直接传入 subject class。

```typescript
import { Can } from "@nest-boot/auth";
import { Query, Resolver } from "@nestjs/graphql";

import { Post } from "./post.entity";

@Resolver(() => Post)
export class PostResolver {
  @Can("read", Post)
  @Query(() => [Post])
  posts() {
    return this.postService.findAll();
  }
}
```

个人资源或应用级操作使用用户权限域：

```typescript
import { Can } from "@nest-boot/auth";

@Can("read", User, { scope: "user" })
@Query(() => User)
me(@CurrentUser() user: User) {
  return user;
}
```

当 ability 需要具体资源实例时，使用 subject factory。factory 的第一个参数是当前 controller 或 resolver 实例，后续参数是被装饰的方法参数。它支持 HTTP、GraphQL 和自定义参数装饰器。

```typescript
import { Can } from "@nest-boot/auth";
import { Args, Mutation, Resolver } from "@nestjs/graphql";

@Resolver(() => Post)
export class PostResolver {
  constructor(private readonly postService: PostService) {}

  @Can("update", (self: PostResolver, id: string) =>
    self.postService.findOneOrFail({ id }),
  )
  @Mutation(() => Post)
  updatePost(@Args("id") id: string) {
    return this.postService.update(id);
  }
}
```

### 在服务中检查权限

`AuthGuard` 为当前请求准备 ability 后，可以在底层代码中使用 `can` 同步检查权限，或通过 `getPermissionAbility()` 直接访问 CASL ability。两个工具默认使用工作区权限域，也可以显式选择用户权限域。

```typescript
import { can } from "@nest-boot/auth";
import { ForbiddenException, Injectable } from "@nestjs/common";

@Injectable()
export class PostService {
  update(post: Post) {
    if (!can("update", post)) {
      throw new ForbiddenException();
    }

    // 更新 Post。
  }
}
```

两个工具都要求路由上的 `@Can` 已经让守卫准备好 ability；如果 ability 不存在，它们会抛出 `ForbiddenException`。

```typescript
can("read", user, { scope: "user" });
getPermissionAbility("user");
```

```typescript
  }

```

```typescript
import { CurrentSession } from "@nest-boot/auth";
```

## 实体设置

继承模块提供的基础实体类来定义你的认证实体：

```typescript
import { Entity, PrimaryKey, Property, t } from "@mikro-orm/postgresql";
import { BaseUser } from "@nest-boot/auth";
import { Field, ID, ObjectType } from "@nest-boot/graphql";

@ObjectType()
@Entity()
export class User extends BaseUser {
  @Field(() => ID)
  @PrimaryKey({ type: t.bigint })
  id!: string;

  @Field(() => String)
  @Property({ type: t.string })
  name!: string;

  @Field(() => String)
  @Property({ type: t.string })
  email!: string;
}
```

模块还提供 `BaseAccount`、`BaseSession`、`BaseVerification`、`BaseWorkspace`、`BaseWorkspaceMember` 和 `BaseApiKey`。每个配置实体都应继承对应的基础类。基础类定义认证服务需要的字段和关联；子类可以按应用需要重新声明字段的列类型、GraphQL 注解、索引，并添加其他属性。

## NestJS 集成

包含认证的完整 `main.ts` 设置：

```typescript
import { Logger } from "@nest-boot/logger";
import { ValidationPipe } from "@nestjs/common";
import { NestFactory } from "@nestjs/core";
import { AppModule } from "./app/app.module";

async function bootstrap() {
  const app = await NestFactory.create(AppModule, {
    bufferLogs: true,
    cors: true,
  });

  app.useLogger(await app.resolve(Logger));
  app.useGlobalPipes(
    new ValidationPipe({ transform: true, forbidUnknownValues: false }),
  );
  app.enableShutdownHooks();

  await app.listen(process.env.PORT ?? 4000);
}

void bootstrap();
```

## 最佳实践

1. **全局守卫** — 始终将 `AuthGuard` 注册为 `APP_GUARD`，对例外路由使用 `@Public()`，而不是逐路由添加守卫。

2. **稳定的上下文装饰器** — 传输层使用 `CurrentWorkspace`、`CurrentWorkspaceMember` 和 `CurrentApiKey`，避免直接依赖应用实体 token。

3. **环境变量** — 将 `AUTH_SECRET` 存储在环境变量中，确保至少 32 个字符且具有高熵值。

4. **RLS 上下文** — 将认证与 PostgreSQL RLS 结合时，从 `RequestContext` 中已有的工作区和成员身份派生数据库上下文。参见 [Row-Level Security 教程](/docs/tutorial/row-level-security)。

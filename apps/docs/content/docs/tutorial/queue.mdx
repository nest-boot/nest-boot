`@nest-boot/queue` integrates [BullMQ](https://docs.bullmq.io/) with Nest. Queue names and processor bindings are static declarations; runtime settings belong in constructors. `@nestjs/bullmq` is not required.

## Installation

```bash
pnpm add @nest-boot/queue @nest-boot/command @nest-boot/request-context bullmq zod
```

## Define and inject a queue

`@Queue()` derives a fixed Redis name by removing the trailing `Queue` and converting the class name to kebab-case: `EmailQueue` becomes `email`, and `JobQueue` becomes `job`. An explicit `@Queue("email")` overrides the generated name. Pass Redis settings and default job options to `super(options)`. Omit the constructor when the defaults are sufficient. `BaseQueue` reads `REDIS_URL` unless `connection` is supplied explicitly.

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";
import { z } from "zod";

@Queue("email")
export class EmailQueue extends BaseQueue {
  readonly jobSchemas = {
    send: {
      data: z.object({ to: z.email(), subject: z.string() }),
      result: z.object({ messageId: z.string() }),
    },
    welcome: {
      data: z.object({ userId: z.string() }),
    },
  };

  constructor() {
    super({ defaultJobOptions: { attempts: 3 } });
  }
}

export type EmailData = z.input<EmailQueue["jobSchemas"]["send"]["data"]>;
```

Import `QueueModule` once in the application module tree and register each queue class as a provider. Its infrastructure providers are global. Redis queue operation does not require database, GraphQL, auth or schedule modules.

```ts
import { QueueModule } from "@nest-boot/queue";
import { Injectable, Module } from "@nestjs/common";
import { EmailQueue, type EmailData } from "./email.queue";

@Injectable()
export class EmailService {
  constructor(private readonly queue: EmailQueue) {}

  async send(data: EmailData) {
    return await this.queue.add("send", data);
  }
}

@Module({
  imports: [QueueModule],
  providers: [EmailQueue, EmailService],
  exports: [EmailQueue],
})
export class EmailModule {}
```

No `registerQueue()` or `@InjectQueue()` is needed. Queue classes inherit BullMQ methods and may add business methods. Keep queue providers singleton and names unique within an application. Every concrete queue class declares its own `@Queue(name)`. Export and reuse the queue provider wherever it is consumed. Nest closes the queue during shutdown.

## Job schemas and inferred types

Import the task type `Job<Q, N>` from `@nest-boot/queue`. The optional database entity `JobEntity` comes from `@nest-boot/queue-api`. `JobEntity` aliases the existing entity class, so the database table remains `job` and the GraphQL type remains `Job`. Internal native BullMQ imports use `BullmqJob`, `BullmqQueue`, `BullmqWorker` and `BullmqQueueEvents`.

Declare allowed names in the instance property `readonly jobSchemas`. No BaseQueue generics or `as const` are needed. Keep the property's inferred type; annotating it as the broad JobSchemas map loses its concrete names.

Each entry requires `data: z.object(...)`. The optional `result` accepts other Zod schemas; omitting it declares no business result and infers void. Names come from the map keys without z.literal. add, addBulk and upsertJobScheduler infer the allowed names and corresponding data. Each job has a required method such as `processSend(job: Job<EmailQueue, "send">)`. The parameter annotation is required; optional extra parameters must accept `token?: string` and `signal?: AbortSignal`, with no additional required arguments. The return type can be inferred and must match that job’s result schema.

```ts
await queue.add("send", { to: "user@example.com", subject: "Hello" });
await queue.add("welcome", { userId: "123" });
// queue.add("unknown", {});                 // Type error
// queue.add("send", { userId: "123" });      // Type error
```

Data is checked before enqueueing, and bulk submissions validate every entry before writing any jobs. Scheduler IDs are independent of job names; queues with schemas require a template with name and data. Workers validate stored input again before invoking the handler, including jobs submitted outside the wrapper, and validate results before completion. An omitted result requires the handler to return undefined. Validation failures follow BullMQ's failure and configured retry behavior. Async validation is supported.

Schemas validate a stable JSON contract. Queue calls `parseAsync()` before enqueueing, before each processing attempt and before completion for a declared result schema, but discards every parsed result. Validation failures retain the original ZodError details. Redis, the processor's `job.data`, `updateData()` and stored return values all use the original schema input types (`z.input`); `Job` is the same type for producers and processors.

Defaults, coercions, transforms and unknown-field stripping are not applied to the values used by the queue. Zod still executes schema callbacks during validation, so keep them free of side effects and perform business conversions explicitly. Use `z.strictObject()` when unknown fields should be rejected. Native BullMQ `updateData()` remains unchanged; updated data is validated on the next processing attempt. Schemas should describe JSON wire values rather than Date/BigInt values that cannot survive JSON unchanged. Queues without jobSchemas can be used as producers; processors require concrete jobSchemas and one processXXX method per job. The generic process(job) API is not supported.

## Process jobs

`@Processor(EmailQueue)` binds a singleton processor to a queue class. Worker settings go in `super(workerOptions)`; the default constructor requires no configuration. Worker lifecycle stays with `BaseProcessor`; no separate Worker provider is declared.

```ts
import { BaseProcessor, Processor, type Job } from "@nest-boot/queue";
import { EmailQueue } from "./email.queue";
import { NotificationService } from "./notification.service";

@Processor(EmailQueue)
export class EmailProcessor extends BaseProcessor {
  constructor(private readonly notifications: NotificationService) {
    super({ concurrency: 5 });
  }

  async processSend(job: Job<EmailQueue, "send">) {
    const messageId = await this.notifications.send(job.data);
    return { messageId };
  }

  async processWelcome(job: Job<EmailQueue, "welcome">) {
    await this.notifications.welcome(job.data.userId);
  }
}
```

The managed Worker dispatches each name to `process${PascalCase<name>}`: `send` calls `processSend`, and `send-email` calls `processSendEmail`. Type checking requires every declared job's method, its exact `Job<QueueClass, "name">` parameter and its matching Promise result. A missing result schema requires a void result. Names that map to the same method, such as `send-email` and `sendEmail`, are rejected by type checking and runtime schema checks.

An unknown job name or missing handler fails the job at runtime with `UnrecoverableError`, preserving the error reason and skipping automatic retries. This also covers jobs written by external producers or older deployments. Other validation and handler failures follow the configured retry policy.

Register `EmailProcessor` and `EmailQueue` as providers, or import the module exporting the queue. Consumer-only applications also register their queue provider. Missing queues fail startup before workers are created. Workers inherit their queue's connection, prefix and telemetry. Import native `Job`, `Queue`, `Worker` and `QueueEvents` directly from `bullmq` when needed.

The shared ESLint config enables `@nest-boot/queue/processor-name`: the processor class must match its queue class name, replacing the trailing `Queue` with `Processor`. For example, `@Processor(EmailQueue)` requires `EmailProcessor`, and `JobQueue` requires `JobProcessor`. This naming check runs during linting and is independent of the Redis queue name.

## Run workers separately

Queue event readers start in every application. Business Workers start through `QueueManager`. For a separate foreground process, configure `src/cli.ts` with `CommandFactory.run(AppModule)` and import `CommandModule` as described in [Command](/docs/tutorial/command):

```bash
pnpm exec nb queue:start
pnpm exec nb queue:start --queue email --queue report-queue
```

Omit `--queue` to start all consumers. With `--queue`, only matching Processors run; the same filter applies to `job`. To run business processing and history synchronization together, select both names, for example `--queue email --queue job`. Registered queues without a Processor do not match; if the filter matches no consumers, the command reports an error without creating Workers. Unknown names fail before transports are created. Queue providers remain injectable in HTTP, REPL and ordinary commands. Scheduled handlers register during application startup; the schedule Worker starts when selected. SIGINT and SIGTERM drain active work before closing dependencies. `queue:start` is the only `queue:*` command.

Programmatic applications inject `QueueManager` and call `await manager.start(["email"])` after initialization. Every selected transport becomes ready before consumers run. `manager.waitForStop()` rejects on fatal consumer loop failures.

### Singleton processors and request context

Processors must be singletons. Request-scoped and transient processors are rejected during initialization, including processors made request scoped by their dependencies. The same Processor instance handles all jobs. Avoid storing current-job state on the instance.

Each handler invocation gets a fresh `RequestContext` with type `"queue"` and the current `JOB_REF`; concurrent jobs have independent contexts. Context middleware runs before the handler. Read current-job values inside methods:

```ts
import { JOB_REF } from "@nest-boot/queue";
import { RequestContext } from "@nest-boot/request-context";
import type { Job as BullmqJob } from "bullmq";

// Inside processSend() or another method called for the current job:
const context = RequestContext.current();
const currentJob = RequestContext.get<BullmqJob>(JOB_REF);
console.log(context.id, currentJob?.id);
```

Do not inject `JOB_REF` into a singleton constructor or capture its context there. Handler errors propagate to BullMQ; recoverable errors follow its retry policy. The `worker` getter is available after `QueueManager.start()`.

## Runtime queue configuration

Inject application configuration through normal Nest dependencies and pass the resulting options to `super()`. The name remains fixed in `@Queue(name)`.

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";
import { ConfigService } from "@nestjs/config";

@Queue("email")
export class EmailQueue extends BaseQueue {
  constructor(config: ConfigService) {
    super({
      connection: { host: config.getOrThrow<string>("REDIS_HOST") },
      defaultJobOptions: {
        attempts: config.get<number>("EMAIL_JOB_ATTEMPTS", 3),
      },
    });
  }
}
```

For asynchronous settings, register an asynchronous factory provider and inject its result. Nest waits for it before creating the queue. Queue classes use ordinary Nest construction with no hidden arguments or construction context. Tests and custom factories may also instantiate them directly with `new`.

## Redis storage and event synchronization

Queues use BullMQ's Redis backend. `BaseQueue` reads `REDIS_URL`; explicit constructor `connection` options override it. The `prefix` option selects the Redis namespace and is inherited by workers and internal event readers. Queue state stays in Redis, and `queue:migrate` is no longer registered. Standard application migrations manage Job history.

Each registered Queue has a QueueEvents reader, started automatically in HTTP, REPL and producer-only applications. `processor.worker` is a read-only getter available after `QueueManager.start()`, and `queue.queueEvents` is a read-only getter available after application bootstrap. Creation and shutdown are managed internally through Symbol references; processors provide no event subscription wrappers. It reads the queue’s `<prefix>:<queue>:events` stream. Only the optional QueueApiModule forwards snapshots to its `job` queue; QueueModule alone does not submit database snapshots. The source stream ID is passed unchanged from the callback's second argument.

When QueueApiModule is imported, `job` uses BullMQ deduplication with the qualified source queue name and stream ID; duplicates from application replicas are suppressed for 24 hours. Queue-api excludes its own `job` queue from event forwarding to prevent recursion. Application bootstrap waits for reader connections. Readers use BullMQ's default starting position and listen for new events without replaying history on startup or restart. Connection readiness does not guarantee that the first stream read has started; events preceding that read are not replayed. Keep Redis jobs long enough to capture full snapshots if complete names, payloads and results are required. Auto-removal can leave only partial terminal event information.

## Database history and GraphQL

Database records and GraphQL queries are optional and provided by `@nest-boot/queue-api`. Install it with its Database, GraphQL, GraphQL Connection and Auth peer dependencies, configure those global modules in the application, then import `QueueApiModule`. Queue-api does not depend on schedule. Configure the global `DatabaseModule` once in the application and register `JobEntity`. Queue-api injects that global `EntityManager` without importing or registering `DatabaseModule` again. Processors, services and resolvers are ordinary providers; there is no optional integration detection or `graphql` option. API applications configure `GraphQLModule`; CLI entry points use the same global database configuration.

Register `JobEntity` as a normal entity with `@nest-boot/database`, using the same entity list at runtime and in the MikroORM CLI. Standard application migrations manage the table and its indexes; Job history has no RLS policy. Table names, column names and schema follow ORM defaults. Queues automatically read `REDIS_URL`; an explicit `connection` takes precedence.

```ts
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { DatabaseModule } from "@nest-boot/database";
import { QueueModule } from "@nest-boot/queue";
import { JobEntity, QueueApiModule } from "@nest-boot/queue-api";

const database = DatabaseModule.forRoot({
  driver: PostgreSqlDriver,
  clientUrl: process.env.DATABASE_URL,
  entities: [JobEntity],
});
// Import QueueModule in the application; configure individual queues in their constructors.
const queues = QueueModule;
const jobApi = QueueApiModule;
```

`JobQueue` and `JobProcessor` belong to queue-api and use the standard `@Queue()` / `@Processor(JobQueue)` lifecycle. QueueManager discovers queues once and creates their native event readers. JobService subscribes before readers start and provides history queries and event forwarding. On shutdown, it drains source Workers, closes source readers and flushes pending snapshots, then drains the Job Worker. The sync schema rejects invalid states, timestamps and metadata before enqueueing. The `job` queue participates in normal queue filters and health checks. Without QueueApiModule, no `job` queue is registered and no database snapshots are submitted.

The Job worker starts with `nb queue:start`. Like every other Processor, it runs when no queue filter is provided or its name is selected. `nb queue:start --queue job` starts Job synchronization and cleanup alone. Failed database writes use exponential backoff with up to 20 attempts. Producers continue to enqueue Redis jobs while database history is unavailable.

The built-in `job` queue has `sync` and `cleanup` jobs. JobService registers a single BullMQ Job Scheduler for cleanup at 00:00 UTC every day, shared by application replicas. JobProcessor deletes records whose last event is more than 30 days old in batches of up to 1000, regardless of status. Records with `lastEventMs = 0` use `createdAt` instead. Cleanup only removes database history and leaves Redis jobs intact, including long-running or delayed jobs. A later event recreates a deleted record with a new UUID. Cleanup runs when the `job` Worker is running and requires no dependency on `@nest-boot/schedule`.

Job history stores only `id`, `queue`, `jobId`, `name`, `data`, `status`, `progress`, `returnValue`, `failedReason`, `createdAt`, `startedAt`, `finishedAt`, `lastEventMs` and `lastEventSeq`. The three timestamps are ordinary database date columns; locking, scheduling, dependencies and retry configuration stay in Redis.

The Job table uses a database-generated UUID primary key (`gen_random_uuid()`), with the original BullMQ ID stored separately as `jobId`. A unique `(queue, jobId)` constraint identifies the same job across events. `last_event_ms` and `last_event_seq` are bigint columns storing the source stream's `milliseconds-sequence` ID. Inserts ignore conflicts and updates atomically require a strictly greater pair. Repeated or out-of-order events cannot replace a newer state or change the UUID, even after Redis deduplication expires. History reads are asynchronous; deleting a Redis job does not delete its history.

Job queries are split into `userJob` / `userJobs`, `workspaceJob` / `workspaceJobs`, and `systemJob` / `systemJobs`. AuthGuard protects every entry. User queries match `data.userId` against the authenticated user. Workspace queries match `data.workspaceId` against the currently selected workspace after active membership and read authorization. System queries require a configured administrator (`user.adminRoles`) and match only records where both owner fields are absent or JSON null; empty strings do not qualify. API keys cannot inherit their owner's administrator access. There is no unscoped `job` / `jobs` or admin-wide query.

Mark queue classes with the parameterless `@QueueVisible()` decorator from `@nest-boot/queue-api` to allow their records in these queries. Only explicitly marked queues registered in the API application are visible; subclasses need their own marker. Single-record reads, pagination and counts all exclude hidden queues, including when client filters select them. With no visible queues, queries return empty results. Visibility does not replace authorization, and unmarked queues still synchronize and clean up their database records.

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";
import { QueueVisible } from "@nest-boot/queue-api";

@QueueVisible()
@Queue()
export class EmailQueue extends BaseQueue {}
```

`JobService` injects `EntityManager` directly and provides `getUserJob`, `getWorkspaceJob`, `getSystemJob` and their `get*JobConnection` methods without exposing generic CRUD operations. They combine fixed ownership constraints with client filters for single rows, page nodes and counts. Missing identity and unauthorized workspace access are rejected. Multiple query scopes can run together without changing database context. No Job RLS policy or request session variables are used; direct ORM access remains a trusted internal API without ownership enforcement.

GraphQL exposes only `id`, `queue`, `name`, `status`, numeric `progress` and timestamps. Payloads, results, errors and native job identifiers stay private. Filtering supports queue, name, status and creation time. Only CREATED_AT is sortable, defaulting to descending creation time with ID as an internal tie-breaker. User and workspace expression indexes lead with the corresponding identity, followed by created_at and id. A partial index on (created_at, id) covers system tasks with neither owner.

For existing PostgreSQL-backed deployments, drain or migrate operational jobs before switching transports. Preserve any required history, introduce `jobId`, UUID defaults and the two event-version columns, and update clients to use UUID history IDs. Redis prefixes are independent of ORM database configuration.

## Best Practices

1. **Separate Queues** — Use dedicated queues for different job types (email, file-ops, etc.) with appropriate concurrency settings.

2. **Job IDs** — Use deterministic BullMQ job IDs for idempotent submissions; history UUIDs are generated separately by the database.

3. **Structured Logging** — Use `Logger.assign()` in processors to attach job context to log entries.

4. **Cleanup** — Set `removeOnComplete` and `removeOnFail` to auto-clean old jobs.

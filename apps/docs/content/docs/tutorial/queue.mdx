The `@nest-boot/queue` module wraps [`@nestjs/bullmq`](https://docs.nestjs.com/techniques/queues) for distributed job processing with Redis-backed queues. It also integrates job history and GraphQL queries by discovering registered application services.

## Installation

```bash
pnpm add @nest-boot/queue @nest-boot/request-context @nestjs/bullmq bullmq
```

## Module Registration

Register `QueueModule` in your `CommonModule` to configure the Redis connection:

```typescript
import { QueueModule } from "@nest-boot/queue";
import { Module } from "@nestjs/common";

@Module({
  imports: [QueueModule],
})
export class AppModule {}
```

The module reads and parses `REDIS_URL` automatically. You can also call `QueueModule.forRoot()` or `forRootAsync()` with an explicit BullMQ `connection`.

## Defining Queues

Register named queues in feature modules:

```typescript
import { QueueModule } from "@nest-boot/queue";
import { Module } from "@nestjs/common";

@Module({
  imports: [
    QueueModule.registerQueue({
      name: "file-ops-queue",
      defaultJobOptions: {
        removeOnComplete: { age: 60 * 60 },
        removeOnFail: { age: 60 * 60 },
      },
    }),
  ],
  providers: [FileService, FileOpsProcessor],
})
export class FileModule {}
```

## Adding Jobs

Inject `Queue` using `@InjectQueue()` to add jobs:

```typescript
import { InjectQueue } from "@nest-boot/queue";
import { Injectable } from "@nestjs/common";
import { Queue } from "bullmq";

interface EmailJobData {
  to: string;
  subject: string;
  body: string;
}

@Injectable()
export class EmailService {
  constructor(
    @InjectQueue("email-queue")
    private readonly emailQueue: Queue<EmailJobData>,
  ) {}

  async sendEmail(data: EmailJobData): Promise<string> {
    const job = await this.emailQueue.add("send", data, {
      jobId: `email-${Date.now()}`,
    });

    return job.id!;
  }
}
```

## Processing Jobs

Create a processor by extending `WorkerHost` with the `@Processor()` decorator:

```typescript
import { OnWorkerEvent, Processor, WorkerHost } from "@nest-boot/queue";
import { Logger } from "@nest-boot/logger";
import { Job } from "bullmq";
import { NotificationService } from "./notification.service";

@Processor("email-queue", { concurrency: 5 })
export class EmailProcessor extends WorkerHost {
  constructor(
    private readonly logger: Logger,
    private readonly notificationService: NotificationService,
  ) {
    super();
    this.logger.setContext(EmailProcessor.name);
  }

  async process(job: Job<EmailJobData>): Promise<void> {
    const { to, subject, body } = job.data;

    this.logger.assign({ jobId: job.id, to });
    this.logger.log("Processing email job");

    await this.notificationService.sendEmail({ to, subject, body });

    this.logger.log("Email sent successfully");
  }

  @OnWorkerEvent("completed")
  onCompleted(job: Job<EmailJobData>): void {
    this.logger.log(`Email job ${job.id} completed`);
  }
}
```

Nest Boot's `@Processor()` wraps each job in a `RequestContext`, stores BullMQ's `JOB_REF`, and then invokes the normal `@nestjs/bullmq` processor.

## Queue Events

Import `OnWorkerEvent` and `OnQueueEvent` from `@nest-boot/queue` to give each event callback an independent `RequestContext` and run registered context middleware. An event emitted inside another context does not inherit its EntityManager or other contextual values.

Use `@OnWorkerEvent()` on a `WorkerHost` marked with `@Processor()` to observe that worker, as in `onCompleted()` above. Use `@OnQueueEvent()` on a separate `QueueEventsHost` to observe events across the queue:

```typescript
import {
  QueueModule,
  OnQueueEvent,
  QueueEventsHost,
  QueueEventsListener,
} from "@nest-boot/queue";
import { RequestContext } from "@nest-boot/request-context";
import { Logger, Module } from "@nestjs/common";

@QueueEventsListener("email-queue")
export class EmailQueueEvents extends QueueEventsHost {
  private readonly logger = new Logger(EmailQueueEvents.name);

  @OnQueueEvent("completed")
  onCompleted(event: { jobId: string }, eventId: string): void {
    this.logger.log({
      jobId: event.jobId,
      eventId,
      contextId: RequestContext.id,
    });
  }
}

@Module({
  imports: [QueueModule.registerQueue({ name: "email-queue" })],
  providers: [EmailQueueEvents],
})
export class EmailEventsModule {}
```

Register both kinds of listeners as providers and keep them singleton-scoped; Nest does not register event listeners on request-scoped providers.

All these contexts use type `"queue"`. Worker `active`, `completed`, `progress`, and job-bearing `failed` events bind `JOB_REF` and use the Job ID as the context ID. A `stalled` event supplies only a Job ID. QueueEvents payloads supply event data rather than Jobs: their `jobId` becomes the context ID, but `JOB_REF` is not bound. Events without a Job ID get a generated context ID. No Redis lookup is performed to fetch a Job.

Handler and context middleware failures are caught and logged to prevent unhandled promise rejections. BullMQ does not wait for asynchronous listeners or retry jobs when a listener fails; errors from `process()` still propagate to BullMQ normally. Context middleware can be asynchronous, so do not depend on synchronous listener side effects.

These behaviors apply only to decorators imported from `@nest-boot/queue`. Callbacks registered directly with `worker.on()`, `queue.on()`, or `queueEvents.on()` need explicit wrapping, such as `RequestContext.run()`, and asynchronous error handling.

## Integrated job history and GraphQL

`QueueModule` discovers the application's registered integrations automatically. No `persistence` or `graphql` switches are needed:

| Application configuration                      | Behavior                                                                        |
| ---------------------------------------------- | ------------------------------------------------------------------------------- |
| Queue only, or no registered `Job` entity      | BullMQ queues and workers only                                                  |
| `DatabaseModule` and the built-in `Job` entity | Persist local queue/worker events; provide `JobHistoryService` and `JobService` |
| Database history plus `GraphQLModule`          | Also provide `job(id)` and the `jobs` connection                                |

Installing a package alone does not enable its integration. Database and GraphQL packages are optional peers; plain queues do not require either. Add `@nest-boot/database` for persistence and `@nest-boot/graphql` plus `@nest-boot/graphql-connection` for GraphQL, with their documented peer dependencies.

```typescript
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { DatabaseModule } from "@nest-boot/database";
import { GraphQLModule } from "@nest-boot/graphql";
import { QueueModule } from "@nest-boot/queue";
import { entities as queueEntities } from "@nest-boot/queue/persistence";
import { Module } from "@nestjs/common";

@Module({
  imports: [
    DatabaseModule.forRoot({
      driver: PostgreSqlDriver,
      entities: [...queueEntities, "dist/**/*.entity.js"],
      entitiesTs: [...queueEntities, "src/**/*.entity.ts"],
    }),
    GraphQLModule,
    QueueModule.forRoot({
      history: { jobTTL: 7 * 24 * 60 * 60 * 1000, excludeQueues: ["schedule"] },
      // Authorize this request using your application's verified identity.
      // Return a MikroORM filter for visible jobs, or null to deny access.
      getJobReadFilter: () => null,
    }),
  ],
})
export class JobsModule {}
```

Add `queueEntities` to **both** the application's database options and the MikroORM CLI configuration. Generate, review and apply the migration before starting workers. Runtime discovery does not create or alter tables. The built-in table is `job`, with IDs of the form `queueName:jobId`.

`getJobReadFilter` is evaluated for every read. Its scope applies to single-job queries, pagination and counts. Missing callbacks, `null` and `undefined` deny access. Returning `{}` explicitly allows all jobs; do so only after checking the caller's authorization. Task payloads and results can contain sensitive data. Applications remain responsible for assigning trustworthy job ownership when enqueueing and, where used, configuring their own RLS policies. The example server retains its user/workspace RLS policy using MikroORM's `discovery.onMetadata` hook.

For async registration, put `history` and `getJobReadFilter` in the `forRootAsync` factory result. Services and the built-in entity are available from `@nest-boot/queue/persistence`; GraphQL connection types and the resolver are available from `@nest-boot/queue/graphql`. These are entry points in the same package, separated so importing plain queues does not load optional dependencies. Only import the GraphQL entry point in applications that install its peers.

The `jobs` connection supports queue, name, status and date filters, name search, cursor pagination and sorting. `job(id)` returns `null` for missing or out-of-scope jobs. Query authorization is enforced in `JobService`, including direct service calls.

History observes **local** Queue and Worker events. It is a best-effort history mirror, not a durable audit log or a replacement for BullMQ state. Each write forks an EntityManager; failures are logged without failing workers. `history.includeQueues` and `history.excludeQueues` select queues. `history.convertJobToEntityData` can transform persisted values. An owned hourly timer deletes records whose last update is older than `history.jobTTL` (30 days by default), and is stopped during shutdown. `ScheduleModule` is not required for history cleanup.

### Migrating from queue-database

`@nest-boot/queue-database` has been removed from the repository. Migrate to the integrated `@nest-boot/queue` package. Previously published versions remain on npm but do not receive this update.

To adopt the integrated API, remove `QueueDatabaseModule`, register the built-in `Job` entity instead of the application's previous entity, move history options under `QueueModule.history`, and configure `getJobReadFilter`. Remove application-owned `JobResolver`, `JobService` and connection definitions to avoid duplicate GraphQL fields. Review the generated migration carefully to preserve existing job data, additional fields and RLS policies.

## Best Practices

1. **Separate Queues** — Use dedicated queues for different job types (email, file-ops, etc.) with appropriate concurrency settings.

2. **Job IDs** — Use deterministic or Sonyflake-based job IDs for idempotency and traceability.

3. **Structured Logging** — Use `Logger.assign()` in processors to attach job context to log entries.

4. **Cleanup** — Set `removeOnComplete` and `removeOnFail` to auto-clean old jobs.

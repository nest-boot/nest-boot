`@nest-boot/queue` integrates [BullMQ](https://docs.bullmq.io/) directly with Nest. Queue classes are injectable providers; consumers refer to the same class. `@nestjs/bullmq` is not required.

## Installation

```bash
pnpm add @nest-boot/queue @nest-boot/request-context bullmq
```

## Define and inject a queue

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";

export interface EmailData {
  to: string;
  subject: string;
}

@Queue({
  name: "email",
  defaultJobOptions: { attempts: 3, removeOnComplete: { age: 3600 } },
})
export class EmailQueue extends BaseQueue<EmailData> {}
```

Add the queue class to `providers`. `QueueModule` reads `QUEUE_DATABASE_URL` / `DATABASE_URL`; use `forRoot()` or `forRootAsync()` to set an explicit connection and shared defaults. Register `QueueModule` once in the application, using either the plain module or a root configuration. Its providers are global; feature modules and `ScheduleModule` use that registration without importing it again.

```ts
import { QueueModule } from "@nest-boot/queue";
import { Injectable, Module } from "@nestjs/common";
import { EmailQueue, type EmailData } from "./email.queue";

@Injectable()
export class EmailService {
  constructor(private readonly queue: EmailQueue) {}

  async send(data: EmailData) {
    return await this.queue.add("send", data);
  }
}

@Module({
  imports: [QueueModule],
  providers: [EmailQueue, EmailService],
  exports: [EmailQueue],
})
export class EmailModule {}
```

No `registerQueue()` or `@InjectQueue()` is needed. Queue classes inherit BullMQ's methods and can add domain-specific methods. Keep queue providers singleton-scoped and queue names unique within an application. Export a queue from its owning module and import that module where needed instead of constructing additional instances. Nest closes each queue during shutdown.

If a queue class declares its own constructor for business dependencies, inject `QueueFactory` and call `super(factory)`. `QueueFactory.create()` is for classes using the inherited constructor.

## Process jobs

```ts
import { BaseProcessor, OnWorkerEvent, Processor } from "@nest-boot/queue";
import { Job } from "bullmq";
import { EmailQueue, type EmailData } from "./email.queue";
import { NotificationService } from "./notification.service";

@Processor(EmailQueue, { concurrency: 5 })
export class EmailProcessor extends BaseProcessor {
  constructor(private readonly notifications: NotificationService) {
    super();
  }

  async process(job: Job<EmailData>) {
    await this.notifications.send(job.data);
  }

  @OnWorkerEvent("completed")
  onCompleted(job: Job<EmailData>) {
    console.log(`Completed ${job.id}`);
  }
}
```

Register `EmailProcessor` as a provider alongside `EmailQueue` (or import the module exporting the queue). Consumer-only applications must also register the queue class. Registration creates a client but does not enqueue jobs. A missing queue provider fails startup before any worker starts. Consumers use their queue instance's PostgreSQL connection and telemetry; worker options cannot select another database or schema. `BaseProcessor` replaces the removed `WorkerHost` export.

### Scope and request context

Each invocation runs in a fresh `RequestContext` with type `"queue"` and the current `JOB_REF`. The context and its middleware are established **before** Nest resolves the consumer's dependencies. `process()` failures propagate to BullMQ for retries.

Consumers support singleton, request and transient scopes. Request-scoped dependencies propagate their scope to consumers. Request/transient consumers are resolved for each task in their declaring module using `ContextIdFactory.getByRequest()` and `ModuleRef.resolve()`, including application-defined durable context strategies.

Import `RequestContextModule` to inject the current context. Its `RequestContext` provider is request-scoped and returns the active context, so injecting it also makes the consumer request-scoped:

```ts
import {
  BaseProcessor,
  JOB_REF,
  Processor,
  QueueModule,
} from "@nest-boot/queue";
import {
  RequestContext,
  RequestContextModule,
} from "@nest-boot/request-context";
import { Inject, Module } from "@nestjs/common";
import { Job } from "bullmq";
import { EmailQueue, type EmailData } from "./email.queue";

@Processor(EmailQueue)
export class EmailProcessor extends BaseProcessor {
  constructor(
    private readonly context: RequestContext,
    @Inject(JOB_REF) private readonly job: Job<EmailData>,
  ) {
    super();
  }

  async process() {
    return { contextId: this.context.id, recipient: this.job.data.to };
  }
}

@Module({
  imports: [QueueModule, RequestContextModule],
  providers: [EmailQueue, EmailProcessor],
})
export class EmailWorkerModule {}
```

Singleton services can keep using `RequestContext.current()` or `RequestContext.get(JOB_REF)` inside methods. Do not capture a task context in a singleton constructor. Use durable dependencies only for intentionally shared state, not current-job data. The `worker` getter is available after module initialization and inside scoped consumers' `process()` methods.

## Dynamic queue configuration

Use a normal Nest factory provider when queue settings depend on injected services or asynchronous configuration. `QueueFactory.create()` retains the declared name and merges runtime options over the decorator options. The resulting instance has the same lifecycle as a class provider.

```ts
import { QueueFactory, QueueModule } from "@nest-boot/queue";
import { Module } from "@nestjs/common";
import { EmailQueue } from "./email.queue";
import { SettingsService } from "./settings.service";

@Module({
  imports: [QueueModule],
  providers: [
    SettingsService,
    {
      provide: EmailQueue,
      inject: [QueueFactory, SettingsService],
      useFactory: async (factory: QueueFactory, settings: SettingsService) =>
        factory.create(EmailQueue, await settings.getEmailQueueOptions()),
    },
  ],
  exports: [EmailQueue],
})
export class EmailModule {}
```

## Queue events

`@OnWorkerEvent()` observes the local worker. Use a separate singleton `QueueEventsHost` for explicit PostgreSQL queue event listeners:

```ts
import {
  OnQueueEvent,
  QueueEventsHost,
  QueueEventsListener,
} from "@nest-boot/queue";
import { RequestContext } from "@nest-boot/request-context";
import { EmailQueue } from "./email.queue";

@QueueEventsListener(EmailQueue)
export class EmailEvents extends QueueEventsHost {
  @OnQueueEvent("completed")
  completed(event: { jobId: string }) {
    console.log(event.jobId, RequestContext.id);
  }
}
```

Register `EmailEvents` and its queue as providers. Worker event handlers are bound only on singleton consumers; scoped consumer handlers are skipped. Queue event listener providers must be singletons. Job queries read the native table and need no event listeners.

Each decorated event callback has an independent request context and runs context middleware. Job-bearing worker events bind `JOB_REF`; `stalled` uses the job ID only. QueueEvents payloads supply a `jobId`, not a Job, so their contexts do not bind `JOB_REF`. Other events receive a generated context ID. Handler or middleware failures are logged and suppressed because BullMQ does not await listeners. Direct `.on()` callbacks need their own context and asynchronous error handling.

## PostgreSQL storage and migrations

All queues use BullMQ 6's official PostgreSQL backend. `QUEUE_DATABASE_URL` takes precedence over `DATABASE_URL`; without either, node-postgres connection defaults apply. Explicit `connection` options support a PostgreSQL config, URL or caller-owned pool. Use a config object with `schema` for a namespace other than `bullmq`. Redis prefixes and Redis connections are no longer queue options.

Run BullMQ's migrations before starting producers, workers or queries. They own the tables, functions, indexes and migration ledger:

```ts
import { runMigrations } from "bullmq";
import { Client } from "pg";

const client = new Client({ connectionString: process.env.DATABASE_URL });
await client.connect();
try {
  await runMigrations(client); // Pass a custom schema as the second argument.
} finally {
  await client.end();
}
```

The migrator needs one dedicated client, not `pool.query()` across different sessions. Explicit `connection: { connectionString, migrate: true }` is also supported by BullMQ; Nest Boot does not enable automatic migrations by default. Enqueueing and business writes do not share a transaction merely because they use the same database.

Caller-owned `pg.Pool` instances must set the correct `search_path` (for example, `options: "-c search_path=bullmq,public"`) before being passed to BullMQ. The caller also closes the pool after queues and workers stop. Use a config object rather than a raw pool when selecting a custom `schema`.

## Optional MikroORM and GraphQL queries

Persistence is inherent to the PostgreSQL backend. `queue.add()` and `addBulk()` write native jobs immediately. There is no event mirror, per-queue persistence switch, synchronization listener or separate cleanup timer. Keep completed/failed rows using BullMQ's `removeOnComplete` / `removeOnFail` policies (`age` is in seconds). Removing a job also removes it from ORM and GraphQL queries. A duplicate retained job ID keeps the original job; remove the original before intentionally reusing its ID.

| Application configuration                 | Behavior                                                  |
| ----------------------------------------- | --------------------------------------------------------- |
| QueueModule only                          | PostgreSQL queues and workers; no ORM or GraphQL required |
| DatabaseModule plus built-in Job metadata | Also provide read-only JobService queries                 |
| Database integration plus GraphQLModule   | Also expose job(id) and jobs, unless graphql is false     |

`@nest-boot/database`, `@nest-boot/graphql` and `@nest-boot/graphql-connection` remain optional peers. Install their required dependencies only when using the integration. Installed packages alone do not activate features. Database-only applications can use JobService without installing GraphQL; connection queries require the GraphQL peers.

```ts
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { DatabaseModule } from "@nest-boot/database";
import { GraphQLModule } from "@nest-boot/graphql";
import { QueueModule } from "@nest-boot/queue";
import {
  entities,
  jobSchemaGeneratorOptions,
} from "@nest-boot/queue/persistence";
import { Module } from "@nestjs/common";

@Module({
  imports: [
    DatabaseModule.forRoot({
      driver: PostgreSqlDriver,
      entities,
      schemaGenerator: jobSchemaGeneratorOptions,
    }),
    GraphQLModule,
    QueueModule.forRoot({
      graphql: true,
      // Return a MikroORM filter from verified request identity, or null to deny.
      getJobReadFilter: () => null,
    }),
  ],
})
export class JobsModule {}
```

Use the same entity discovery and `schemaGenerator` exclusions in the application and MikroORM CLI configuration. The Job entity is a read-only wildcard-schema mapping, excluded from normal ORM migration generation. `jobSchemaGeneratorOptions` also excludes the native `bullmq` schema from introspection and its table from schema targets. `readonly` alone only disables flush tracking; it does not prevent explicit native writes. Mutate jobs through BullMQ.

For a custom schema such as `tasks`, set `QueueModule.connection` to `{ connectionString, schema: "tasks" }`, run `runMigrations(client, "tasks")`, and add `tasks` to `schemaGenerator.ignoreSchema` and `tasks.job` to `skipTables`. Direct ORM calls must pass `{ schema: "bullmq" }` (or the custom schema). JobService supplies this from the root queue configuration, defaulting to `bullmq`. The ORM connection must access the same database as that root configuration. Per-queue overrides targeting other databases/schemas are not aggregated by the root JobService.

| Entity field                       | Native mapping                                                      |
| ---------------------------------- | ------------------------------------------------------------------- |
| queue                              | queue column                                                        |
| jobId                              | id column                                                           |
| id                                 | SQL formula combining queue and jobId as queue:jobId                |
| status                             | Native state, with waiting priority jobs represented as prioritized |
| createdAt / startedAt / finishedAt | Millisecond timestamps converted to Date                            |

The native primary key remains `(queue, id)`. The computed API ID provides a unique cursor tie-breaker across queues. The native table has no last-update timestamp, so there is no `updatedAt` field or filter. GraphQL exposes `queue`, `jobId` and the computed `id`; filters and sorting support `queue`, `name`, `status` and `created_at`.

`getJobReadFilter` runs for every read and scopes nodes, filters, pagination and counts. Missing callbacks, null and undefined deny access; returning an empty object explicitly grants all jobs. Payload ownership must come from trusted application identity. The default BullMQ schema has no application tenant RLS policy. Applications using database request roles must grant those roles schema usage and SELECT on the native job table; the example's `queue:migrate` command does this for `authenticated`. The example enforces user/workspace visibility in JobService rather than generating policies on BullMQ-owned tables.

Entities and JobService are exported from `@nest-boot/queue/persistence`; GraphQL types and resolvers from `@nest-boot/queue/graphql`. These entry points keep optional dependencies out of plain queue imports.

### Migrating existing queues

This API remains in v8. Remove `@nest-boot/queue-database`, `QueueDatabaseModule`, the old mirror entity/resolver, persistence/TTL options and Redis prefixes. Register queue classes as providers, switch to a PostgreSQL connection, run official migrations and configure optional ORM exclusions and read authorization. Existing Redis jobs and legacy mirror rows are not moved automatically; drain or migrate them separately before changing a deployment. Review old application table cleanup separately to preserve any history you need.

## Best Practices

1. **Separate Queues** — Use dedicated queues for different job types (email, file-ops, etc.) with appropriate concurrency settings.

2. **Job IDs** — Use deterministic or Sonyflake-based job IDs for idempotency and traceability.

3. **Structured Logging** — Use `Logger.assign()` in processors to attach job context to log entries.

4. **Cleanup** — Set `removeOnComplete` and `removeOnFail` to auto-clean old jobs.

---
title: "Request Context"
description: "Share lifecycle-scoped state and application providers across asynchronous NestJS execution."
---

`@nest-boot/request-context` keeps data available throughout one asynchronous
execution lifecycle without passing it through every method call. A context has
an ID, a lifecycle type, its own values, and optionally a parent context.

For HTTP requests, `RequestContextModule` creates and propagates the context
automatically. Jobs, events, scripts, and other entry points can create one
explicitly.

## Installation

```bash
pnpm add @nest-boot/request-context
```

## HTTP Setup

Import `RequestContextModule` once in the root module. The module is global and
automatically covers HTTP requests.

```typescript
import { RequestContextModule } from "@nest-boot/request-context";
import { Module } from "@nestjs/common";

@Module({
  imports: [RequestContextModule],
})
export class AppModule {}
```

## Storing and Reading Values

Use a class, symbol, or string as the token. Classes and exported symbols are
preferred because they avoid collisions.

```typescript
import { RequestContext } from "@nest-boot/request-context";

export const CURRENT_TENANT = Symbol("CURRENT_TENANT");

RequestContext.set(User, authenticatedUser);
RequestContext.set(CURRENT_TENANT, tenant);

const user = RequestContext.get(User);
const currentTenant = RequestContext.get<Tenant>(CURRENT_TENANT);
```

`get()` returns `undefined` when the token cannot be resolved. `getOrSet()` can
initialize a value on first access:

```typescript
const metadata = RequestContext.getOrSet(
  "request-metadata",
  new Map<string, unknown>(),
);
```

Lookups use the following order:

1. A value stored in the current context.
2. A value inherited from a parent context.
3. An application provider available through the HTTP context.

An explicitly stored value takes precedence even when it is `null` or
`undefined`. This allows a child or request context to mask an inherited or
application-level value.

The static accessors require an active context. Use `isActive()` before reading
context data from code that may run outside a managed lifecycle.

```typescript
if (RequestContext.isActive()) {
  const user = RequestContext.get(User);
}
```

## Accessing Application Providers

HTTP contexts can lazily resolve singleton providers from the Nest application
container. This is useful for callbacks that execute during a request but are
created outside Nest dependency injection.

```typescript
const mailer = RequestContext.get(Mailer);

await mailer?.sendMail({
  subject: "Verify your email",
  text: verificationUrl,
  to: user.email,
});
```

Request-scoped and transient providers cannot be resolved by this synchronous
lookup and return `undefined`. Unexpected provider resolution errors are not
suppressed.

## Request and Response

The built-in HTTP context stores the Express request and response under the
`REQUEST` and `RESPONSE` tokens.

```typescript
import { REQUEST, RESPONSE, RequestContext } from "@nest-boot/request-context";
import type { Request, Response } from "express";

const request = RequestContext.get<Request>(REQUEST);
const response = RequestContext.get<Response>(RESPONSE);
```

## Context Metadata

Use `current()` to inspect the active context:

```typescript
const context = RequestContext.current();

console.log(context.id);
console.log(context.type);
console.log(context.parent);
```

`RequestContext.id` is a shortcut for the active context ID. The `type` is an
application lifecycle category, not `ExecutionContext.getType()`:

| Context source                 | Type example |
| ------------------------------ | ------------ |
| HTTP middleware or interceptor | `http`       |
| BullMQ processor               | `queue`      |
| REPL                           | `repl`       |
| Application-created context    | `job`        |

## Child Contexts

`child()` creates an isolated context inside the active one. The child keeps the
same ID and type, reads values and application providers through its parent, and
stores its own overrides without changing the parent.

```typescript
RequestContext.set("tenant-id", "tenant-a");

await RequestContext.child(async (childContext) => {
  childContext.get<string>("tenant-id"); // tenant-a

  childContext.set("tenant-id", "tenant-b");
  childContext.set("attempt", 1);

  await processAttempt();
});

RequestContext.get<string>("tenant-id"); // tenant-a
RequestContext.get<number>("attempt"); // undefined
```

Within the callback, static calls such as `RequestContext.get()` and
`RequestContext.set()` operate on the child. `child()` requires an active parent
context and does not run registered context middleware again.

Use a child context for temporary overrides, transaction branches, retries, or
other nested work that must not mutate the surrounding context.

## Contexts Outside HTTP

### Running a Context Explicitly

Create a `RequestContext` and pass it to `run()` for jobs, events, scripts, or
tests. Registered context middleware runs before the callback.

```typescript
await RequestContext.run(
  new RequestContext({ id: job.id, type: "job" }),
  async (context) => {
    context.set("job", job);
    await processJob();
  },
);
```

### Using the Decorator

`CreateRequestContext` wraps a method in a context created from its instance and
arguments.

```typescript
import {
  CreateRequestContext,
  RequestContext,
} from "@nest-boot/request-context";
import { Injectable } from "@nestjs/common";

@Injectable()
export class EventHandler {
  @CreateRequestContext(
    (_handler, event: DomainEvent) =>
      new RequestContext({ id: event.id, type: "event" }),
  )
  async handle(event: DomainEvent): Promise<void> {
    RequestContext.set("event", event);
    await dispatchEvent(event);
  }
}
```

## Context Middleware

Context middleware initializes values or wraps every lifecycle created through
`run()`, including the HTTP lifecycle. Register middleware once during
application bootstrap.

The optional third `dependencies` argument to `registerMiddleware()` lists
middleware names that must run first:

```typescript
RequestContext.registerMiddleware("authentication", async (context, next) => {
  context.set(User, await authenticate());
  return next();
});

RequestContext.registerMiddleware(
  "authorization",
  async (context, next) => {
    const user = context.get(User);
    context.set(Ability, await createAbility(user));
    return next();
  },
  ["authentication"],
);
```

In this example, `authentication` always runs before `authorization`, regardless
of registration order. Multiple dependencies run before the middleware that
declares them, and circular dependencies throw an error. Child contexts inherit
initialized values and therefore do not execute the middleware stack again.

## Recommendations

- Import `RequestContextModule` only once.
- Prefer class or exported symbol tokens over ad hoc strings.
- Populate request values early in middleware, guards, or authentication hooks.
- Use `child()` for isolated nested work and `run()` for new entry points.
- Treat `get()` as optional unless the lifecycle guarantees the token exists.

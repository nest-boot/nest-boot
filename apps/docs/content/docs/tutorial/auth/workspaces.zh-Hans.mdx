## 选择工作区

客户端通过 `x-workspace-id` 请求头或 `workspace_id` Cookie 选择工作区。
`AuthMiddleware` 会校验该选择，解析已认证用户的活动成员身份，并把两个实体保存到
`RequestContext`。

```typescript
import {
  CurrentWorkspace,
  CurrentMember,
} from "@nest-boot/auth";

currentWorkspace(
  @CurrentWorkspace() workspace: Workspace,
  @CurrentMember() member: Member,
) {
  return { workspace, member };
}
```

路由或请求头始终是工作区选择的来源。Session 不需要 `activeWorkspaceId`，因此不同的
浏览器标签页可以同时使用不同工作区。

## 工作区生命周期

`WorkspaceService` 提供与传输协议无关的工作区操作：

- `findOne(where)`；
- `getWorkspaceConnectionByUser(user, args)`；
- `createWorkspace(user, input)`；
- `updateWorkspace(id, input)`；
- `deleteWorkspace(id)`。

创建工作区会同时创建已激活的所有者成员。删除采用软删除，需要具备所选工作区的
删除能力。

删除工作区、添加成员、创建或接受邀请时，会在事务内锁定工作区记录并重新
检查其有效状态。即使请求在删除前已选中该工作区，也不能在删除提交后继续创建下级记录。

## 成员生命周期

以下方法由 `MemberService` 提供：

- `getMemberByUser(workspace, user)`；
- `getMember(id)` — 从请求上下文获取当前工作区，并检查读取能力；
- `getMemberConnectionByWorkspace(workspace, args)`；
- `addMember(workspace, user, input)`；
- `addMemberByEmail(workspace, email, input)`；
- `updateMember(id, input)`；
- `setMemberRoles(id, roles)`；
- `setMemberPermissions(id, permissions)`；
- `removeMember(id)`；
- `leaveWorkspace(member)`。

禁用和移除成员按更新、删除能力授权，不再针对所有者角色做特殊限制。当前成员可主动
退出，包括所有者；工作区允许没有所有者。管理删除接口仍禁止删除本人，应使用退出接口。
成员状态与角色更新会锁定相关
成员记录，并在同一事务内重新检查状态。GraphQL Resolver 与 HTTP Controller 应只
负责输入输出映射，把这些约束留在对应的 Service 中。
同一工作区可以有多名成员持有配置的创建者角色。通过 `setMemberRoles` 授予或移除该角色，
仍需满足更新能力和操作者的授权范围。不再提供专门的所有权转移操作；两次角色更新是
独立操作，不保证原子转移。

邀请投递和状态流转单独记录在[邀请](/docs/tutorial/auth/invitations)章节中。

## 写入授权与 RLS

普通工作区与成员写入同时保留 Service 权限、当前工作区、所有者约束以及数据库 RLS。
Service 可从请求上下文读取当前身份；Resolver 只传 ID 和输入。
以上方法仍兼容实体参数，但 GraphQL 的 `updateWorkspace`、`deleteWorkspace`
现在必须显式传 `id: ID!`，且与选中的工作区一致。
废弃别名 `removeWorkspace` 已移除，请使用 `deleteWorkspace`。

GraphQL 工作区更新、成员创建/更新/角色/权限设置返回仅含 `id` 的专用 Payload。
需要资料时另行查询，写权限不代表可以读取关联字段。
`leaveWorkspace` 提交后会清理当前请求的成员、工作区能力和工作区 RLS 上下文，
因此不能在外部已开启的事务中调用。

部署前执行示例迁移 `Initial → generated schema migrations`。
auth 基础设施层为软删除事务建立局部 ORM fork，设置 `app.operation = auth.workspace.delete`，
保留原有用户与工作区 RLS 上下文；配套策略仅在该操作内允许读取当前工作区的删除结果。
普通请求仍看不到已删除工作区，也不能恢复它。自定义应用需要对应的策略。
用户删除则由 Service 和 RLS 授权根记录，再由数据库外键级联原子清理
关联数据。删除用户后，工作区与其他用户的成员关系继续保留，允许工作区没有所有者。

所有 Service 都只使用注入的 `this.em`。创建工作区、接受或拒绝邀请所需的跨身份
数据库上下文由 `AuthModule` 基础设施统一建立，业务权限与生命周期检查仍由 Service 执行。
普通查询和写入不会关闭 RLS。

工作区、成员和邀请查询统一使用上述连接分页方法。各 Service 分别校验权限，
并保留请求级 RLS。

## 用户成员与工作区可见资料

`Member` 内置姓名和邮箱，`Workspace.members` 和 `User.members` 内置反向集合。
应用无需重复声明这些字段或关联。
原始 ORM 集合不直接暴露为 GraphQL 字段，分页仍由带权限检查的连接字段解决器提供。
示例的 `Workspace.features` 字段及枚举已移除。

成员必须关联用户，同时独立保存 `name` 和可空的 `email`，作为工作区内可见的
姓名与联系邮箱。创建成员时从用户资料初始化，之后不自动同步：修改成员不会修改
User 的姓名或登录邮箱，修改 User 也不会改变成员资料。具有成员更新权限的主体
可以修改姓名、邮箱和状态；角色、权限继续使用专用设置接口。传入 `email: null`
仅清空成员联系邮箱，不影响登录。示例页面与过滤器直接读取成员字段，支持精确过滤
和 `name:Alice*` 形式的前缀搜索，不通过关联 User 搜索私人资料。

`Member.user` 是私有 User 关联，不是工作区共享联系方式的来源。
只有本人或通过 Service 全局用户读取权限检查的主体可读；
工作区角色不会授予此权限。`Invitation.inviter` 同样遵循此边界，
持有邀请并不意味着可以读取邀请人的个人资料。

服务账号创建方法、Options、Input 导出及成员类型枚举仍然移除，不保留别名。
示例现仅保留新库基线 `Initial → generated schema migrations`，直接创建必填用户关联和
独立的成员姓名、邮箱，不再包含历史成员类型或搜索向量列。

生成基线中的 User SELECT 策略允许 authenticated 数据库角色读取 User 行，匿名仍不可读。
个人资料可见性由 Service 的 Ability 检查限制，支持自定义权限名并保留 API Key 权限上限。
直接 ORM/SQL 查询不再限制个人资料可见性，因此对外读取必须经过 Service 授权。
User 写入及 Session RLS 策略仍检查可信请求上下文 `app.user.permissions` 中的内置权限名。

新基线替代旧迁移历史，仅用于空数据库。已有数据库不能直接重复执行该基线，
也不能只清空迁移记录表；应先备份数据并制定单独的数据保留与基线衔接方案。
自定义实体、过滤器、GraphQL 文档和生成类型需同步更新。

## Selecting a Workspace

Clients select a workspace with the `x-workspace-id` header or `workspace_id`
Cookie. `AuthMiddleware` verifies that selection, resolves the authenticated
user's active membership, and stores both entities in `RequestContext`.

```typescript
import {
  CurrentWorkspace,
  CurrentMember,
} from "@nest-boot/auth";

currentWorkspace(
  @CurrentWorkspace() workspace: Workspace,
  @CurrentMember() member: Member,
) {
  return { workspace, member };
}
```

The route or header remains the source of workspace selection. A session does
not need an `activeWorkspaceId`, which lets separate browser tabs work in
different workspaces.

## Workspace Lifecycle

`WorkspaceService` owns transport-independent workspace operations:

- `findOne(where)`;
- `getWorkspaceConnectionByUser(user, args)`;
- `createWorkspace(user, input)`;
- `updateWorkspace(id, input)`;
- `deleteWorkspace(id)`.

Creating a workspace also creates its active owner membership. Deletion is a
soft delete and requires delete ability for the selected workspace.
Deletion, member creation, and invitation creation/acceptance
lock the workspace row and recheck its active state inside their transaction.
Requests that selected a workspace before deletion cannot create new children
after the deletion commits.

## Member Lifecycle

`MemberService` owns these operations:

- `getMemberByUser(workspace, user)`;
- `getMember(id)` — requires the current workspace and checks read ability;
- `getMemberConnectionByWorkspace(workspace, args)`;
- `addMember(workspace, user, input)`;
- `addMemberByEmail(workspace, email, input)`;
- `updateMember(id, input)`;
- `setMemberRoles(id, roles)`;
- `setMemberPermissions(id, permissions)`;
- `removeMember(id)`;
- `leaveWorkspace(member)`.

Member disable/remove operations check update/delete ability regardless of role.
Any current member may leave, including an owner; the workspace may remain without owners.
Administrative removal still rejects self-removal; use `leaveWorkspace` instead.
Member status and role changes lock the affected memberships
and recheck their state in the same transaction.
GraphQL resolvers and HTTP controllers should map input/output types and leave
these invariants in the corresponding Service.
Multiple members may hold the configured creator role. Use `setMemberRoles` to
assign or remove that role, subject to update ability and the caller's permission
scope. There is no dedicated ownership-transfer operation; these are separate
role updates, not an atomic transfer.

Workspace invitation delivery and state transitions are documented separately
under [Invitations](/docs/tutorial/auth/invitations).

## Write Authorization and RLS

Ordinary workspace/member writes retain both Service authorization (including
selected-workspace and owner invariants) and database RLS. Services may read the
actor from request context; resolvers only pass IDs and inputs. The methods
above still accept entity arguments, but GraphQL `updateWorkspace` and
`deleteWorkspace` now require an explicit
`id: ID!` matching the selected workspace.
The deprecated `removeWorkspace` alias has been removed; use `deleteWorkspace`.

Apply `Initial → generated schema migrations` before deployment.
Auth infrastructure establishes a local ORM fork for soft deletion with
`app.operation = auth.workspace.delete`, preserving the actor/workspace RLS
context. Its matching policy allows the deletion result only inside that
operation. Normal requests still cannot read deleted workspaces or restore them.
Custom applications need equivalent policies. User deletion authorizes the root
row with Service checks and RLS, then uses foreign-key cascades for atomic
dependent cleanup. Deleting a user preserves workspaces and other
users' memberships; a workspace is allowed to remain without an owner.

Services use only injected `this.em`. `AuthModule` infrastructure establishes
cross-identity database contexts for workspace creation and invitation
acceptance/rejection; Services still enforce authorization and lifecycle checks.
Ordinary queries and writes do not disable RLS.

Use the connection pagination methods above for workspaces, members, and
invitations. Each service checks its own authorization and retains request RLS.

## Workspace-visible member profiles

Built-in `Member` owns name/email, and `Workspace.members` / `User.members` own the inverse collections. Applications do not redeclare these fields. Raw ORM collections stay hidden from GraphQL; connection
field resolvers remain responsible for authorized pagination. The example's
`Workspace.features` field and enum have been removed.

Every member requires a user and retains its own `name` and nullable `email`.
These are workspace-visible contact details, initialized from the user's profile
when membership is created. They are independent thereafter: member edits do not
change the user's name or login email, and user edits do not synchronize to members.
Authorized callers may update member name, email and status; roles and permissions
use dedicated setters. Clearing the member email with `null` does not affect login.
The example displays and filters member fields directly, with exact filters and
prefix searches such as `name:Alice*`, without joining private user profiles.

`Member.user` remains a private User relation, not a source of shared
contact details. Reading another user's profile requires global user-read
authorization and User SELECT RLS access; workspace roles alone do not grant it.
The same boundary applies to `Invitation.inviter`: access to an invitation
does not grant access to the inviter's private profile.

Service-account creation and its options/input exports remain removed without
aliases; there is no member type enum. The example now has a two-step fresh-database
baseline, `Initial → generated schema migrations`, which creates required member user
relations and independent name/email fields directly, without historical columns.

The baseline restricts User SELECT to self or global user-management access using
the trusted request-local `app.user.permissions` JSON array. Auth merges role and
direct grants and applies the API-key permission ceiling before staging it.
Policies no longer query User to resolve permissions, so no recursive policy or
custom SQL function is needed. Services independently protect relations, including
when an application omits RLS.

This baseline replaces the previous migration history and is intended for empty
databases. Do not apply it on top of an existing schema or merely clear the migration
history table. Back up existing data and plan a separate data-preserving transition
before upgrading an existing database. Update custom entities, filters and GraphQL
documents together.

The underlying Better Auth instance and injection token are internal. Inject the
service that owns the required domain:

| Service             | Responsibility                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------- |
| `AuthService`       | Authentication, email verification, password recovery, profiles, and provider accounts      |
| `SessionService`    | Session resolution, parent-user connections, impersonator lookup, and self/admin revocation |
| `UserService`       | User administration, permissions, bans, impersonation, and passwords                        |
| `AccountService`    | Safe account connections for the owning user session                                        |
| `WorkspaceService`  | Workspace queries and lifecycle operations                                                  |
| `MemberService`     | Member queries, connections, profiles, roles, permissions, adding/removing, and leaving     |
| `InvitationService` | Invitation queries, connections, creation, acceptance, rejection, and cancellation          |
| `ApiKeyService`     | Personal and workspace API-key lifecycle and validation                                     |

`UserService`, `AccountService`, `WorkspaceService`, `MemberService` and `InvitationService` operate directly on the MikroORM entities
provided by `AuthModule`; they do not require Better Auth's admin or
organization plugins.

```typescript
@Injectable()
export class AccountApplicationService {
  constructor(
    private readonly authService: AuthService,
    private readonly sessionService: SessionService,
    private readonly userService: UserService,
    private readonly accountService: AccountService,
    private readonly workspaceService: WorkspaceService,
    private readonly memberService: MemberService,
    private readonly invitationService: InvitationService,
    private readonly apiKeyService: ApiKeyService,
  ) {}
}
```

## Built-in entities and GraphQL

`AuthModule` registers domain services and all standard resolvers. Remove
`AuthGraphQLModule` and import entities, inputs, payloads and connections from
`@nest-boot/auth`. Configure your GraphQL module and `AuthModule.forRoot()`;
no application auth entities or named connection registration are required.
Resolvers use concrete class callbacks.

Auth owns the concrete `User`, `Account`, `Session`, `Verification`,
`Workspace`, `Member`, `Invitation`, and `ApiKey` entities, their GraphQL
metadata, relations, RLS policies, and connections. There are no public auth
`Base*` classes or `AuthModuleOptions.entities` overrides.

Register the exported `entities` array in both your runtime MikroORM configuration
and the configuration loaded by the migration CLI. The CLI does not initialize Nest:

```typescript
import { entities as authEntities } from "@nest-boot/auth";
import { defineConfig } from "@mikro-orm/postgresql";

export default defineConfig({
  entities: [...authEntities, "dist/**/*.entity.js"],
  entitiesTs: [...authEntities, "src/**/*.entity.ts"],
  // Connection and migration options...
});
```

Use separate related business entities and additional field resolvers to extend
these models. Import the built-in classes directly for relation targets; do not
redeclare or register replacement auth entities. Role/permission catalogs, ability
builders, delivery callbacks, and provider settings remain configurable.

## Transport Adapters

Resolvers and controllers translate protocol parameters and delegate domain rules
to services. Service authorization and database RLS remain in effect.
Authentication methods forward every Set-Cookie value through the request-scoped
cookies store. `AuthMiddleware` runs after `RequestContextMiddleware` and stores
identity under built-in entity classes, for example `RequestContext.get(User)`.
No auth base-token aliases are registered; prefer the current identity decorators.

`Member` / `Invitation` use `MemberService` / `InvitationService` and the
`member:*` / `invitation:*` permission subjects. Existing GraphQL field names,
arguments and authorization behavior are unchanged by the package merge.

## PostgreSQL RLS

MikroORM 7.2 native RLS uses the request EntityManager session context. Auth updates
that context after resolving the identity; service-authorized persistence uses
isolated, unscoped forks where necessary. The example configures `session` through
`createSessionContext`, so no custom RLS driver or interceptor is needed. See the
[MikroORM tutorial](/docs/tutorial/mikro-orm).

## Bootstrap

```typescript
import { Logger } from "@nest-boot/logger";
import { ZodValidationPipe } from "@nest-boot/validator";
import { NestFactory } from "@nestjs/core";

async function bootstrap() {
  const app = await NestFactory.create(AppModule, {
    bufferLogs: true,
    cors: true,
  });

  app.useLogger(await app.resolve(Logger));
  app.useGlobalPipes(new ZodValidationPipe());
  app.enableShutdownHooks();

  await app.listen(process.env.PORT ?? 4000);
}

void bootstrap();
```

## Operational Guidance

Auth inputs now use Zod instead of class-validator. Remove the old global
`ValidationPipe` after migrating your application's DTOs. Zod returns plain parsed
objects and strips undeclared properties; it does not construct DTO instances.
GraphQL validation errors use `BAD_USER_INPUT` with field details in
`extensions.validationErrors`.

`banUser` and `deleteCurrentUser` still allow omitting `input` (default `{}`).
Explicit `input: null` is rejected. For a property, `.optional()` accepts omission
and `.nullish()` also accepts `null`; see the [Validator tutorial](/docs/tutorial/validator).
Direct Service calls do not run the pipe automatically.

- Register `AuthGuard` once as `APP_GUARD` and mark exceptions with `@Public()`.
- Use current-identity decorators in transport code instead of raw context tokens.
- Store high-entropy `AUTH_SECRET` and `HASH_SECRET` values outside source control.
- Keep workspace selection explicit in the route, header, or Cookie.
- `AuthModule` provides the standard GraphQL schema; applications can add their own field resolvers.

For symbol-level documentation, see the [Auth API Reference](/docs/api/auth)

## Additional GraphQL-native APIs

`AuthModule` provides `Account`, `AccountConnection`, `UserConnection`, `SessionConnection` and their argument classes; all references use concrete classes. `users(first: 20)` returns a connection. `currentUser { sessions(first: 20) { edges { node { id } } } accounts(first: 20) { edges { node { id providerId } } } }` replaces the old session/account root lists. Self session reads are allowed; other users require administrative permission.

Authentication payloads now reference `User` instead of `AuthUserType`, loading the built-in entity and adopting newly issued sessions before nested resolution. Registration without a session does not grant authentication.

Apply the example's `Initial → generated schema migrations` before deployment. It enables account/session RLS and uniform default privileges. Services and GraphQL exclude credential fields; database column-level restrictions are removed. Session administrative reads use the server-computed request permission array.

### Operation naming changes

Use `currentSession`,
`createWorkspaceApiKey`, `updateWorkspaceApiKey` and `deleteWorkspaceApiKey`.
Their old names are removed without aliases. Workspace deletion is only
`deleteWorkspace`; `removeWorkspace` is no longer exposed. Update GraphQL documents,
response-field access and generated types together.

The default GraphQL module no longer exposes `authFetchAccessToken`,
`authFetchAccountInfo` or `authRefreshToken`, nor their dedicated input/result
types. There are no aliases. Use `currentUser { accounts(first: 20) { edges { node { id providerId scopes } } } }`
for account bindings. Server-side provider integrations can still call
`AuthService.getAccessToken()`, `refreshToken()` and `getAccountInfo()`.

---
title: "Invitations"
description: "Create, deliver, accept, reject, and cancel workspace invitations."
---

Workspace invitations are independent lifecycle entities. They use `pending`,
`accepted`, `rejected`, and `canceled` states; accepting one creates a separate
active member while retaining the invitation record.

## Invitation Email

Configure `workspace.sendInvitationEmail` to deliver an application-owned
acceptance link. Nest Boot persists the invitation before calling the sender and
supplies its normalized email, ID, role, workspace, record, and the inviting
member with its authenticated user.

```typescript
import { Mailer } from "@nest-boot/mailer";
import { RequestContext } from "@nest-boot/request-context";

AuthModule.forRoot({
  // ...
  workspace: {
    async sendInvitationEmail({ email, id, inviter, workspace }) {
      const url = new URL(
        "/invite",
        process.env.APP_URL ?? "http://localhost:3000",
      );
      url.searchParams.set("invitationId", id);

      const mailer = RequestContext.get(Mailer);
      if (!mailer) throw new Error("Mailer is unavailable");

      await mailer.sendMail({
        to: email,
        subject: `Invitation to join ${workspace.name}`,
        text: `${inviter.name} invited you: ${url}`,
      });
    },
  },
});
```

The application owns the URL because acceptance may be exposed through
GraphQL, REST, or another transport. The sender receives an optional Fetch
`Request` when the `createInvitation()` caller supplies one.

## InvitationService API

GraphQL `createInvitation`, `rejectInvitation` and `cancelInvitation` return
dedicated ID-only payloads. Read invitation details separately; these writes do
not grant access to the inviter's private user profile. Creating invitations
requires a user identity: use a user API key, not a workspace API key.

- `createInvitation(workspace, inviter, input, request?)`;
- `getInvitation(id)` — single-record lookup using the current request's native RLS;
- `getInvitationByUser(id, user)`;
- `getInvitationByWorkspace(id, workspace)`;
- `getInvitationConnectionByWorkspace(workspace, args)` — authorized workspace invitation connection;
- `getInvitationConnectionByUser(user, args)` — current recipient's pending invitation connection;
- `acceptInvitation(user, invitationId)`;
- `rejectInvitation(user, invitation)`;
- `cancelInvitation(invitation)`.

`invitation(id)` calls `getInvitation(id)` without passing a user.
This method checks read permission and queries the request's ORM manager without
bypassing RLS or disabling filters. Configure both workspace-scoped and recipient
SELECT policies: a recipient must be able to read their invitation before joining
the workspace. The example's incremental recipient-policy migration grants only
SELECT; writes and other service-authorized invitation operations retain their
existing checks. Apply this migration when upgrading an existing example database.

Invitations expire after 48 hours unless `input.expiresIn` supplies another
positive integer lifetime in seconds. Creation rejects existing members and
duplicate pending invitations. Acceptance and rejection require the invitation
email to match the authenticated user. Only pending, unexpired invitations can
be accepted.

Directly adding an existing user with `MemberService.addMember()` or `MemberService.addMemberByEmail()`
cancels pending invitations for the same workspace and email in the membership
transaction. The invitation remains as a `canceled` audit record and disappears
from the user's pending list. Concurrent direct addition and acceptance can
create only one membership.

`InvitationService` enforces the relevant workspace or current-user permission
for every operation. Workspace administrators create and cancel invitations,
while the addressed user gets, accepts, or rejects an invitation.

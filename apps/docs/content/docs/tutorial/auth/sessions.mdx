---
title: "Sessions"
description: "Resolve, list, and revoke authenticated sessions."
---

Browser authentication uses HttpOnly Cookie sessions. Same-origin GraphQL and
auth requests must enable credentials so the browser stores and returns those
cookies. API keys use a separate Bearer flow described in
[API Keys](/docs/tutorial/auth/api-keys).

## Current Identity

`AuthMiddleware` resolves the authenticated application `User` and `Session`
entities into `RequestContext`. Transport code should use decorators instead of
reading context tokens directly.

```typescript
import { CurrentSession, CurrentUser } from "@nest-boot/auth";

profile(
  @CurrentUser() user: User,
  @CurrentSession() session: Session,
) {
  return { user, session };
}
```

Both decorators return `null` when the corresponding identity is unavailable,
allowing public handlers to declare nullable parameters explicitly.

## SessionService

`AuthModule` provides the built-in `Session` entity and GraphQL type.
`currentSession` returns `Session`; `User.sessions` returns `SessionConnection`.
The former `AuthSessionType`, `userSessions(userId)` and `authSessions` APIs are removed.
Use `currentUser { sessions(first: 20) { edges { node { id current expiresAt } } pageInfo { endCursor hasNextPage } } }`.
The same field works under `user(id: $id)` for administrators. Browser users may read their own sessions; foreign-user and API-key access require `session:read`.
`SessionResolver` computes `current`, `impersonatedById` and the `impersonatedBy: User` relation.
Apply the session SELECT policy migration; ordinary reads exclude the token column and retain RLS. Never expose `token` as a GraphQL field.

`SessionService` provides:

- `getCurrentAuthenticatedSession()` — resolves the current built-in entities;
- `listCurrentUserSessions()` — lists the current user's active sessions;
- `getSessionConnectionByUser(user, args)` — paginates safe session entities for the parent user;
- `getSessionImpersonator(session)` — resolves the impersonator under request RLS;
- `revokeSession(userOrId, id)` / `revokeUserSessions(userOrId)` — administrative revocation;
- `revokeCurrentUserSession(id)` — revokes one of the current user's sessions by its public ID;
- `revokeCurrentUserOtherSessions()` — keeps only the current session;
- `revokeCurrentUserSessions()` — revokes every session for the current user;
- `setSessionCookie(token)` — writes an application-created session's signed
  cookie to the browser response without changing the current request's identity.

Authentication-backed methods read request headers from `RequestContext`;
parent-scoped methods receive the query target and authorize the current caller.
Transport code does not need to convert or forward Express headers.

The parent-scoped methods now belong to `SessionService`, not `UserService`.
Safe reads retain request RLS and are not in the infrastructure's privileged
allowlist. Administrative revocation keeps its existing special context and
`session:revoke` permission checks. `listCurrentUserSessions()` remains a credential-bearing
internal workflow helper; GraphQL uses `getSessionConnectionByUser()` instead.

Session lists preserve backend order and expose the non-secret session ID used
to revoke a specific session. Authentication tokens remain internal and in the
HttpOnly browser cookie. A UI should identify the current session and avoid
presenting it as an ordinary remote-device revoke action.

`setSessionCookie()` writes the signed browser cookies through the request-scoped
`cookies()` store and expires cached session and account cookies. `AuthService.impersonateUser(id)` and `stopImpersonating()` coordinate this with
session creation/restoration and refresh the current request's user, session,
workspace membership, abilities and RLS before returning. Nested mutation fields
therefore use the new identity, not the identity from the original cookie.

For administrative revocation, `SessionService.revokeUserSessions(user)` removes
both the user's own sessions and impersonation sessions started by that user.
Revoked impersonation sessions cannot restore the administrator's identity;
the impersonated user's independent sessions remain valid.

When PostgreSQL RLS is enabled, AuthModule infrastructure establishes an isolated
auth context for SessionService credential hydration after Better Auth validates
the request. SessionService itself only uses its injected `this.em`. Business
roles do not need to read credential columns; the parent database context remains
unchanged. GraphQL `User.sessions` always retains request RLS.

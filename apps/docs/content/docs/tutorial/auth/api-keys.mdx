title: "API Keys"
description: "Authenticate personal and workspace automation with scoped API keys."
---

`UserApiKeyService` and `MemberApiKeyService` manage personal keys owned by users and workspace-scoped keys owned by members.

- A **user key** restores its user and may access a selected workspace only
  while that user remains an active member.
- A **member key** restores its owning member and workspace. User members
  also restore their login user; service accounts have no login user. Disabled
  members and currently banned login users cannot authenticate.

Personal key management uses `user-api-key:read` and `user-api-key:write`.
Member key management uses `member-api-key:read` and `member-api-key:write`.
`read` allows queries; `write` allows creation, updates, enabling/disabling, and
deletion. Neither permission implies the other. Ownership and grant ceilings still apply.
In the example, both user roles include personal key-management permissions.
API-key requests receive only the explicitly granted actions after permission
intersection; they do not inherit an unconditional `manage` rule.
The example UI uses the server's permission options and preselects only entries
with both `default` and `grantable` set to true.

## Member ownership and service accounts

`Member.type` is `USER` (the default) or `SERVICE_ACCOUNT`. User members require
a login user; service accounts require `user = null` and use the same roles,
permissions, status, profile editor, and removal operations as other members.
Create one with `MemberService.addServiceAccount(workspace, name, options)` or:

```graphql
mutation {
  addMember(input: { type: SERVICE_ACCOUNT, name: "CI deployer" }) {
    id
  }
}
```

`MemberApiKeyService.createMemberApiKey(workspace, { member, ...options })`
accepts a member entity or ID; GraphQL accepts optional `input.memberId`.
A user can issue keys for their own membership or an active service account
in the selected workspace, never another user's membership. Omitting the owner
uses the current member. The example form defaults to **You**, passing the current
member ID. Choose **Service account** to show a searchable account dropdown.
When that dropdown is left unselected, the frontend first calls `addMember` with
`type: SERVICE_ACCOUNT` and the key name, then passes the returned `memberId`
to `createMemberApiKey`. Account and key creation are separate API operations,
requiring `service-account:write` and `member-api-key:write`, respectively.
Selected permissions are sent to `addMember` as direct grants with `roles: []`.
With no selection, roles and permissions are omitted, assigning the configured
default workspace role (MEMBER by default).

Creation and updates cannot grant permissions beyond the target member's effective
roles and direct grants or the issuer's grants. At request time, non-empty key
permissions intersect with the member's current grants. Empty key permissions
inherit the member's full grants, including later role and permission changes.
With `member-api-key:read` or `member-api-key:write`, callers can read or
delete other members’ keys in that workspace, subject to object rules and
credential ceilings. Plaintext remains available only at creation.

`MemberApiKey.member` is the only persisted owner relation. `memberId` and
the derived `workspaceId` support clients and authorization conditions. Removing
a member deletes its keys; disabling a member rejects future authentication.
Role and direct-permission changes affect the key on its next request.

The beta example keeps init and generates `Migration20261009070926` from the final
model. It creates member-owned keys and service account constraints directly; old
conversion migrations are removed. Application databases with existing data need
their own migration.

## Service API

- `getUserApiKey`, `createUserApiKey`, `updateUserApiKey`, and `deleteUserApiKey`;
- `getMemberApiKey`, `createMemberApiKey`, `updateMemberApiKey`, and `deleteMemberApiKey`;
- `UserApiKeyService.getUserApiKeyConnection(user, args)` and `MemberApiKeyService.getMemberApiKeyConnection(workspace, args)` return connections;
  Authentication and usage tracking are internal infrastructure responsibilities; consumers use the two management services.

GraphQL exposes the connections as `User.apiKeys` and `Workspace.apiKeys`,
usually queried through `currentUser` or `currentWorkspace`. The service performs
authorization and invokes `ConnectionManager` in the request ORM context with native RLS; the
resolver passes its parent and connection arguments without running queries itself.
Connection methods check the current identity and read ability directly. Ownership
and API-key permission-ceiling filters are internal implementation details, shared
with single-key lookups rather than exposed as public filter-building methods.
Connections also check each returned node against the read ability. If a conditional
rule denies any node, the entire page fails authorization; nodes are not silently
removed after pagination, so successful pages retain their original cursors and counts.

Single-key lookups use `User.apiKey(id)` and `Workspace.apiKey(id)`, replacing
the root `userApiKey(id)` and `apiKey(id)` queries. The service checks the parent
owner, permissions and request RLS. Rows excluded by ownership, credential scope,
or RLS return null; the service also checks the loaded entity against conditional
read rules and raises an authorization error if those rules deny access.

```graphql
query Keys($userKeyId: ID!, $memberKeyId: ID!) {
  currentUser {
    apiKey(id: $userKeyId) {
      id
      name
    }
  }
  currentWorkspace {
    apiKey(id: $memberKeyId) {
      id
      name
    }
  }
}
```

Creation and parent-field lookups still receive the owning user or workspace.
Updates and deletes only receive resource IDs: `updateUserApiKey(id, input)`,
`updateMemberApiKey(id, input)`, `deleteUserApiKey(id)`, and
`deleteMemberApiKey(id)`. The Service reads the persisted owner, checks the
request identity, selected workspace, operation ability and delegation ceiling,
and preserves native request RLS. Foreign owners are rejected even if the
database returns them; rows hidden by RLS are treated as not found.
Workspace mutations are named `createMemberApiKey`, `updateMemberApiKey`
and `deleteMemberApiKey`, matching the existing `*UserApiKey` operations.
The old unqualified mutation names are removed. Inputs and results are scoped: `CreateUserApiKeyInput`, `UpdateUserApiKeyInput`, `CreateUserApiKeyResult`, and their `Workspace` counterparts. Connections return `UserApiKey` or `MemberApiKey`, respectively.

Apply the example's `Initial → generated schema migrations`. It supplies uniform default table privileges. Services restrict update fields and omit credential hashes from read results; the database no longer enforces column-level restrictions. Custom applications still need correct policies; RLS does not replace
Service authorization.

Create methods return the plaintext key exactly once. The database stores a
SHA-256 hash of the complete key, the display-safe `start` and `prefix`, enabled
state, permissions, expiration, and usage timestamps. Successful authenticated
requests update `lastUsedAt` automatically. A custom prefix must contain 1–32
lowercase ASCII letters, digits, underscores, or hyphens and start with a letter.
User keys default to `user_`; member keys default to `ws_`.

Prefixes are concatenated directly with the random suffix; separators are not added automatically. Precedence is the creation `prefix` → the scope’s `apiKey.user.defaultPrefix` or `apiKey.member.defaultPrefix` → the `API_KEY_PREFIX` environment variable → the built-in default. Configuration changes affect newly created keys only.

## Permission Values

The auth package stores and evaluates permissions as `string[]`. Applications
define closed user and workspace permission catalogs. `UserApiKeyService` and `MemberApiKeyService` validates
permission values against those catalogs during key creation and updates.
Permission identifiers use lowercase `resource:action` names; each segment starts
with a letter and may contain lowercase letters, digits, and single hyphens.
Underscores, consecutive hyphens, and mixed-case values are rejected at startup.
Catalog membership, grant ceilings,
and key intersections use exact string equality without normalization.
GraphQL uses separate `UserApiKeyPermission` and `MemberApiKeyPermission` enums, mapping `user-api-key:read` to
`USER_API_KEY__READ` on the wire while retaining the original value internally.
Auth maps `user-api-key:*` to `UserApiKey` in user abilities and
`member-api-key:*` to `MemberApiKey` in workspace abilities. Business extensions bind
custom permissions through the restricted `AbilityRules.can` API.

```typescript
const workspacePermissions = ["workspace:update", "member:write"] as const;

type WorkspacePermission = (typeof workspacePermissions)[number];

const userKeyPermissions = ["user:read", ...workspacePermissions] as const;
```

Entity properties and database columns retain original strings. GraphQL inputs and outputs use scoped enums; the client derives form options and TypeScript types from generated enums. A member key accepts only configured workspace
permissions; a user key accepts the union of the configured user and workspace
catalogs. Malformed, duplicate, and unknown values are rejected. PostgreSQL
persists the values in `text[]` columns.

Creation and update also enforce a permission ceiling. User-scoped permissions
on a User Key cannot exceed the owning user's current role and direct
permissions. A Member Key cannot exceed its owning member's current role
and direct permissions, the issuer's effective workspace permissions, or the
authenticating API key's permissions.
Workspace permissions on a User Key are checked again
against the selected member at request time, so one key can be used across
workspaces without freezing or copying membership privileges.

Configure defaults and grant allowlists independently for each key scope:

```typescript
AuthModule.forRoot({
  // ...other auth options
  apiKey: {
    user: {
      defaultPrefix: "user_",
      defaultPermissions: ["user:read"],
      allowedPermissions: ["user:read", "workspace:update"],
    },
    member: {
      defaultPrefix: "ws_",
      defaultPermissions: ["workspace:update"],
      allowedPermissions: ["workspace:update", "workspace:delete"],
    },
  },
});
```

`defaultPermissions` defaults to `[]` and applies only when creation omits the
`permissions` field. Passing `null` or `[]` inherits the owner's complete current permissions.
For user keys, an omitted `allowedPermissions` uses the combined user/workspace
catalog; for member keys, it uses only the workspace catalog. An explicit `[]`
allows no explicit permission selections. This allowlist does not cap inherited
owner permissions on keys with `permissions: []`. Both scopes are validated at startup and defaults must be a
subset of that scope's allowlist. User keys may default to `user:read` or
`member:invite`. Member keys owned by user members can send invitations
when their member and key grants allow it; service accounts have no inviter user.

The previous flat `apiKey.defaultPermissions` and `apiKey.allowedPermissions`
options have been removed. Move each list under `apiKey.user` and/or
`apiKey.member`, removing user-only grants from the workspace list. Omitted
scope configuration retains its normal defaults; it does not inherit the other scope.

Use `userApiKeyPermissions` and `memberApiKeyPermissions` to populate key
editors. Both return `{ permission, grantable, default }` entries using the corresponding
API-key permission enum. Grantability includes the configured allowlist, the
issuer's grant ceiling, and the current key's permissions. Member keys may
receive `member:invite` to read and cancel invitations; creation still requires a
user identity. Retain non-grantable entries for
display, but exclude them from new selections and default selections. Services
still validate every write; this list is not an authorization substitute.
`default` reflects the configured default permissions independently of grantability.
Preselect only entries where `default && grantable`; do not infer defaults from enum values.

The allowlist caps explicit selections rather than granting permissions. Requested
permissions must also belong to the key owner's supported scope and remain
within the issuer's effective permissions. When an API key creates or updates
another key, the delegated permissions cannot exceed the authenticating key's
own permissions. Reading, updating, or deleting an existing key also requires
that its **stored** permissions fit inside the authenticating key's scope;
replacing its permissions with an empty list cannot bypass this check. Lists
apply the same restriction in the database, including pagination counts. Restricted
credentials cannot create or manage inherited keys; those keys are excluded from their lists.
Browser sessions can still manage all keys they own, subject to the normal
ability checks. Updates that omit `permissions` preserve the stored value;
passing `null` clears it.

An authorized caller can disable a key with `{ enabled: false }`, without replacing
its permissions, even if those stored permissions no longer satisfy the configured
allowlist or the issuer's current grants. Ownership, update ability, and the
authenticating key's stored-permission ceiling still apply. Re-enabling the key,
other updates, and explicit permission replacements validate permissions normally.

## Transport

Send API keys with the Bearer scheme:

```http
Authorization: Bearer sk-4tR9s...
```

`x-api-key` is not supported. Cookie session resolution runs first. When no
valid Cookie session exists, the Bearer credential is treated as an API key.

Use `@CurrentApiKey()` when a handler needs the credential that authenticated
the request:

```typescript
import { type ApiKey, CurrentApiKey } from "@nest-boot/auth";

audit(@CurrentApiKey() apiKey: ApiKey | null) {
  return apiKey;
}
```

For non-empty key permissions, before the configured builder runs, User Key permissions are intersected with
the owning user's effective permissions and, for workspace routes, the user's
current membership permissions. Member Key permissions are intersected with the owning member’s current
roles and direct grants. They populate `workspacePermissions`; member keys
never receive user-scope permissions. The builder receives the current member.
The top-level builder receives both scoped permission arrays and produces one
`AuthAbility`, which the guard checks.

The example baseline `Initial → generated schema migrations` also includes:
API-key creation and usage tracking retain request RLS and use default INSERT/UPDATE privileges. Services exclude credential hashes from ordinary reads and prevent ownership changes; direct SQL does not have these column restrictions. Auth infrastructure
establishes the isolated credential-validation context; both management services use their injected `this.em`.

## Persistence

`UserApiKey` and `MemberApiKey` use separate `user_api_key` and `member_api_key` tables, each with one required owner foreign key and its own RLS policy. Authentication checks both tables and rejects credentials found in both, rather than choosing an ambiguous identity.

## Permission and ability responsibilities

| Setting or result             | Meaning                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| `permissions`                 | Declares available names; does not grant them.                                             |
| `roles`                       | Assigns permissions to roles; same-name roles extend built-in grants.                      |
| `buildAbility`                | Maps effective permissions to actions and object conditions.                               |
| `ability.can(action, object)` | Checks an operation on a particular object.                                                |
| `grantable`                   | Whether the current caller can delegate a permission; not target authorization.            |
| API-key option `default`      | Whether configuration preselects a permission; the editor requires `default && grantable`. |

Configuration extends built-in catalogs. User/member `set*` methods instead replace
stored assignments. Configure static options before startup; use Services to change
assignments at runtime. API-key ceilings apply before business rules are built.

## Built-in permission catalog

The catalog contains 26 permissions. Compose each name as `resource:action`:

| Scope     | Resource            | Actions                                                                                                                                      |
| --------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| User      | `user`              | `create`, `read`, `update`, `delete`, `set-roles`, `set-permissions`, `set-email`, `set-password`, `ban`, `impersonate`, `impersonate-admin` |
| User      | `session`           | `read`, `revoke`                                                                                                                             |
| User      | `user-api-key`      | `read`, `write`                                                                                                                              |
| User      | `workspace`         | `create`                                                                                                                                     |
| Workspace | `workspace`         | `read`, `update`, `delete`                                                                                                                   |
| Workspace | `member`            | `read`, `write`, `set-roles`, `set-permissions`, `invite`                                                                                    |
| Workspace | `workspace-api-key` | `read`, `write`                                                                                                                              |

`read` covers single and connection queries. `write` covers ordinary creation,
updates, and deletion, but does not imply `read` or role/permission changes.
`member:invite` maps to `read` and `write` on `Invitation`, independently of member
writes. Role and direct-permission setters also enforce the caller's grant ceiling.
`user:ban` covers banning and unbanning; administrator impersonation requires both
`user:impersonate` and `user:impersonate-admin`.

There are no unconditional baseline abilities. The default `user` role explicitly
grants `workspace:create`; `member` grants `workspace:read` and `member:read`.
Session-only self-service paths (such as discovering one's memberships and
accepting/rejecting one's invitations) check identity and ownership separately.
API keys do not inherit these session-only paths.

## Complete business example

The [tested Report recipe](https://github.com/nest-boot/nest-boot/tree/beta/examples/server/src/app/auth/examples)
connects configuration, a Service, and the example client's actual ability helper.
It is optional and is not registered in the demo application or its database.

```typescript
AuthModule.forRoot({
  workspace: {
    permissions: ["report:read", "report:archive"],
    roles: {
      owner: ["report:read", "report:archive"],
      "report-reader": ["report:read"],
    },
  },
  buildAbility: ({ can }, { workspace }) => {
    if (!workspace) return;
    can({ workspace: "report:read" }, "read", Report, {
      workspaceId: workspace.id,
    });
    can({ workspace: "report:archive" }, "archive", Report, {
      workspaceId: workspace.id,
      archived: false,
    });
  },
});
```

The callback's `can` is the permission-bound auth helper, not raw CASL `can`:
it adds no rule unless the caller has the first argument's permission. Do not
repeat `permissions.includes(...)`. A reader may read reports but not archive;
an owner using a read-only API key also cannot archive.

Load the operation target before checking its conditions. Do not trust ownership
fields supplied by the client or substitute a class-level route check:

```typescript
async archiveReport(id: string): Promise<Report> {
  const report = await this.loadReport(id);
  this.access.assertCan("archive", report);
  return await this.repository.archive(report);
}
```

The frontend queries `currentAbilityRules { actions subjects conditions
fields inverted reason }`. Rehydrate those rules with the existing client helper:

```typescript
const ability = createAbility(data.currentAbilityRules);
const canArchive = ability.can(
  "archive",
  createAbilitySubject("Report", report),
);
```

Select the condition fields (`workspaceId`, `archived`) with each report. Never
rebuild role-to-permission mappings in the client. Use permission option queries
for grant editors and instance abilities for action buttons; the Service makes
the final decision. API-key editors use the server's scoped defaults, not a
hardcoded list of enum values. See [API keys](./api-keys).

This recipe uses operation/object checks. Built-in auth Service methods do not
automatically enforce CASL field-level rules. Business-specific field restrictions
require explicit Service checks; declaring a field rule alone is insufficient.
No rule preventing administrators from editing names is introduced here.

## Global Guard

Register the configured module's `AuthGuard` globally. It accepts a valid Cookie
session or API key and evaluates route permissions with the same guard.

```typescript
import { AuthGuard } from "@nest-boot/auth";
import { APP_GUARD } from "@nestjs/core";

@Global()
@Module({
  imports: [AuthDynamicModule],
  providers: [{ provide: APP_GUARD, useExisting: AuthGuard }],
})
export class CommonModule {}
```

Use `@Public()` for routes that do not require authentication. If a public route
also declares a permission decorator, its permission is still evaluated.
Unauthenticated access to a protected route returns `401 Unauthorized`;
authenticated requests that fail a permission check return `403 Forbidden`.

```typescript
@Public()
@Query(() => String)
health(): string {
  return "ok";
}
```

## Build Abilities

Configure one top-level `buildAbility` callback. `AuthGuard` prepares a single
`AuthAbility` for the current identity, even without a permission decorator.
Its context contains `user`, `workspace`, `member`, `userPermissions`, and
`workspacePermissions`. Identity fields are nullable: workspace API keys have
no user or member; workspace context requires an active membership or a matching
workspace key. Check identity fields before using them in conditions.

Auth owns built-in mappings; no callback is required for built-in operations.
The callback runs once per identity snapshot, synchronously, and returns nothing.
The ability is cached in `RequestContext` and rebuilt after identity or authorization changes.

Class-level checks only gate an operation; conditional rules are also evaluated
against loaded entities and proposed entities before creation. `currentMember`
and `currentWorkspace` also check the selected instance's workspace read rules;
being present in the request context does not bypass authorization. CASL-authorized
connections validate each returned node and reject the entire page if one is
denied, rather than silently filtering a page and changing its pagination.
Administrative bulk session revocation locks and authorizes every target before
deleting any of them. Ownership-based self-service session operations remain
separate from administrative `session:read` and `session:revoke` permissions.

After a successful password reset, auth rechecks the current session in the
database. If the reset revoked it, the request loses its identity, abilities, and
database scope before another mutation can run. Unrelated sessions and API-key
identities are retained.

Sign-in, registration, and impersonation flows reject an active outer transaction
before issuing a replacement session or cookie. Self-deletion revokes the request
identity immediately after its database commit, before `afterDelete` runs; a
failing post-delete callback cannot leave the deleted identity authorized.

```typescript
import { AuthModule } from "@nest-boot/auth";

const userRoles = {
  admin: ["post:create"],
  user: ["post:read", "post:update"],
} as const;
const userPermissions = [
  "post:create",
  "post:archive",
  "post:read",
  "post:update",
] as const;

const workspaceRoles = {
  owner: ["post:create", "post:delete"],
  member: ["post:create"],
} as const;
const workspacePermissions = [
  "post:create",
  "post:delete",
  "post:archive",
] as const;

AuthModule.forRoot({
  workspace: {
    permissions: workspacePermissions,
    roles: workspaceRoles,
  },
  user: {
    permissions: userPermissions,
    roles: userRoles,
  },
  buildAbility: ({ can }, { user, workspace, member }) => {
    if (user) {
      can({ user: "post:read" }, "read", Post);
      can({ user: "post:update" }, "update", Post, { authorId: user.id });
    }
    if (workspace) {
      can({ workspace: "post:create" }, "create", Post, {
        workspaceId: workspace.id,
      });
      can({ workspace: "post:delete" }, "delete", Post, {
        workspaceId: workspace.id,
      });
      if (member) {
        can({ workspace: "post:archive" }, "archive", Post, {
          workspaceId: workspace.id,
          assignedMemberId: member.id,
        });
      }
    }
  },
});
```

User and workspace scopes retain separate catalogs and role registries. Roles
must reference permissions from their own scope. The context permission arrays
are immutable, deduplicated, and already limited by the authenticating API key.
They remain separate so equal custom permission names do not imply equal scope.

The first argument is a restricted `AbilityRules`, not a CASL builder.
Bind each grant to exactly one source:
`can({ user: permission }, action, subject, conditions?)` or
`can({ workspace: permission }, action, subject, conditions?)`.
A grant is added only when that scope's effective permissions contain the name.
Field rules use `can(binding, action, subject, fields, conditions?)`.
Unknown permission names, grants targeting built-in auth entities (by class or
name), and grants targeting `all` are rejected. Use built-in permissions to grant
auth operations; custom permission names cannot redefine their mappings.
`cannot(action, subject, conditions?)` can restrict both business and built-in
operations; it also supports fields and always takes precedence over extension
grants, regardless of declaration order. The callback exposes neither mutable
rules nor `build()`. It is a trusted application extension, not a JavaScript sandbox.

## Manage Roles

Role names match `^[a-z][a-z0-9-]*$`; permission names use
`resource:action`, with each segment matching the same pattern. Underscores,
uppercase letters, whitespace, and consecutive hyphens (`--` or longer) are
rejected at startup, not normalized. Both resource and action segments may
contain single hyphens, for example `member:set-roles`.
The role names `true`, `false`, and `null` are reserved.
`RoleName<T>` and `PermissionName<T>` validate string literals at compile time;
`AuthModule.forRoot()` and `forRootAsync()` infer catalogs, role keys, and lifecycle
role references. Dynamic strings are checked at startup.

```typescript
import type { PermissionName, RoleName } from "@nest-boot/auth";

const role: RoleName<"super-admin"> = "super-admin";
const permission: PermissionName<"user-api-key:read"> = "user-api-key:read";
```

GraphQL generates `UserRole`, `WorkspaceRole`, `UserPermission`,
`WorkspacePermission`, `UserApiKeyPermission`, and `WorkspaceApiKeyPermission` from the configuration.
Enum names are uppercase: hyphens become `_` and the permission separator `:`
becomes `__`. For example, `super-admin` is exposed as `SUPER_ADMIN` and
`user-api-key:read` as `USER_API_KEY__READ`. GraphQL variables and responses use these enum
names; services, ability builders, and the database retain the original values.
Regenerate client types after changing a catalog. Existing stored assignments
must remain in the configured catalog to be serialized by GraphQL.

`UserApiKeyPermission` uses the combined user and workspace catalogs;
`WorkspaceApiKeyPermission` uses the workspace catalog. Neither enum narrows with
the corresponding `apiKey.user.allowedPermissions` or `apiKey.workspace.allowedPermissions`,
so previously stored grants remain readable after
the allowlist changes. Services enforce the allowlist on writes.
User and workspace permission catalogs extend the built-in defaults. Omitting
them or passing `user.permissions: []` or `workspace.permissions: []` preserves
those defaults. To define a role without permission grants, add a new role with
`[]`; empty additions do not remove an existing role's built-in grants.
An empty allowlist in either API-key scope still generates enums
from the full catalogs, but does not allow granting permissions to a key.
Services continue to check key scope and the issuer's permission ceiling.

Nest enum metadata is process-wide. Concurrent AuthModule applications in one
process must use identical enum catalogs; conflicting registrations fail at
startup instead of overwriting another application's schema. Shutdown releases
the registration so a later application can use a different configuration.

Permission catalogs and role definitions come from `user.permissions`,
`user.roles`, `workspace.permissions`, and `workspace.roles`; they are not
stored or managed by a separate role service. `UserService` and
`MemberService` expose the configured catalogs to transports and validate
role assignments.

`listRoles()` returns `{ role, grantable }` objects and `listPermissions()` returns
`{ permission, grantable }` objects for the current request. Services retain the
original configured values; GraphQL serializes them as enum names.

```typescript
const userRoles = userService.listRoles();
const userPermissions = userService.listPermissions();
await userService.setUserRoles(user, ["admin", "auditor"]);

const workspaceRoles = memberService.listRoles();
const workspacePermissions = memberService.listPermissions();
await memberService.setMemberRoles(member, ["admin"]);
```

`setUserRoles()` and `setMemberRoles()` reject empty or unknown role names.
`setMemberRoles()` can assign or replace any configured role, including
`workspace.creatorRole`, when update ability and permission-grant checks pass.
Multiple members may hold the creator role; assigning it does not change other
members' roles. Member creation and invitations use the same grant checks.

`user.defaultRole` and `workspace.defaultRole` provide fallback roles for new
users and members. `workspace.creatorRole` identifies the ownership role.
`user.adminRoles` may contain multiple roles and is used by
`UserService.isAdmin()` to classify administrative users. Every configured
lifecycle role is validated against its role map at startup.

`getEffectiveUserPermissions()` and `getEffectiveMemberPermissions()` return the deduplicated
union of permissions inherited from every assigned role and permissions stored
directly on the entity. `hasPermissions()` evaluates against the same result.
`createUser()`, `addMember()`, `setUserPermissions()`, and
`setMemberPermissions()` reject malformed, duplicate, or unknown direct
permissions instead of persisting values outside the configured catalog.

User administration also enforces a grant ceiling: `createUser()`, `setUserRoles()`,
and `setUserPermissions()` cannot grant permissions the caller does not hold.
Role assignments include their inherited permissions, including the default role
on user creation. For a personal API key, the ceiling is the intersection of the
user's role/direct permissions and the key's permissions. Holding `user:set-roles`
alone does not allow promotion to a more privileged role.

`userRoles` and `workspaceRoles` return the full role catalog as `{ role, grantable }`
objects. `userPermissions` and `workspacePermissions` similarly return
`{ permission, grantable }` objects. The enum-valued fields preserve type-safe inputs;
`grantable` reflects the current principal's grant ceiling, including API-key
restrictions. Workspace role options require `member:set-roles` or `member:invite`
to be grantable; direct permission options require `member:set-permissions`.
Callers with only `member:read` receive workspace options with `grantable: false`.
User role and permission catalogs require `user:set-roles` and `user:set-permissions`, respectively.
Use these flags to disable new grants while keeping existing values removable,
and validate the complete replacement list before submission. Mutation Services
still enforce target-specific abilities and grant ceilings. The separate
`workspaceAssignableRoles` query has been removed.

The example GraphQL application exposes `userRoles`, `userPermissions`,
`workspaceRoles`, and `workspacePermissions` queries. Role changes use the
dedicated `setUserRoles` and `setMemberRoles` mutations. Direct
member grants use `setMemberPermissions`; ordinary member
profile updates do not accept authorization fields.

## Protect Routes

Use `@Can(action, subject)` for both user and workspace operations. `AuthGuard`
checks the same unified ability as Services; decorators need no scope option.

```typescript
@Can("read", Post)
@Query(() => [Post])
posts() {
  return this.postService.findAll();
}

@Can("read", User)
@Query(() => User)
me(@CurrentUser() user: User) {
  return user;
}
```

Every requirement declared on a route must pass. Repeated `@Can` declarations
use `all` semantics. Class-level requirements are merged with method-level
requirements, not replaced by them.

```typescript
@Can("read", Post)
@Can("update", Post)
@Mutation(() => Post)
updatePost() {
  // Requires both post:read and post:update.
}
```

Use a subject factory when authorization depends on a concrete object. The
factory receives the controller or resolver instance first, followed by its
decorated method parameters.

```typescript
@Can("update", (self: PostResolver, id: string) =>
  self.postService.findOneOrFail({ id }),
)
@Mutation(() => Post)
updatePost(@Args("id") id: string) {
  return this.postService.update(id);
}
```

Workspace API keys contribute only workspace grants. User API keys contribute
user grants and, with a live membership, workspace grants. Each source is
limited by the credential before `buildAbility` runs. The Guard checks the
resulting `AuthAbility`. Built-in workspace rules match the selected workspace's
ID; select `workspaceId` on Member, Invitation, and WorkspaceApiKey when checking
their instances in the client. Business rules must declare their own object
conditions using the callback context.

Auth maps built-in permissions automatically. Business extensions bind their
rules explicitly, for example `can({ user: "post:read" }, "read", Post)`. The factory
checks effective permissions even if the callback does not inspect them, so an
API key without `post:read` cannot acquire that rule. The frontend rehydrates the
final serialized rules instead of maintaining a separate permission mapping.

## Service Authorization Boundary

`UserService`, `SessionService`, `WorkspaceService`, `MemberService`,
`InvitationService`, and `UserApiKeyService` and `WorkspaceApiKeyService` enforce their permissions
before reading or mutating authentication data. Resolver and controller
decorators provide early rejection and declare intent, but they are not the
security boundary: omitting one does not make a protected service operation
public.

The services follow the same split as Better Auth's admin and organization
access control:

- user administration uses `user:*` and `session:*` permissions;
- workspace operations use `workspace:*` and `member:*` permissions;
- `member:invite` manages invitation queries, creation, and cancellation, separately
  from `member:write`; accepting or rejecting one's own invitation checks recipient identity;
- workspace API-key management uses `workspace-api-key:read/write`;
- current-user authentication, session management, invitation acceptance, and
  leaving a workspace use authenticated identity and ownership checks.

`AccessControlService` exposes `can()` and `assertCan()` for
application services that need the same fail-closed boundary. An ability must
have been prepared by the global `AuthGuard`; calls outside that request
lifecycle are denied rather than implicitly trusted.

The Guard, route decorators, Services, and helpers all evaluate operations
through this service's `ability.can()` checks. Helpers do not fall back to a cached
Ability when the authorization service is unavailable.

Ability construction and grantability checks share one immutable effective-permission
snapshot for the current request identity. Owner permissions remain distinct from
credential-limited permissions: managing an API key checks both its owner's grants
and the issuing credential's ceiling. Permission delegation is not inferred from
an operation's `ability.can()` result.

## Lower-Level Checks

After `AuthGuard` prepares the request, use the same helpers in lower-level code:

```typescript
import { can, getAbility } from "@nest-boot/auth";

if (!can("update", post)) {
  throw new ForbiddenException();
}
const ability = getAbility();
ability.can("read", post);
```

`can()` returns `false` when authorization context is unavailable.
`getAbility()` throws `ForbiddenException` instead. `AuthAbility` is also the
request-context token, but use the helpers for fail-closed access.

The example frontend exposes `useAbility()` for both personal and workspace
pages. Its provider consumes `currentAbilityRules` for the selected identity;
it does not merge or independently derive permissions.

## Database Scope Policies

The built-in User SELECT policy permits the `authenticated` database role to
read all User rows; anonymous reads remain denied. User profile visibility is
enforced by Service Ability checks, not by this SELECT policy. Custom permissions
can therefore grant User read actions without a database permission-name mapping.
Do not expose direct User ORM/SQL queries without Service authorization. User
writes and Session reads likewise rely on Service authorization. Database request
variables do not carry application permissions; other RLS policies retain their
ownership and workspace-scope constraints.

`userScopePolicy()` and `workspaceScopePolicy()` return native MikroORM policy
definitions. Every option is optional:

| Factory                  | `type`   | `property`  | `command` | `roles`             |
| ------------------------ | -------- | ----------- | --------- | ------------------- |
| `userScopePolicy()`      | `bigint` | `user`      | `all`     | `["authenticated"]` |
| `workspaceScopePolicy()` | `bigint` | `workspace` | `all`     | `["authenticated"]` |

```typescript
import { Entity } from "@mikro-orm/decorators/legacy";
import { Member, userScopePolicy, workspaceScopePolicy } from "@nest-boot/auth";

@Entity({
  policies: [
    // Read your memberships across workspaces; do not grant cross-workspace writes.
    userScopePolicy({ command: "select" }),
    workspaceScopePolicy(),
  ],
})
export class Member extends Member {}
```

`property` names an entity property, not its SQL column. Native callbacks resolve
custom column mappings; use a scalar ID or a single-column owning relation.
`type` is an explicit database cast: `bigint`, `integer`, `uuid` or `text`.
For example, `userScopePolicy({ property: "owner", type: "uuid" })` matches an
owner UUID. On the User entity itself, use `property: "id"`.
`command`, `roles` and the optional policy `name` can also be overridden.

The policies compare against `app.user.id` or `app.workspace.id` and preserve
`nullif(current_setting(..., true), '')`, so missing/empty identifiers match no
rows. They are permissive policies: policies for the same operation combine with
OR. They do not check workspace lifecycle or replace Service authorization.
Continue to configure database roles, table privileges and trusted session
variables separately.

Auth stages identity variables `app.user.id` and `app.workspace.id`, but does not
pass application permissions to the database. Services enforce Ability rules,
custom permissions and API-key ceilings; RLS handles ownership, workspace
isolation. Authenticated User reads/writes and Session reads
rely on Service authorization. Do not expose direct ORM/SQL access to these
records as an alternative to Services. Old identity keys are no longer supported.

The example `UserApiKey` and `WorkspaceApiKey` use separate tables, each with one required owner foreign key, so no exclusive-owner CHECK is needed. RLS compares `user_id` with `app.user.id` and `workspace_id` with `app.workspace.id` independently, including when IDs coincide. Deleting an owner cascades to its keys; workspace deletion is permanent. Default privileges authorize table operations; both management services hide credential hashes, prevent ownership changes, and enforce authorization.

These are plain factories, not filters or decorators. Neither runtime nor CLI
needs a custom discovery hook. Generate and apply migrations after changing
policies; keep metadata caching disabled when using policy callbacks.
For custom application entities that need soft deletion, compose
[`softDeletePolicies()`](/docs/tutorial/mikro-orm#soft-delete-rls-policies).

## Authorization Changes Within a Request

After a Service commits changes to the current user's profile, roles, permissions
or ban state, the current member's profile, roles, permissions or status, or the
current workspace's profile, Auth refreshes the request identity and abilities.
An internal identity coordinator invalidates the permission snapshot, rebuilds
abilities, and synchronizes changed database identity values. Session adoption
also completes this process before returning; callers do not separately refresh
the Guard. If post-commit identity publication fails, the request is revoked.
Disabling the current
member, leaving a workspace or deleting it clears the workspace scope, including
the parent request when deletion uses an isolated execution context.

Call these self-updates, `leaveWorkspace()` and `deleteWorkspace()` outside an
existing transaction. They must complete their own commit before updating request
authorization; MikroORM cannot restage session context inside an active transaction.
Failed writes leave request authorization unchanged. Updates to other users or
members do not replace the caller's identity.

The same commit boundary applies when editing the authenticating API key:
permission changes refresh its abilities; disabling or deleting
it clears the entire request identity, without falling back to unrestricted user
permissions. Successful `signOut()` also clears authentication immediately, while
`updateCurrentUser()` reloads the persisted profile before subsequent operations.
Call these methods outside an existing transaction as well.

## Client Ability Rules

Use `serializeAbilityRules()` when a transport needs to send an already-built
ability to a browser or another process. It converts class subjects to their
stable class names and preserves actions, fields, conditions, inverted rules,
and reasons. The result is JSON-safe and can be rehydrated with CASL's
`createMongoAbility()`.

```typescript
const rules = serializeAbilityRules(getAbility());
```

Treat transported rules as a user-interface capability model only. The server
guard and service authorization checks remain authoritative for every request.

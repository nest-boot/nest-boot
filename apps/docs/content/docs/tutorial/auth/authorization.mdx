## Global Guard

Register the configured module's `AuthGuard` globally. It accepts a valid Cookie
session or API key and evaluates route permissions with the same guard.

```typescript
import { AuthGuard } from "@nest-boot/auth";
import { APP_GUARD } from "@nestjs/core";

@Global()
@Module({
  imports: [AuthDynamicModule],
  providers: [{ provide: APP_GUARD, useExisting: AuthGuard }],
})
export class CommonModule {}
```

Use `@Public()` for routes that do not require authentication. If a public route
also declares a permission decorator, its permission is still evaluated.

```typescript
@Public()
@Query(() => String)
health(): string {
  return "ok";
}
```

## Build Abilities

Configure separate user and workspace abilities. Each callback runs at most
once per request and its result is cached in `RequestContext`. Returning `null`
causes that authorization scope to fail.

```typescript
import { AuthModule, PermissionAbilityBuilder } from "@nest-boot/auth";
import { RequestContext } from "@nest-boot/request-context";

const userRoles = {
  admin: ["project:create"],
  user: [],
} as const;
const userPermissions = ["project:create", "project:archive"] as const;

const workspaceRoles = {
  owner: ["project:create", "project:delete"],
  member: ["project:create"],
} as const;
const workspacePermissions = [
  "project:create",
  "project:delete",
  "project:archive",
] as const;

AuthModule.forRoot({
  // ...
  workspace: {
    permissions: workspacePermissions,
    roles: workspaceRoles,
    buildAbility: (_context, permissions) => {
      const { can, build } = new PermissionAbilityBuilder();
      for (const permission of permissions) {
        const [subject, action] = permission.split(":");
        if (subject === "post" && action) can(action, Post);
      }
      return build();
    },
  },
  user: {
    permissions: userPermissions,
    roles: userRoles,
    buildAbility: () => {
      const user = RequestContext.get(User);
      if (!user) return null;

      const { can, build } = new PermissionAbilityBuilder();
      can("read", Post);
      can("update", Post, { authorId: user.id });
      return build();
    },
  },
});
```

Each scope owns its permission catalog, role registry, and ability builder.
Every permission granted by a role must exist in that scope's `permissions`
array, otherwise application startup fails. AuthModule resolves role permissions
and direct entity permissions first. The builder receives only the deduplicated
effective permission list as its second argument.

## Manage Roles

Permission catalogs and role definitions come from `user.permissions`,
`user.roles`, `workspace.permissions`, and `workspace.roles`; they are not
stored or managed by a separate role service. `UserService` and
`WorkspaceService` expose the configured catalogs to transports and validate
role assignments.

```typescript
const userRoles = userService.listRoles();
const userPermissions = userService.listPermissions();
await userService.setRole(user, ["admin", "auditor"]);

const workspaceRoles = workspaceService.listRoles();
const workspacePermissions = workspaceService.listPermissions();
await workspaceService.updateMemberRole(member, ["admin"]);
```

`setRole()` and `updateMemberRole()` reject empty or unknown role names.
`updateMemberRole()` cannot modify a current creator or assign the configured
creator role; use `transferOwnership()` for that transition. An ownership
transfer assigns `workspace.creatorRole` to the next owner and demotes the
previous owner to `workspace.defaultRole`.

`user.defaultRole` and `workspace.defaultRole` provide fallback roles for new
users and members. `workspace.creatorRole` identifies the ownership role.
`user.adminRoles` may contain multiple roles and is used by
`UserService.isAdmin()` to classify administrative users. Every configured
lifecycle role is validated against its role map at startup.

`getUserPermissions()` and `getMemberPermissions()` return the deduplicated
union of permissions inherited from every assigned role and permissions stored
directly on the entity. `hasPermission()` evaluates against the same result.
`createUser()`, `addMember()`, `setUserPermissions()`, and
`setMemberPermissions()` reject malformed, duplicate, or unknown direct
permissions instead of persisting values outside the configured catalog.

The example GraphQL application exposes `userRoles`, `userPermissions`,
`workspaceRoles`, and `workspacePermissions` queries. Role changes use the
dedicated `setUserRoles` and `updateWorkspaceMemberRole` mutations. Direct
workspace-member grants use `setWorkspaceMemberPermissions`; ordinary member
profile updates do not accept authorization fields.

## Protect Routes

Use `@WorkspaceCan` for workspace permissions and `@UserCan` for personal or
application-level permissions. They write separate metadata and are evaluated
by the same `AuthGuard`.

```typescript
@WorkspaceCan("read", Post)
@Query(() => [Post])
posts() {
  return this.postService.findAll();
}

@UserCan("read", User)
@Query(() => User)
me(@CurrentUser() user: User) {
  return user;
}
```

If both decorators are present on a route, both permissions must pass. `@Can`
is a thin alias that delegates to the scoped decorator; omitted `scope`
delegates to `@WorkspaceCan`.

```typescript
@Can("read", Post) // @WorkspaceCan("read", Post)
@Can("read", User, { scope: "user" }) // @UserCan("read", User)
```

Use a subject factory when authorization depends on a concrete object. The
factory receives the controller or resolver instance first, followed by its
decorated method parameters.

```typescript
@WorkspaceCan("update", (self: PostResolver, id: string) =>
  self.postService.findOneOrFail({ id }),
)
@Mutation(() => Post)
updatePost(@Args("id") id: string) {
  return this.postService.update(id);
}
```

Workspace API keys can pass only workspace checks. User API keys can pass user
checks and, with a live membership, workspace checks. API-key permissions are
intersected with the corresponding ability.

## Lower-Level Checks

After a route-level decorator prepares an ability, lower-level code can use the
matching scoped helpers. `can()` is a thin alias that routes to them by `scope`
and defaults to `workspaceCan()`.

```typescript
if (!workspaceCan("update", post)) {
  throw new ForbiddenException();
}

userCan("read", user);
getWorkspaceAbility();
getUserAbility();

can("read", post); // workspaceCan(...)
can("read", user, { scope: "user" }); // userCan(...)
```

These helpers throw `ForbiddenException` if the route did not prepare the
requested ability.

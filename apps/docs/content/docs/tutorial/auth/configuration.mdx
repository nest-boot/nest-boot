## Module Options

Register `AuthModule` with `forRoot()` or `forRootAsync()`. Every public option is
declared by Nest Boot and translated to the internal authentication backend, so
dependency upgrades cannot silently expand the public API. Built-in social and
custom OAuth providers share one flat `providers` option.

Important Nest Boot options include:

- **`emailAndPassword.enabled`** — enables email/password authentication, defaulting to `true`;
- **`emailAndPassword.requireEmailVerification`** — requires verified email before sign-in, defaulting to `true`;
- **`emailAndPassword.password`** — overrides password hashing; the default uses `HashService`;
- **`emailAndPassword.sendResetPassword`** — overrides password-reset delivery;
- **`emailVerification.sendVerificationEmail`** — overrides verification delivery;
- **`user.changeEmail.enabled`** — enables the two-stage email-change flow;
- **`user.defaultRole`**, **`user.adminRoles`**, **`user.permissions`**, **`user.roles`**, and **`user.buildAbility`** — define user role lifecycles and authorization;
- **`workspace.defaultRole`**, **`workspace.creatorRole`**, **`workspace.permissions`**, **`workspace.roles`**, and **`workspace.buildAbility`** — define workspace role lifecycles and authorization;
- **`workspace.sendInvitationEmail`** — delivers persisted workspace invitations;
- **`apiKey.defaultPermissions`** — supplies permissions when key creation omits them;
- **`apiKey.allowedPermissions`** — limits permissions that may be granted to API keys;
- **`middleware`** — controls auth middleware registration and route selection;
- **`basePath`** — changes the auth endpoint path from `/api/auth/`;
- **`trustedOrigins`** — configures allowed browser origins;
- **`account`** — configures OAuth account linking, storage, and state validation;
- **`providers`** — configures built-in social, custom OAuth 2.0, and OpenID Connect providers.

`user.permissions` defaults to the standard `user:*`, `session:*`, and `api-key:*` catalog.
`user.roles` defaults to `admin` and `user`. The `admin` role grants the full
default catalog, while `user` grants none. Configured permissions extend the
catalog; configured roles add new roles or append grants to existing roles.
`user.defaultRole` defaults to `user`.
`user.adminRoles` defaults to `['admin']` and classifies administrative
identities, including targets that require `user:impersonate-admins` to
impersonate.

`workspace.permissions` defaults to the standard workspace permission catalog.
`workspace.roles` defaults to `owner`, `admin`, and `member`. Owners receive the
full default catalog, including workspace API-key management. Administrators
receive workspace, member, and invitation management permissions except
`workspace:delete`; API-key management is owner-only by default. Members receive none. Configured permissions and roles
extend these defaults in the same way. `workspace.defaultRole` defaults
to `member` for additions and invitations. `workspace.creatorRole` defaults to
`owner` and assigns the initial role to the workspace creator.

Empty permission arrays or role maps add nothing; built-in catalogs and role
grants remain available. Same-name role grants are merged and deduplicated.
Custom permissions are not automatically granted to built-in administrators or
owners: append them to the appropriate role explicitly. Use a new role for a
restricted grant set; setting `admin: []` does not remove its built-in grants.
Entity mutations such as `setUserRoles` and `setMemberPermissions` still replace
the stored values. API-key `allowedPermissions` remains a ceiling, not an
additive catalog; `[]` permits no grants but retains the full output enum.

Every permission granted by a configured role must be present in the matching
permission catalog. `forRoot()` infers literal permission unions and rejects
unknown role grants in TypeScript; runtime validation also protects dynamic and
asynchronous configuration. Each default, administrator, and creator role must
also exist in its corresponding role map. Invalid role configuration prevents
application startup.

Users, workspace members, and invitations store role names as `string[]`, so a
subject may receive permissions from multiple configured roles. Permission
properties are also `string[]`. Role assignment methods validate names against
the configured role map, while the module options keep the configured catalogs
typed without coupling the GraphQL or database schema to literal unions.
Direct user, member, and API-key permission writes are also validated
against these catalogs at runtime.

`apiKey.defaultPermissions` defaults to an empty list.
`apiKey.allowedPermissions` defaults to the combined user and workspace
permission catalogs. Both lists are validated at startup, and defaults must be
a subset of the allowlist. A User Key may use entries from either catalog; a
Workspace Key may use only workspace permissions and cannot send invitations.
Shared defaults therefore cannot include `invitation:create`; invalid defaults
are rejected at startup. These settings are additional
limits: issuer permissions and the authenticating API Key's own permissions are
still enforced during creation and update.

## Environment Variables

Options passed to `forRoot()` or `forRootAsync()` are merged with environment
defaults. Provider-specific environment flags can override the matching nested
provider settings.

### Common

| Variable               | Purpose                                                                                                         | Default                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `AUTH_SECRET`          | Secret used to sign and encrypt auth data. Falls back to `APP_SECRET`; use at least 32 high-entropy characters. | Required                             |
| `HASH_SECRET`          | Pepper used by `HashModule`. Falls back to `APP_SECRET`; use at least 32 high-entropy characters.               | Required when `APP_SECRET` is unset  |
| `APP_SECRET`           | Shared fallback when an auth- or hash-specific secret is absent.                                                | Required when `AUTH_SECRET` is unset |
| `APP_NAME`             | Application name passed to Better Auth.                                                                         | unset                                |
| `AUTH_URL`             | Public authentication base URL. Falls back to `APP_URL`.                                                        | unset                                |
| `APP_URL`              | Public application URL and fallback for `AUTH_URL`.                                                             | unset                                |
| `AUTH_DISABLE_SIGN_UP` | Disables new signup for every configured authentication method without disabling sign-in.                       | signup enabled                       |
| `API_KEY_PREFIX`       | Prefix used when creating API keys; 1–32 lowercase ASCII letters or digits, starting with a letter.             | `sk`                                 |

### Email

| Variable                          | Purpose                                               | Default        |
| --------------------------------- | ----------------------------------------------------- | -------------- |
| `AUTH_EMAIL_ENABLED`              | Enables email/password auth unless set to `false`.    | enabled        |
| `AUTH_EMAIL_REQUIRE_VERIFICATION` | Requires verified email unless set to `false`.        | required       |
| `AUTH_EMAIL_DISABLE_SIGN_UP`      | Blocks new email/password signups when set to `true`. | signup enabled |

### Google and GitHub

Google and GitHub remain disabled until their `*_ENABLED` flag is `true`.
Enabling either provider requires both its client ID and client secret.

| Variable                      | Purpose                                           |
| ----------------------------- | ------------------------------------------------- |
| `AUTH_GOOGLE_ENABLED`         | Enables Google authentication.                    |
| `AUTH_GOOGLE_CLIENT_ID`       | Google OAuth client ID.                           |
| `AUTH_GOOGLE_CLIENT_SECRET`   | Google OAuth client secret.                       |
| `AUTH_GOOGLE_DISABLE_SIGN_UP` | Blocks new Google users while preserving sign-in. |
| `AUTH_GITHUB_ENABLED`         | Enables GitHub authentication.                    |
| `AUTH_GITHUB_CLIENT_ID`       | GitHub OAuth client ID.                           |
| `AUTH_GITHUB_CLIENT_SECRET`   | GitHub OAuth client secret.                       |
| `AUTH_GITHUB_DISABLE_SIGN_UP` | Blocks new GitHub users while preserving sign-in. |

### Authentication Providers

Every provider is a flat object identified by `id`. An ID recognized by Better
Auth, such as `github`, uses its built-in social-provider implementation. Other
IDs use Generic OAuth. Each ID must be unique across `providers` and the
environment-configured `oidc` provider.

```typescript
AuthModule.forRoot({
  // ...entities and other options
  providers: [
    {
      id: "github",
      clientId: process.env.GITHUB_CLIENT_ID!,
      clientSecret: process.env.GITHUB_CLIENT_SECRET!,
    },
    {
      id: "company",
      name: "Company SSO",
      clientId: process.env.COMPANY_OAUTH_CLIENT_ID!,
      clientSecret: process.env.COMPANY_OAUTH_CLIENT_SECRET!,
      discoveryUrl:
        "https://accounts.example.com/.well-known/openid-configuration",
      scopes: ["openid", "profile", "email"],
    },
  ],
});
```

Providers with discovery metadata can use OpenID Connect. Plain OAuth providers
can configure `authorizationUrl`, `tokenUrl`, and `userInfoUrl` explicitly.
Advanced provider callbacks such as `getToken`, `getUserInfo`, and
`mapProfileToUser` are also supported. Generic providers use the same
`AuthService.signInSocial()`, `AuthService.linkCurrentUserAccount()`, and callback
routes as built-in social providers. `AUTH_DISABLE_SIGN_UP=true` overrides every
provider's signup setting.

OAuth state Cookie validation remains enabled by default for every provider.
Do not set `account.skipStateCookieCheck` unless an exceptional deployment
cannot preserve the signed state Cookie across the authorization redirect and
the resulting login CSRF trade-off has been explicitly accepted.

### OIDC

For a single conventional OIDC provider, the following environment variables
are a concise alternative to a `providers` entry. The provider remains disabled
until `AUTH_OIDC_ENABLED=true`; when enabled, its ID is `oidc`.

| Variable                    | Purpose                                                                                                                | Default                |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `AUTH_OIDC_ENABLED`         | Enables the generic OIDC provider.                                                                                     | disabled               |
| `AUTH_OIDC_CLIENT_ID`       | OIDC client ID.                                                                                                        | Required when enabled  |
| `AUTH_OIDC_CLIENT_SECRET`   | OIDC client secret.                                                                                                    | Required when enabled  |
| `AUTH_OIDC_DISCOVERY_URL`   | OIDC discovery document URL.                                                                                           | Required when enabled  |
| `AUTH_OIDC_PROMPT`          | Optional prompt: `none`, `login`, `create`, `consent`, `select_account`, `select_account consent`, or `login consent`. | unset                  |
| `AUTH_OIDC_SCOPES`          | Comma-separated scopes; whitespace and empty entries are ignored.                                                      | `openid,profile,email` |
| `AUTH_OIDC_DISABLE_SIGN_UP` | Blocks new OIDC users while preserving sign-in.                                                                        | signup enabled         |

## Entity Setup

Auth owns the concrete `User`, `Account`, `Session`, `Verification`,
`Workspace`, `Member`, `Invitation`, `UserApiKey`, and `WorkspaceApiKey` entities, their GraphQL
metadata, relations, RLS policies, and connections. There are no public auth
`Base*` classes or `AuthModuleOptions.entities` overrides.

Register the exported `entities` array in both your runtime MikroORM configuration
and the configuration loaded by the migration CLI. The CLI does not initialize Nest:

```typescript
import { entities as authEntities } from "@nest-boot/auth";
import { defineConfig } from "@mikro-orm/postgresql";

export default defineConfig({
  entities: [...authEntities, "dist/**/*.entity.js"],
  entitiesTs: [...authEntities, "src/**/*.entity.ts"],
  // Connection and migration options...
});
```

Use separate related business entities and additional field resolvers to extend
these models. Import the built-in classes directly for relation targets; do not
redeclare or register replacement auth entities. Role/permission catalogs, ability
builders, delivery callbacks, and provider settings remain configurable.

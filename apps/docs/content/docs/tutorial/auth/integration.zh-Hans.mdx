底层 Better Auth 实例及其注入 token 属于内部实现。应用应注入负责对应领域的服务：

| 服务                | 职责                                                   |
| ------------------- | ------------------------------------------------------ |
| `AuthService`       | 身份认证、邮箱验证、密码找回、用户资料与 provider 账号 |
| `SessionService`    | 会话解析、按用户分页、模拟登录者关联、自助与管理员撤销 |
| `UserService`       | 用户管理、权限、封禁、模拟登录和密码                   |
| `AccountService`    | 当前用户会话的安全账号连接查询                         |
| `WorkspaceService`  | 工作区查询与生命周期管理                               |
| `MemberService`     | 成员查询、分页、资料、角色、权限及加入/退出            |
| `InvitationService` | 邀请查询、分页、创建、接受、拒绝及取消                 |
| `ApiKeyService`     | 个人与工作区 API Key 生命周期和校验                    |

`UserService`、`AccountService`、`WorkspaceService`、`MemberService` 和 `InvitationService` 直接操作 `AuthModule` 内置的 MikroORM 实体，
不依赖 Better Auth 的 admin 或 organization 插件。

```typescript
@Injectable()
export class AccountApplicationService {
  constructor(
    private readonly authService: AuthService,
    private readonly sessionService: SessionService,
    private readonly userService: UserService,
    private readonly accountService: AccountService,
    private readonly workspaceService: WorkspaceService,
    private readonly memberService: MemberService,
    private readonly invitationService: InvitationService,
    private readonly apiKeyService: ApiKeyService,
  ) {}
}
```

## 内置实体与 GraphQL

`AuthModule` 统一注册认证 Service 和全部标准 Resolver，不再导入 `AuthGraphQLModule`。
实体、输入、Payload 和连接都从 `@nest-boot/auth` 导入，Resolver 使用具体类回调。
应用只需配置 GraphQL 模块和 `AuthModule.forRoot()`，无需重新定义认证实体或注册命名连接。

Auth 内置 `User`、`Account`、`Session`、`Verification`、`Workspace`、
`Member`、`Invitation` 和 `ApiKey` 具体实体，以及 GraphQL 元数据、关联、RLS 策略和连接。
不再提供认证 `Base*` 类或 `AuthModuleOptions.entities` 替换配置。

在运行时和迁移 CLI 的 MikroORM 配置中注册导出的 `entities` 数组；CLI 不会启动 Nest 模块：

```typescript
import { entities as authEntities } from "@nest-boot/auth";
import { defineConfig } from "@mikro-orm/postgresql";

export default defineConfig({
  entities: [...authEntities, "dist/**/*.entity.js"],
  entitiesTs: [...authEntities, "src/**/*.entity.ts"],
  // Connection and migration options...
});
```

自定义字段请使用独立的业务关联实体和额外的字段 Resolver。关联目标直接导入内置实体类，
不要重新声明或注册同名认证实体。角色、权限目录、Ability 构造器、邮件回调和 Provider 配置仍可自定义。

## 传输适配器

Resolver 与 Controller 将参数交给领域 Service，授权、作用域和 RLS 检查仍由 Service 和数据库执行。
认证操作通过请求级 cookies 存储转发全部 Set-Cookie 响应。
`AuthMiddleware` 在 `RequestContextMiddleware` 之后执行，使用内置实体类保存身份，
例如 `RequestContext.get(User)`。不再注册认证 Base 类别名；传输层优先使用当前身份装饰器。

`Member` / `Invitation` 对应的 Service 是 `MemberService` / `InvitationService`，
权限主体仍为 `member:*` / `invitation:*`。所有已有字段、参数和授权行为保持不变。

## PostgreSQL RLS

MikroORM 7.2 原生 RLS 使用请求 EntityManager 的 session 上下文。Auth 在解析身份后
更新该上下文；经过服务授权的持久化操作在必要时使用隔离且不带 session 的 fork。
示例通过 `createSessionContext` 配置 `session`，无需自定义 RLS 驱动或拦截器。
参见 [MikroORM 教程](/docs/tutorial/mikro-orm)。

## 应用启动

```typescript
import { Logger } from "@nest-boot/logger";
import { ZodValidationPipe } from "@nest-boot/validator";
import { NestFactory } from "@nestjs/core";

async function bootstrap() {
  const app = await NestFactory.create(AppModule, {
    bufferLogs: true,
    cors: true,
  });

  app.useLogger(await app.resolve(Logger));
  app.useGlobalPipes(new ZodValidationPipe());
  app.enableShutdownHooks();

  await app.listen(process.env.PORT ?? 4000);
}

void bootstrap();
```

## 运行建议

Auth 输入已从 class-validator 切换为 Zod。业务 DTO 迁移完成后，请移除旧的全局
`ValidationPipe`。Zod 返回普通解析对象并移除未声明的属性，不创建 DTO 类实例。
GraphQL 验证错误使用 `BAD_USER_INPUT`，字段详情位于
`extensions.validationErrors`。

`banUser` 和 `deleteCurrentUser` 仍允许省略 `input`（默认 `{}`），但拒绝显式
`input: null`。属性的 `.optional()` 允许省略，`.nullish()` 额外允许 `null`，
参见 [Validator 教程](/docs/tutorial/validator)。直接调用 Service 不会自动执行管道。

- 将 `AuthGuard` 作为 `APP_GUARD` 注册一次，并使用 `@Public()` 标记例外；
- 传输层使用当前身份装饰器，不直接依赖上下文 token；
- 把高熵 `AUTH_SECRET` 与 `HASH_SECRET` 保存在源码仓库之外；
- 通过路由、请求头或 Cookie 显式选择工作区；
- `AuthModule` 提供标准 GraphQL schema；应用可添加自己的字段 Resolver。

具体符号文档请参阅 [Auth API 参考](/docs/api/auth)与

## 其他 GraphQL 原生接口

`AuthModule` 内置 `Account`、`AccountConnection`、`UserConnection`、`SessionConnection` 及对应连接参数，全部直接引用类。
`users(first: 20)` 返回连接；使用 `currentUser { sessions(first: 20) { edges { node { id } } } accounts(first: 20) { edges { node { id providerId } } } }` 查询本人会话和账号。读取别人的会话需管理员权限，API Key 调用还需对应授权。

登录与注册结果引用内置 `User`，不再使用 `AuthUserType`。签发会话后会更新请求身份、工作区成员、RLS 和能力上下文，再解析关联字段；未签发会话的注册不会授予认证身份。

部署前执行示例基线 `Initial → generated schema migrations`：启用 Session／Account RLS 和统一默认表权限，不再保留数据库列级限制。Service 与 GraphQL 排除密码、token 和 API Key 哈希；会话管理员读取策略使用服务端计算的请求权限。

### 操作命名调整

使用 `currentSession`、
`createWorkspaceApiKey`、`updateWorkspaceApiKey`、`deleteWorkspaceApiKey`。
旧名称不保留别名；删除工作区只使用 `deleteWorkspace`，`removeWorkspace` 已移除。
客户端需同步更新 GraphQL 文档、返回字段访问与生成类型。

默认 GraphQL 模块已移除 `authFetchAccessToken`、`authFetchAccountInfo`、
`authRefreshToken` 及其专用输入、返回类型，不保留别名。账号绑定信息通过
`currentUser { accounts(first: 20) { edges { node { id providerId scopes } } } }` 查询；服务端第三方集成仍可使用
`AuthService.getAccessToken()`、`refreshToken()` 和 `getAccountInfo()`。

## 全局守卫

将已配置模块的 `AuthGuard` 注册为全局守卫。它接受有效的 Cookie Session 或 API Key，
并使用同一个守卫检查路由权限。

```typescript
import { AuthGuard } from "@nest-boot/auth";
import { APP_GUARD } from "@nestjs/core";

@Global()
@Module({
  imports: [AuthDynamicModule],
  providers: [{ provide: APP_GUARD, useExisting: AuthGuard }],
})
export class CommonModule {}
```

不需要认证的路由使用 `@Public()`。如果公开路由同时声明权限装饰器，权限检查仍会执行。

```typescript
@Public()
@Query(() => String)
health(): string {
  return "ok";
}
```

## 构建 Ability

分别配置用户与工作区 Ability。对于已认证请求，即使处理器没有权限装饰器，
`AuthGuard` 也会准备两套 Ability。每个回调在一次请求中最多执行一次，结果会缓存在
`RequestContext` 中。返回 `null` 会使对应权限域的检查失败。

```typescript
import { AuthModule, PermissionAbilityBuilder } from "@nest-boot/auth";
import { RequestContext } from "@nest-boot/request-context";

const userRoles = {
  admin: ["project:create"],
  user: [],
} as const;
const userPermissions = ["project:create", "project:archive"] as const;

const workspaceRoles = {
  owner: ["project:create", "project:delete"],
  member: ["project:create"],
} as const;
const workspacePermissions = [
  "project:create",
  "project:delete",
  "project:archive",
] as const;

AuthModule.forRoot({
  // ...
  workspace: {
    permissions: workspacePermissions,
    roles: workspaceRoles,
    buildAbility: (_context, permissions) => {
      const { can, build } = new PermissionAbilityBuilder();
      for (const permission of permissions) {
        const [subject, action] = permission.split(":");
        if (subject === "post" && action) can(action, Post);
      }
      return build();
    },
  },
  user: {
    permissions: userPermissions,
    roles: userRoles,
    buildAbility: () => {
      const user = RequestContext.get(User);
      if (!user) return null;

      const { can, build } = new PermissionAbilityBuilder();
      can("read", Post);
      can("update", Post, { authorId: user.id });
      return build();
    },
  },
});
```

每个作用域分别维护权限目录、角色注册表和 Ability 构建器。角色授予的每项权限都
必须存在于对应作用域的 `permissions` 数组中，否则应用会启动失败。AuthModule 会先
解析角色权限与实体直接权限，构建器的第二个参数只接收去重后的最终权限列表。

## 管理角色

权限目录和角色定义来自 `user.permissions`、`user.roles`、
`workspace.permissions` 与 `workspace.roles`，不使用独立的角色服务保存或管理。
`UserService` 与 `WorkspaceService` 负责向传输层提供配置目录并校验角色赋值。

```typescript
const userRoles = userService.listRoles();
const userPermissions = userService.listPermissions();
await userService.setRole(user, ["admin", "auditor"]);

const workspaceRoles = workspaceService.listRoles();
const workspacePermissions = workspaceService.listPermissions();
await workspaceService.updateMemberRole(member, ["admin"]);
```

`setRole()` 与 `updateMemberRole()` 会拒绝空角色列表和不存在的角色。
`updateMemberRole()` 不能修改当前创建者或赋予配置的创建者角色；此类变更应使用
`transferOwnership()`。所有权转移会把 `workspace.creatorRole` 赋给下一位所有者，并将
原所有者降级为 `workspace.defaultRole`。

`user.defaultRole` 与 `workspace.defaultRole` 分别为新用户和新成员提供默认角色；
`workspace.creatorRole` 标识所有权角色；`user.adminRoles` 可以包含多个角色，并由
`UserService.isAdmin()` 用于识别管理员用户。所有配置的生命周期角色都会在启动时依据
对应角色映射进行校验。

`getUserPermissions()` 与 `getMemberPermissions()` 返回所有角色继承权限和实体直接权限
去重后的合集；`hasPermission()` 使用同一份结果进行判断。
`createUser()`、`addMember()`、`setUserPermissions()` 与
`setMemberPermissions()` 会拒绝格式错误、重复或不在配置目录中的直接权限，避免将未知
权限写入实体。

示例 GraphQL 应用提供 `userRoles`、`userPermissions`、`workspaceRoles` 与
`workspacePermissions` 查询。角色修改分别使用 `setUserRoles` 和
`updateWorkspaceMemberRole` mutation；工作区成员的直接权限使用
`setWorkspaceMemberPermissions`，普通成员资料更新不再接受授权字段。

## 保护路由

工作区权限使用 `@WorkspaceCan`，个人或应用级权限使用 `@UserCan`。两者写入独立
元数据，并由同一个 `AuthGuard` 执行。

```typescript
@WorkspaceCan("read", Post)
@Query(() => [Post])
posts() {
  return this.postService.findAll();
}

@UserCan("read", User)
@Query(() => User)
me(@CurrentUser() user: User) {
  return user;
}
```

同一路由同时声明两个装饰器时，两项权限都必须通过。`@Can` 是按 `scope` 转发的
薄别名；省略 `scope` 时转发给 `@WorkspaceCan`。

```typescript
@Can("read", Post) // @WorkspaceCan("read", Post)
@Can("read", User, { scope: "user" }) // @UserCan("read", User)
```

权限取决于具体对象时，使用 subject factory。factory 的第一个参数是 Controller 或
Resolver 实例，后续参数是被装饰方法的参数。

```typescript
@WorkspaceCan("update", (self: PostResolver, id: string) =>
  self.postService.findOneOrFail({ id }),
)
@Mutation(() => Post)
updatePost(@Args("id") id: string) {
  return this.postService.update(id);
}
```

Workspace API Key 只能通过工作区权限检查。User API Key 可以通过用户权限检查，并在
具有有效成员身份时通过工作区权限检查。API Key 权限会与相应 Ability 取交集，`read`
操作也不例外。

## Service 授权边界

`UserService`、`WorkspaceService` 与 `ApiKeyService` 会在读取或修改认证数据前强制校验
权限。Resolver 和 Controller 上的装饰器用于提前拒绝并声明接口意图，但不是安全边界；
即使遗漏装饰器，受保护的 Service 操作也不会变成公开操作。

Service 权限划分与 Better Auth 的 admin、organization 访问控制保持一致：

- 用户管理使用 `user:*` 与 `session:*` 权限；
- 工作区变更使用 `workspace:*`、`workspaceMember:*` 与
  `workspaceInvitation:*` 权限；
- 工作区 API Key 管理使用 `apiKey:create/read/update/delete`；
- 当前用户认证、会话管理、接受邀请和退出工作区使用已认证身份与资源归属校验。

应用 Service 可以注入 `AuthorizationService`，使用 `assertUserCan()` 与
`assertWorkspaceCan()` 建立同样的默认拒绝边界。Ability 必须由全局 `AuthGuard` 在当前
请求生命周期准备；生命周期外的调用不会被隐式信任。

## 底层权限检查

`AuthGuard` 准备好当前请求的 Ability 后，底层代码可以使用对应的作用域辅助函数。
`can()` 是按 `scope` 转发的薄别名，默认转发到 `workspaceCan()`。

```typescript
if (!workspaceCan("update", post)) {
  throw new ForbiddenException();
}

userCan("read", user);
getWorkspaceAbility();
getUserAbility();

can("read", post); // workspaceCan(...)
can("read", user, { scope: "user" }); // userCan(...)
```

请求生命周期没有准备对应 Ability 时，`userCan()` 与 `workspaceCan()` 会按默认拒绝
返回 `false`；更底层的 `getUserAbility()` 与 `getWorkspaceAbility()` 则会抛出
`ForbiddenException`。

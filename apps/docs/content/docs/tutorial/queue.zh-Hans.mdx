`@nest-boot/queue` 直接基于 [BullMQ](https://docs.bullmq.io/) 集成 Nest。队列类是可注入的 provider，消费者引用同一个队列类，不再依赖 `@nestjs/bullmq`。

## 安装

```bash
pnpm add @nest-boot/queue @nest-boot/request-context bullmq
```

## 定义与注入队列

`@Queue()` 默认将类名转换为 kebab-case 作为队列名称，例如 `EmailQueue` 转为 `email-queue`。可直接向装饰器传入队列配置，并通过可选的 `name` 覆盖名称。

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";

export interface EmailData {
  to: string;
  subject: string;
}

@Queue({
  defaultJobOptions: { attempts: 3, removeOnComplete: { age: 3600 } },
})
export class EmailQueue extends BaseQueue<EmailData> {}
```

把队列类加入 `providers`，直接通过构造函数注入。在应用模块树的任意一个模块中导入一次 `QueueModule` 即可，例如 `CommonModule`、`JobsModule` 或下面的业务模块，不要求放在 `AppModule`。可以直接导入，或使用 `forRoot()` / `forRootAsync()` 配置。其 provider 为全局服务，其他模块和 `ScheduleModule` 直接复用，无需重复导入。应用仍需这次导入，以提供配置、发现消费者并管理 worker：

```ts
import { QueueModule } from "@nest-boot/queue";
import { Injectable, Module } from "@nestjs/common";
import { EmailQueue, type EmailData } from "./email.queue";

@Injectable()
export class EmailService {
  constructor(private readonly queue: EmailQueue) {}

  async send(data: EmailData) {
    return await this.queue.add("send", data);
  }
}

@Module({
  imports: [QueueModule],
  providers: [EmailQueue, EmailService],
  exports: [EmailQueue],
})
export class EmailModule {}
```

不需要 `registerQueue()` 或 `@InjectQueue()`。`QueueModule` 自动读取 `QUEUE_DATABASE_URL` / `DATABASE_URL`；通过 `forRoot()` / `forRootAsync()` 可以指定连接和共享默认配置，全局配置只定义一份。队列类继承 BullMQ 的方法，也可以添加业务方法。

队列 provider 必须保持单例，队列名称在应用内必须唯一。需要跨模块使用时，导出队列类并导入所属模块，不要重复创建实例。应用关闭时会关闭队列连接。

队列会自动取得全局配置。自定义构造函数只注入业务依赖，并调用 `super(localOptions)`；装饰器配置足够时，可完全省略构造函数。

## 消费任务

```ts
import { BaseProcessor, OnWorkerEvent, Processor } from "@nest-boot/queue";
import { Job } from "bullmq";
import { EmailQueue, type EmailData } from "./email.queue";
import { NotificationService } from "./notification.service";

@Processor(EmailQueue, { concurrency: 5 })
export class EmailProcessor extends BaseProcessor {
  constructor(private readonly notifications: NotificationService) {
    super();
  }

  async process(job: Job<EmailData>) {
    await this.notifications.send(job.data);
  }

  @OnWorkerEvent("completed")
  onCompleted(job: Job<EmailData>) {
    console.log(`Completed ${job.id}`);
  }
}
```

将 `EmailProcessor` 与 `EmailQueue` 都注册为 provider，或者导入导出队列的模块。纯消费者部署也必须注册队列类。注册只创建客户端，不会自动入队；缺少队列 provider 时会在启动任何 worker 前报错。消费者的PostgreSQL 连接和 telemetry 都来自队列实例，worker 配置不能指向不同的数据库或 schema。使用 `BaseProcessor` 替代已移除的 `WorkerHost` 导出。

### Scope 与 RequestContext

每次任务执行都创建独立的 `RequestContext`，类型为 `"queue"`，并绑定 `JOB_REF`。上下文及其中间件会在 Nest **解析消费者依赖之前**建立。`process()` 的错误继续交给 BullMQ 重试。

支持单例、REQUEST 和 TRANSIENT 消费者。注入 request-scoped 服务时，作用域会沿依赖链传递；框架会通过 `ContextIdFactory.getByRequest()` 和消费者所属模块的 `ModuleRef.resolve()` 为任务解析实例，也支持应用定义的 durable context 策略。

导入 `RequestContextModule` 后可以直接注入 `RequestContext`。该 provider 使用 REQUEST 作用域，返回当前已有的上下文，因此注入它也会让消费者变为 request-scoped：

```ts
import {
  BaseProcessor,
  JOB_REF,
  Processor,
  QueueModule,
} from "@nest-boot/queue";
import {
  RequestContext,
  RequestContextModule,
} from "@nest-boot/request-context";
import { Inject, Module } from "@nestjs/common";
import { Job } from "bullmq";
import { EmailQueue, type EmailData } from "./email.queue";

@Processor(EmailQueue)
export class EmailProcessor extends BaseProcessor {
  constructor(
    private readonly context: RequestContext,
    @Inject(JOB_REF) private readonly job: Job<EmailData>,
  ) {
    super();
  }

  async process() {
    return { contextId: this.context.id, recipient: this.job.data.to };
  }
}

@Module({
  imports: [QueueModule, RequestContextModule],
  providers: [EmailQueue, EmailProcessor],
})
export class EmailWorkerModule {}
```

单例服务可以继续在方法中使用 `RequestContext.current()` 或 `RequestContext.get(JOB_REF)`，不要在单例构造函数中捕获任务上下文。durable 依赖只适合有意共享的状态，不能保存当前任务数据。`worker` getter 可在模块初始化后及 scoped 消费者的 `process()` 中使用。

## 动态队列配置

在队列构造函数中注入配置服务，只向 `super()` 传递当前队列的配置。BaseQueue 按全局配置、装饰器配置、构造函数配置的顺序合并，后者优先且不修改原始对象。`@Queue()` 自动提供全局配置，继承构造函数时也一样。

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";
import { Module } from "@nestjs/common";
import { ConfigModule, ConfigService } from "@nestjs/config";

@Queue()
export class EmailQueue extends BaseQueue {
  constructor(config: ConfigService) {
    super({
      defaultJobOptions: {
        attempts: config.get<number>("EMAIL_JOB_ATTEMPTS", 3),
      },
    });
  }
}

@Module({
  imports: [ConfigModule],
  providers: [EmailQueue],
  exports: [EmailQueue],
})
export class EmailModule {}
```

应用统一注册一次全局 `QueueModule`。共享配置需要异步加载时，使用 `QueueModule.forRootAsync()`。单个队列需要异步配置时，通过 `useFactory: async ...` 注册其依赖的配置 provider，Nest 会等待该 provider 就绪后再构造队列。

队列实例由 Nest 创建，以自动提供全局配置和业务依赖。需要自定义 factory provider 时，注入 `ModuleRef` 并返回 `moduleRef.create(EmailQueue)`。将队列类注册为 provider，无需自行 `new` 实例。

## 队列事件

`@OnWorkerEvent()` 监听本地 worker。显式监听 PostgreSQL 队列事件时使用独立的单例 `QueueEventsHost`：

```ts
import {
  OnQueueEvent,
  QueueEventsHost,
  QueueEventsListener,
} from "@nest-boot/queue";
import { RequestContext } from "@nest-boot/request-context";
import { EmailQueue } from "./email.queue";

@QueueEventsListener(EmailQueue)
export class EmailEvents extends QueueEventsHost {
  @OnQueueEvent("completed")
  completed(event: { jobId: string }) {
    console.log(event.jobId, RequestContext.id);
  }
}
```

将 `EmailEvents` 及其队列注册为 provider。Worker 事件仅绑定单例消费者，scoped 消费者的事件方法会被跳过；QueueEvents listener 必须是单例。任务查询直接读取原生表，无需事件监听器。

每个事件回调都有独立上下文并运行上下文中间件。携带 Job 的 worker 事件绑定 `JOB_REF`；`stalled` 只有任务 ID。QueueEvents 使用 payload 中的 `jobId`，不绑定 `JOB_REF`。其他事件生成上下文 ID。事件处理器及中间件的错误会记录并抑制，因为 BullMQ 不等待异步监听器。直接调用 `.on()` 时，需要自行处理上下文及异步错误。

## PostgreSQL 存储与迁移

所有队列使用 BullMQ 6 官方 PostgreSQL 后端。优先读取 `QUEUE_DATABASE_URL`，其次使用 `DATABASE_URL`；都未设置时使用 node-postgres 默认连接参数。显式 `connection` 支持 PostgreSQL 配置、URL 或调用方管理的连接池。自定义 schema 请传配置对象中的 `schema`；默认是 `bullmq`，不再使用 Redis prefix。

启动生产者、消费者或查询服务之前，执行 BullMQ 官方迁移。队列表、函数、索引和迁移记录均由它管理：

```ts
import { runMigrations } from "bullmq";
import { Client } from "pg";

const client = new Client({ connectionString: process.env.DATABASE_URL });
await client.connect();
try {
  await runMigrations(client); // 第二个参数可指定自定义 schema。
} finally {
  await client.end();
}
```

迁移需要独占一个连接，不能通过 `pool.query()` 在多个会话间切换。也可显式配置 `connection: { connectionString, migrate: true }`；Nest Boot 默认不会自动执行迁移。连接同一个数据库并不意味着入队和业务写入自动处于同一个事务。

传入调用方管理的 `pg.Pool` 时，需要提前设置正确的 `search_path`（如 `options: "-c search_path=bullmq,public"`），并在队列和 worker 停止后自行关闭连接池。自定义 `schema` 使用配置对象，不直接传裸 Pool。

## 可选 MikroORM 与 GraphQL 查询

PostgreSQL 后端本身负责持久化，`add()` 和 `addBulk()` 完成后原生任务立即可查。不再维护事件同步表、持久化开关、同步监听器或额外清理定时器。任务保留时间通过 BullMQ 的 `removeOnComplete` / `removeOnFail` 设置，`age` 单位为秒。任务被移除后，ORM 和 GraphQL 也查询不到。重复使用仍存在的 job ID 会保留原任务；确实需要复用 ID 时先移除旧任务。

| 应用配置                       | 行为                                         |
| ------------------------------ | -------------------------------------------- |
| 仅 QueueModule                 | PostgreSQL 队列和消费者，无需 ORM 或 GraphQL |
| DatabaseModule 和内置 Job 实体 | 同时提供只读 JobService                      |
| 再注册 GraphQLModule           | 暴露 job(id) 和 jobs，除非 graphql 为 false  |

队列默认 `expose: false`。只有在 API 应用中注册并显式声明 `@Queue({ expose: true })` 的队列，才参与 JobService 和 GraphQL 查询，包括单条任务、筛选、分页和数量统计。可见队列范围始终与 `getJobReadFilter` 取交集，客户端筛选不能绕过它。Schedule 等内部队列默认隐藏。此设置不影响 BullMQ 持久化或直接操作队列。

生产者、消费者与 API 分开部署时，API 应用也需要在 `providers` 中注册要开放的队列类；Processor 只需在消费者应用中注册。`expose` 是应用配置，不是 BullMQ 任务表字段。`QueueModule.graphql` 单独控制是否注册 GraphQL 接口。

`@nest-boot/database`、`@nest-boot/graphql` 和 `@nest-boot/graphql-connection` 仍为可选对等依赖，按功能安装各自所需的依赖。仅安装包不会启用功能。只查询单个实体可以不安装 GraphQL；连接分页查询需要 GraphQL 相关依赖。

```ts
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { DatabaseModule } from "@nest-boot/database";
import { GraphQLModule } from "@nest-boot/graphql";
import { BaseQueue, Queue, QueueModule } from "@nest-boot/queue";
import { entities, getJobSchemaOptions } from "@nest-boot/queue/persistence";
import { Module } from "@nestjs/common";

@Queue({ expose: true })
export class ReportsQueue extends BaseQueue {}

@Module({
  imports: [
    DatabaseModule.forRoot({
      driver: PostgreSqlDriver,
      entities,
      ...getJobSchemaOptions(),
    }),
    GraphQLModule,
    QueueModule.forRoot({
      graphql: true,
      // 根据可信请求身份返回 MikroORM 筛选条件，null 表示拒绝访问。
      getJobReadFilter: () => null,
    }),
  ],
  providers: [ReportsQueue],
})
export class JobsModule {}
```

运行时和 MikroORM CLI 配置都加入相同实体及 `...getJobSchemaOptions()`。Job 完整映射原生字段、默认值、PostgreSQL 枚举和 BullMQ 的 7 个运行索引，并声明 `(queue, data->>'userId')`、`(queue, data->>'workspaceId')` 两个归属索引。先执行 BullMQ 迁移，再生成并执行应用迁移：首次 Job 差异添加这两个索引，并启用 RLS、创建 authenticated 的 SELECT 策略。应用迁移前先创建 `authenticated` 数据库角色，此后再次比较为空。

导出的 `entities` 数组完整映射 BullMQ 的 11 张表，包含迁移记录、任务日志、依赖、事件、元数据、指标、限流、去重和调度器。与 Auth 模块一样，每张表对应独立的只读实体文件；只有 Job 提供 GraphQL API。MikroORM 原生 schema generator 比较字段、默认值、枚举、外键和索引，不再安装自定义生成器。原生 schema、函数及独立序列仍由 BullMQ 官方迁移创建和升级。`readonly` 只关闭 flush 变更追踪，不影响迁移生成，也不阻止显式原生写入；所有任务修改继续调用 BullMQ。

`getJobSchemaOptions()` 使用原生 `schemaGenerator.ignoreRoutines: true` 并设置实体 schema。该选项作用于**所有 schema**：已有业务函数的修改也需要显式迁移。保留 MikroORM 默认的迁移快照，在执行 BullMQ 和应用迁移后更新快照，再生成后续迁移。MikroORM 7.2.0 直接从在线数据库生成 `down` 时，可能带入被忽略的函数定义；应检查这些 SQL，不将 BullMQ 函数放入应用回滚。示例保留完整表快照，索引和 RLS 使用独立迁移，回滚均不修改 BullMQ 函数。升级 BullMQ 后应检查 schema 差异，再接受生成的迁移。

自定义 schema（如 `tasks`）时，两处 ORM 配置均使用 `getJobSchemaOptions("tasks")`，设置 `QueueModule.connection: { connectionString, schema: "tasks" }`，并执行 `runMigrations(client, "tasks")`。不要再将 Job 表或其 schema 加入 `skipTables` / `ignoreSchema`。直接 ORM 查询使用实体配置的 schema；JobService 使用根 Queue 连接配置中的 schema，默认 `bullmq`。ORM 必须连接根队列配置对应的同一个数据库。单个队列覆盖到其他数据库或 schema 时，不会被根 JobService 自动聚合。

| 实体字段                           | 原生映射                                                  |
| ---------------------------------- | --------------------------------------------------------- |
| queue                              | queue 列                                                  |
| jobId                              | id 列                                                     |
| id                                 | formula 计算 queue:jobId，不新增数据库列                  |
| status                             | 原生 state，并将有优先级的 waiting 任务表示为 prioritized |
| createdAt / startedAt / finishedAt | 毫秒时间戳转换为 Date                                     |

数据库保持 `(queue, id)` 复合主键，计算出的 API ID 用于跨队列唯一标识和游标排序。原生表没有最后更新时间，因此不提供 `updatedAt` 字段或筛选。GraphQL 只暴露 `id`、`queue`、`name`、`status`、`progress`、`createdAt`、`startedAt` 和 `finishedAt`。可空的 `progress: Float` 通过 resolver 只返回有限数值；JSON 对象、字符串、布尔值及非有限数值均返回 null。`jobId`、任务入参、原始结果、错误和运行参数不公开。业务结果由应用通过有明确类型和授权逻辑的字段或 API 提供。筛选和排序支持 `queue`、`name`、`status`、`created_at`。

每次读取都执行 `getJobReadFilter`，范围同时约束单条任务、筛选、分页和数量。未配置、返回 null 或 undefined 均拒绝访问；返回空对象表示服务层只限制已开放队列，数据库 RLS 仍然生效。入队数据的身份必须来自可信应用上下文。Job 实体为 `authenticated` 声明 RLS SELECT 策略：`data.userId` 匹配 `app.user.id`，或 `data.workspaceId` 匹配 `app.workspace.id`。缺失或空身份不会匹配；服务账户无需用户身份即可读取所属工作区的任务。没有允许请求写入或匿名读取的策略。先创建该角色，再授予 schema usage 和 job 表 SELECT，示例迁移已包含这些配置。Auth 通过请求 EntityManager session 提供已验证身份；不使用 Auth 的应用也可自行设置相同的可信 session 变量。

BullMQ 生产者和 Worker 使用独立连接，以表所有者或具备 `BYPASSRLS` 的角色运行，才能处理所有租户及没有归属字段的后台任务。Job 启用 RLS，但不启用 `FORCE ROW LEVEL SECURITY`。请求查询必须切换到既非表所有者、也不绕过 RLS 的角色。RLS 只保护 Job；BullMQ 内部表不开放请求 API，也不应向请求角色授权。继续保留 `getJobReadFilter` 和队列开放范围来执行应用授权。

实体和 JobService 从 `@nest-boot/queue/persistence` 导入；JobConnectionService、GraphQL 类型和 Resolver 从 `@nest-boot/queue/graphql` 导入。JobConnectionService 继承 JobService，通过 `getJobConnection()` 提供使用同一授权范围的分页查询。这些入口同时隔离运行时和 TypeScript 声明中的可选依赖。需要数据库筛选类型检查时，可使用 `QueueModuleOptions<FilterQuery<Job>>`，从相应数据库入口导入筛选及实体类型。

### 迁移现有队列

此 API 保持 v8。移除 `@nest-boot/queue-database`、`QueueDatabaseModule`、旧同步实体和 Resolver、persistence/TTL 配置与 Redis prefix，改为注册队列类 provider，配置 PostgreSQL 并执行官方迁移；按需添加 ORM 排除配置和查询授权。旧 Redis 任务和同步表数据不会自动搬迁，切换部署前应单独排空或迁移。旧业务表的清理另行审核，以保留需要的历史数据。

## 最佳实践

1. **独立队列** — 为不同的任务类型使用独立队列（邮件、文件操作等），配置适当的并发数。

2. **任务 ID** — 使用确定性或 Sonyflake 的任务 ID 实现幂等性和可追踪性。

3. **结构化日志** — 在处理器中使用 `Logger.assign()` 将任务上下文附加到日志条目。

4. **自动清理** — 设置 `removeOnComplete` 和 `removeOnFail` 自动清理旧任务。

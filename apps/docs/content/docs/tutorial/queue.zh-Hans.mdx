---
title: "任务队列"
description: "基于 BullMQ 的分布式任务队列和后台工作器，支持 Redis 驱动处理和可选的 MikroORM 集成。"
---

`@nest-boot/queue` 模块封装 [`@nestjs/bullmq`](https://docs.nestjs.com/techniques/queues)，提供基于 Redis 支持的分布式任务处理。它也通过发现应用已注册的服务，整合任务持久化和 GraphQL 查询。

## 安装

```bash
pnpm add @nest-boot/queue @nest-boot/request-context @nestjs/bullmq bullmq
```

## 模块注册

在 `CommonModule` 中注册 `QueueModule` 配置 Redis 连接：

```typescript
import { QueueModule } from "@nest-boot/queue";
import { Module } from "@nestjs/common";

@Module({
  imports: [QueueModule],
})
export class AppModule {}
```

模块自动读取并解析 `REDIS_URL`。也可以通过 `QueueModule.forRoot()` 或 `forRootAsync()` 显式传入 BullMQ `connection`。

## 定义队列

在功能模块中注册命名队列：

```typescript
import { QueueModule } from "@nest-boot/queue";
import { Module } from "@nestjs/common";

@Module({
  imports: [
    QueueModule.registerQueue({
      name: "file-ops-queue",
      defaultJobOptions: {
        removeOnComplete: { age: 60 * 60 },
        removeOnFail: { age: 60 * 60 },
      },
    }),
  ],
  providers: [FileService, FileOpsProcessor],
})
export class FileModule {}
```

## 添加任务

使用 `@InjectQueue()` 注入 `Queue` 来添加任务：

```typescript
import { InjectQueue } from "@nest-boot/queue";
import { Injectable } from "@nestjs/common";
import { Queue } from "bullmq";

interface EmailJobData {
  to: string;
  subject: string;
  body: string;
}

@Injectable()
export class EmailService {
  constructor(
    @InjectQueue("email-queue")
    private readonly emailQueue: Queue<EmailJobData>,
  ) {}

  async sendEmail(data: EmailJobData): Promise<string> {
    const job = await this.emailQueue.add("send", data, {
      jobId: `email-${Date.now()}`,
    });

    return job.id!;
  }
}
```

## 处理任务

使用 `@Processor()` 装饰器继承 `WorkerHost` 创建处理器：

```typescript
import { OnWorkerEvent, Processor, WorkerHost } from "@nest-boot/queue";
import { Logger } from "@nest-boot/logger";
import { Job } from "bullmq";
import { NotificationService } from "./notification.service";

@Processor("email-queue", { concurrency: 5 })
export class EmailProcessor extends WorkerHost {
  constructor(
    private readonly logger: Logger,
    private readonly notificationService: NotificationService,
  ) {
    super();
    this.logger.setContext(EmailProcessor.name);
  }

  async process(job: Job<EmailJobData>): Promise<void> {
    const { to, subject, body } = job.data;

    this.logger.assign({ jobId: job.id, to });
    this.logger.log("Processing email job");

    await this.notificationService.sendEmail({ to, subject, body });

    this.logger.log("Email sent successfully");
  }

  @OnWorkerEvent("completed")
  onCompleted(job: Job<EmailJobData>): void {
    this.logger.log(`Email job ${job.id} completed`);
  }
}
```

Nest Boot 的 `@Processor()` 会为每个任务创建 `RequestContext`、写入 BullMQ `JOB_REF`，再调用正常的 `@nestjs/bullmq` processor。

## 队列事件

从 `@nest-boot/queue` 导入 `OnWorkerEvent` 和 `OnQueueEvent`，即可为每次事件回调创建独立的 `RequestContext`，并执行已注册的上下文中间件。即使事件在另一个上下文中触发，也不会继承其中的 EntityManager 或其他上下文数据。

`@OnWorkerEvent()` 放在 `@Processor()` 标记的 `WorkerHost` 中，监听当前 worker 的事件，例如上面示例中的 `onCompleted()`。`@OnQueueEvent()` 则放在独立的 `QueueEventsHost` 中，监听整个队列的事件：

```typescript
import {
  QueueModule,
  OnQueueEvent,
  QueueEventsHost,
  QueueEventsListener,
} from "@nest-boot/queue";
import { RequestContext } from "@nest-boot/request-context";
import { Logger, Module } from "@nestjs/common";

@QueueEventsListener("email-queue")
export class EmailQueueEvents extends QueueEventsHost {
  private readonly logger = new Logger(EmailQueueEvents.name);

  @OnQueueEvent("completed")
  onCompleted(event: { jobId: string }, eventId: string): void {
    this.logger.log({
      jobId: event.jobId,
      eventId,
      contextId: RequestContext.id,
    });
  }
}

@Module({
  imports: [QueueModule.registerQueue({ name: "email-queue" })],
  providers: [EmailQueueEvents],
})
export class EmailEventsModule {}
```

两类监听器都必须注册为 provider，并保持单例作用域；Nest 不会为请求作用域的 provider 注册事件监听器。

所有这些上下文的 `type` 都是 `"queue"`。Worker 的 `active`、`completed`、`progress` 事件，以及携带 Job 的 `failed` 事件，会绑定 `JOB_REF` 并使用 Job ID 作为上下文 ID。`stalled` 事件只有 Job ID；QueueEvents 事件也只有事件数据，使用其中的 `jobId` 作为上下文 ID，不绑定 `JOB_REF`。没有 Job ID 的事件会生成上下文 ID，不会额外查询 Redis 来获取 Job。

事件回调和上下文中间件的异常会被捕获并记录，避免未处理的 Promise 拒绝。BullMQ 不会等待异步监听器完成，也不会因为监听器失败而重试任务；`process()` 的异常仍正常交给 BullMQ 处理。上下文中间件可以是异步的，因此不要依赖事件回调的同步副作用。

这些行为仅适用于从 `@nest-boot/queue` 导入的装饰器。直接使用 `worker.on()`、`queue.on()` 或 `queueEvents.on()` 注册的回调，需要显式通过 `RequestContext.run()` 等方式包装，并处理异步异常。

## 内置任务历史与 GraphQL

`QueueModule` 自动发现应用已注册的集成，`graphql` 默认为 `true`；设置为 `false` 可保留持久化但不注册任务查询。各队列的 `persist` 默认为 `false`，在 `registerQueue` 中按需开启：

| 应用配置                                                            | 行为                                                                              |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 未配置数据库集成，且没有队列设置 `persist: true`                    | 仅运行 BullMQ 队列和 worker                                                       |
| 已注册 `DatabaseModule` 和内置 `Job` 实体                           | 提供 `JobHistoryService` 和 `JobService`，仅记录设置了 `persist: true` 的队列事件 |
| 已启用数据库历史，并注册 `GraphQLModule`，且未设置 `graphql: false` | 同时提供 `job(id)` 和 `jobs` 分页查询                                             |

仅安装依赖包不会启用功能。数据库与 GraphQL 是可选 peer dependency，纯队列无需安装它们。持久化需要 `@nest-boot/database`，GraphQL 还需要 `@nest-boot/graphql` 和 `@nest-boot/graphql-connection`，以及各自文档列出的 peer dependency。

```typescript
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { DatabaseModule } from "@nest-boot/database";
import { GraphQLModule } from "@nest-boot/graphql";
import { QueueModule } from "@nest-boot/queue";
import { entities as queueEntities } from "@nest-boot/queue/persistence";
import { Module } from "@nestjs/common";

@Module({
  imports: [
    DatabaseModule.forRoot({
      driver: PostgreSqlDriver,
      entities: [...queueEntities, "dist/**/*.entity.js"],
      entitiesTs: [...queueEntities, "src/**/*.entity.ts"],
    }),
    GraphQLModule,
    QueueModule.forRoot({
      graphql: true, // 默认开启；false 仅关闭内置任务查询。
      history: { jobTTL: 7 * 24 * 60 * 60 * 1000 },
      // Authorize this request using your application's verified identity.
      // Return a MikroORM filter for visible jobs, or null to deny access.
      getJobReadFilter: () => null,
    }),
    QueueModule.registerQueue(
      { name: "email" },
      { name: "export", persist: true },
    ),
  ],
})
export class JobsModule {}
```

将 `queueEntities` 同时加入**运行时数据库配置和 MikroORM CLI 配置**。启动 worker 前生成、审核并执行迁移；自动发现不会创建或修改数据库表。内置表名是 `job`，ID 格式为 `queueName:jobId`。

`getJobReadFilter` 在每次读取时执行，将授权范围同时应用于单条任务、分页结果及总数。未配置回调、返回 `null` 或 `undefined` 都会拒绝访问。返回 `{}` 明确允许访问全部任务，必须先校验调用者权限。任务参数和返回值可能含有敏感数据；入队时可靠地写入归属信息，以及配置需要的 RLS 策略，仍由应用负责。示例服务端通过 MikroORM 的 `discovery.onMetadata` 保留原有用户/工作区 RLS 策略。

异步注册时，将 `graphql`、`history` 和 `getJobReadFilter` 放在 `forRootAsync` 的工厂返回值中。实体和服务从 `@nest-boot/queue/persistence` 导入；GraphQL 连接类型和 Resolver 从 `@nest-boot/queue/graphql` 导入。这些是同一个包的入口，分开导出以避免纯队列加载可选依赖。只在安装相应依赖的应用中导入 GraphQL 入口。

`jobs` 支持队列、名称、状态、日期筛选，名称搜索、游标分页和排序。`job(id)` 对不存在或超出授权范围的记录返回 `null`。授权范围由 `JobService` 执行，直接调用服务也同样受限。

历史同步监听**本地** Queue 和 Worker 事件，是尽力而为的历史记录，不是可靠审计日志，也不能替代 BullMQ 状态。每次写入都会 fork EntityManager，失败仅记录日志，不使 worker 失败。队列是否记录历史统一由 `persist` 控制，未开启的普通队列和定时任务默认不落库；`history.convertJobToEntityData` 可转换记录内容。模块自己的每小时定时器按 `history.jobTTL` 清理最后更新时间过期的记录，默认 30 天；关闭应用时停止定时器，无需 `ScheduleModule`。

异步注册队列时，在工厂返回值中设置 `persist`；`useClass` 和 `useExisting` 工厂也支持同一配置：

```ts
QueueModule.registerQueueAsync({
  name: "export",
  useFactory: () => ({ persist: true }),
});
```

显式开启 `persist` 时，必须注册 `QueueModule`、`DatabaseModule`，并将内置 `Job` 加入 ORM 实体发现。缺少条件会在创建该队列前导致启动失败。生产者和 worker 分开部署时，两侧都应设置 `persist: true`，以记录各自的本地事件。

### 从 queue-database 迁移

`@nest-boot/queue-database` 已从仓库移除。迁移到同一个 `@nest-boot/queue` 包；已发布的旧版本仍保留在 npm，但不会随本次变更更新。

使用内置 API 时，移除 `QueueDatabaseModule`，以内置 `Job` 替换应用的旧实体，将历史配置移至 `QueueModuleOptions.history`，用各队列的 `persist: true` 替代 include/exclude 列表，并配置 `getJobReadFilter`。删除应用原有的 `JobResolver`、`JobService` 和分页定义，避免重复 GraphQL 字段。审核迁移时注意保留既有任务数据、自定义字段和 RLS 策略。

## 最佳实践

1. **独立队列** — 为不同的任务类型使用独立队列（邮件、文件操作等），配置适当的并发数。

2. **任务 ID** — 使用确定性或 Sonyflake 的任务 ID 实现幂等性和可追踪性。

3. **结构化日志** — 在处理器中使用 `Logger.assign()` 将任务上下文附加到日志条目。

4. **自动清理** — 设置 `removeOnComplete` 和 `removeOnFail` 自动清理旧任务。

`@nest-boot/queue` 基于 BullMQ 的 Redis 后端。`@Queue(name)` 固定名称，`@Processor(QueueClass)` 固定消费者绑定，其余运行配置放进构造函数。无需 `@nestjs/bullmq`。

## 安装

```bash
pnpm add @nest-boot/queue @nest-boot/command @nest-boot/request-context bullmq zod
```

## 声明和注入队列

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";
import { z } from "zod";

@Queue("email")
export class EmailQueue extends BaseQueue {
  readonly jobSchemas = {
    send: {
      data: z.object({ to: z.email(), subject: z.string() }),
      result: z.object({ messageId: z.string() }),
    },
    welcome: {
      data: z.object({ userId: z.string() }),
    },
  };

  constructor() {
    super({ defaultJobOptions: { attempts: 3 } });
  }
}

export type EmailData = z.input<EmailQueue["jobSchemas"]["send"]["data"]>;
```

`@Queue()` 可以省略名称：去掉类名末尾的 Queue 后转为 kebab-case，例如 EmailQueue → email、JobQueue → job。`@Queue("email")` 可显式指定名称。没有额外配置时可以省略构造函数。`BaseQueue` 默认读取 `REDIS_URL`，构造函数的 `connection` 优先。`prefix`、`defaultJobOptions` 等配置传给 `super(options)`；名称必须由 `@Queue(name)` 声明，每个具体队列类都需要自己的名称声明。

在模块树中导入一次全局 `QueueModule`，将队列类注册为普通 provider。队列运行只需 Redis，不依赖数据库、GraphQL、认证或调度模块。

```ts
import { QueueModule } from "@nest-boot/queue";
import { Injectable, Module } from "@nestjs/common";
import { EmailQueue, type EmailData } from "./email.queue";

@Injectable()
export class EmailService {
  constructor(private readonly queue: EmailQueue) {}

  async send(data: EmailData) {
    return await this.queue.add("send", data);
  }
}

@Module({
  imports: [QueueModule],
  providers: [EmailQueue, EmailService],
  exports: [EmailQueue],
})
export class EmailModule {}
```

队列类继承 BullMQ 方法，可以添加业务方法。无需 `registerQueue()` 或 `@InjectQueue()`。队列必须是单例，应用内名称唯一；通过导出 provider 复用同一实例。Nest 关闭应用时关闭队列连接。

## Job schema 与类型推导

从 `@nest-boot/queue` 导入任务类型 `Job<Q, N>`；可选数据库实体 `JobEntity` 从 `@nest-boot/queue-api` 导入。`JobEntity` 是原实体类的导出别名，数据库表名仍为 `job`，GraphQL 类型名仍为 `Job`。内部 BullMQ 原生类统一使用 `BullmqJob`、`BullmqQueue`、`BullmqWorker` 和 `BullmqQueueEvents` 别名。

在实例属性 `readonly jobSchemas` 中声明允许的任务名称，不需要 BaseQueue 泛型或 `as const`。不要将属性显式标注为宽泛的 JobSchemas，否则会丢失具体任务名。

每个任务的 `data` 必填且必须为 `z.object()`；`result` 可选，允许其他 Zod 类型，省略时表示无业务返回值，类型为 void。name 直接从对象键推导，无需 z.literal。生产端的 add、addBulk、upsertJobScheduler 自动约束 name 和 data，消费端为每种任务定义对应方法，例如 `processSend(job: Job<EmailQueue, "send">)`。参数类型必须标注；后续可选参数按 `token?: string`、`signal?: AbortSignal` 声明，不能增加额外必填参数。返回类型可以推导，但必须符合这一种任务的 result schema。

```ts
await queue.add("send", { to: "user@example.com", subject: "Hello" });
await queue.add("welcome", { userId: "123" });
// queue.add("unknown", {});                 // 类型错误
// queue.add("send", { userId: "123" });      // 类型错误
```

入队前校验数据；批量入队会先校验整批再提交。Scheduler 标识与 job name 独立，声明了 schema 的队列必须提供包含 name 和 data 的模板。消费端再次校验源任务，阻止绕过封装写入的未知名称或非法参数；处理结束后校验 result，未声明 result 时要求返回 undefined。校验失败交给 BullMQ 标记失败和按配置重试。支持异步校验。

schema 用于校验稳定的 JSON 契约。队列在入队前、每次处理前，以及声明了 result 时完成任务前调用 `parseAsync()`，但丢弃解析结果。校验失败会保留 ZodError 中的具体原因。Redis、处理器的 `job.data`、`updateData()` 和持久化返回值统一使用 schema 的原始输入类型（`z.input`），生产端和消费端共用 `Job`。

队列不会采用默认值、类型强制转换、transform 或未知字段剔除的结果。Zod 仍会在校验时执行 schema 中的回调，因此应避免副作用，将业务转换显式放在业务代码中。需要拒绝未知字段时，使用 `z.strictObject()`。`updateData()` 保持 BullMQ 原生行为，更新后的数据在下一次处理前校验。schema 应描述 JSON 传输格式，避免 Date、BigInt 等无法原样通过 JSON 传输的值。未声明 jobSchemas 的队列可以用于生产任务；定义 Processor 时必须声明具体的 jobSchemas，并为每种任务实现 processXXX，不再支持通用 process(job) 方法。

## 处理任务

```ts
import { BaseProcessor, Processor, type Job } from "@nest-boot/queue";
import { EmailQueue } from "./email.queue";
import { NotificationService } from "./notification.service";

@Processor(EmailQueue)
export class EmailProcessor extends BaseProcessor {
  constructor(private readonly notifications: NotificationService) {
    super({ concurrency: 5 });
  }

  async processSend(job: Job<EmailQueue, "send">) {
    const messageId = await this.notifications.send(job.data);
    return { messageId };
  }

  async processWelcome(job: Job<EmailQueue, "welcome">) {
    await this.notifications.welcome(job.data.userId);
  }
}
```

Worker 按 `process${PascalCase<name>}` 分发：send 对应 processSend，send-email 对应 processSendEmail。编译期要求每种任务都有对应方法，参数准确声明为 `Job<QueueClass, "name">`，并返回符合该任务 result schema 的 Promise；省略 result 的任务返回 void。send-email 与 sendEmail 等转换后重名的任务在编译期和运行时 schema 检查中都会被拒绝。

运行时遇到未知任务名或缺少处理方法时，抛出 `UnrecoverableError`，将任务标记为失败、保留错误原因，并跳过自动重试。外部生产者或旧部署写入的任务同样适用。其他校验或处理异常按配置重试。

注册 Processor 和对应 Queue provider；仅消费任务的应用也需要注册 Queue。缺少队列时初始化失败，尚未创建 Worker。并发等 Worker 配置传给 `super(workerOptions)`，连接、prefix 和 telemetry 继承对应队列。Worker 仍由 BaseProcessor 配合 QueueManager 管理，无需单独声明 Worker 类。需要原生 `Job`、`Queue`、`Worker`、`QueueEvents` 时直接从 `bullmq` 导入。

共享 ESLint 配置默认启用 `@nest-boot/queue/processor-name`：处理器类名必须将队列类名末尾的 Queue 替换为 Processor。例如 `@Processor(EmailQueue)` 要求类名为 EmailProcessor，JobQueue 对应 JobProcessor。该约束在 lint 时检查，与 Redis 队列名称无关。

Processor 必须为单例。request、transient 或被 request 依赖传播作用域的 Processor 会在初始化时被拒绝。同一实例处理所有任务，避免在实例字段中保存当前任务数据。

每次任务处理都建立独立的 `RequestContext`，类型为 `queue`，并设置当前 `JOB_REF`；并发任务互不影响。上下文中间件在处理任务前执行。通过 `RequestContext.current()` 或 `RequestContext.get(JOB_REF)` 在方法内读取当前任务，不要在单例构造函数中捕获上下文或注入 `JOB_REF`。处理异常交给 BullMQ，可恢复错误按配置重试。

## 启动消费者

自动历史事件读取器在所有应用入口运行。业务 Worker 通过 QueueManager 启动。按照[命令教程](/docs/tutorial/command) 配置 `CommandModule` 和 CLI 入口后运行：

```bash
pnpm exec nb queue:start
pnpm exec nb queue:start --queue email --queue report-queue
pnpm exec nb queue:start --queue job
```

`queue:start` 是唯一的 `queue:*` 命令。不指定 `--queue` 时启动所有消费者；指定时仅运行匹配的 Processor，`job` 也遵循同一个过滤规则。需要同时处理业务任务和同步历史时，显式选择两者，例如 `--queue email --queue job`。已注册但没有 Processor 的队列不会匹配；过滤后没有消费者时，命令报错且不创建 Worker。未知名称在创建消费者前报错。HTTP、REPL 和普通命令仍然可以注入队列提交任务。定时任务在应用启动时注册，选中 schedule 后才启动其 Worker。SIGINT、SIGTERM 会先等待正在执行的任务完成再关闭依赖。

程序内可在应用初始化后调用 `await manager.start(["email"])`；所有选中的连接就绪后才开始消费。`worker` getter 此后可用；`manager.waitForStop()` 在消费者循环致命错误时拒绝。

## 运行配置

通过普通 Nest 依赖注入业务配置，名称保持静态：

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";
import { ConfigService } from "@nestjs/config";

@Queue("email")
export class EmailQueue extends BaseQueue {
  constructor(config: ConfigService) {
    super({
      connection: { host: config.getOrThrow<string>("REDIS_HOST") },
      defaultJobOptions: {
        attempts: config.get<number>("EMAIL_JOB_ATTEMPTS", 3),
      },
    });
  }
}
```

异步配置可通过异步工厂 provider 注入，Nest 会等待其完成。测试与自定义工厂也可以直接 `new` 队列实例。

## Redis 与 Job 同步

队列状态存储在 Redis，不需要队列数据库或 `queue:migrate`。每个已注册 Queue 都持有一个 QueueEvents，在 HTTP、REPL 和仅生产者实例中自动启动，读取 `<prefix>:<queue>:events`。仅导入 QueueModule 时不注册 `job` 队列，也不提交数据库快照；额外导入 QueueApiModule 后才开启持久化同步。

`processor.worker` 和 `queue.queueEvents` 通过只读 getter 访问，分别在 `QueueManager.start()` 和应用初始化后可用。实例通过内部 Symbol 引用创建和管理，Processor 不提供事件订阅封装。

回调第二个参数为 `毫秒-序号` 流 ID，在单个队列内跨实例严格递增。Job 同步使用带 prefix 的源队列名与流 ID 做 BullMQ deduplication，去重窗口 24 小时。queue-api 不转发自身 `job` 队列的事件，避免递归。应用初始化会等待读取器连接就绪。读取器使用 BullMQ 默认起点监听新事件，应用启动或重启时不回放历史事件；连接就绪不代表首次流读取已开始，首次读取之前的事件不会补同步。需要完整快照时，应保留源任务足够长时间；任务提前自动删除时，只能保留终态事件携带的部分信息。

`JobQueue` 和 `JobProcessor` 位于 queue-api 包内，采用标准的 `@Queue()` / `@Processor(JobQueue)` 声明。QueueManager 统一发现队列并创建原生事件读取器；JobService 在读取器启动前订阅事件，同时提供数据库查询。关闭时依次排空来源 Worker、停止来源读取器并提交完待同步快照，最后排空 Job Worker。同步 schema 在入队前拒绝错误状态、时间戳和元数据。数据库写入失败时最多重试 20 次，指数退避；暂时写入失败仍可提交 Redis 业务任务。

内置 `job` 队列承载 `sync` 和 `cleanup`。JobService 通过 BullMQ Job Scheduler 注册每天 UTC 00:00 执行一次的清理任务，多实例共享同一个 scheduler。JobProcessor 每批最多删除 1000 条最后事件时间超过 30 天的记录，不区分状态；`lastEventMs = 0` 时回退到 `createdAt`。清理只删除数据库记录，不影响 Redis 任务。长期执行或延迟的任务也可能被清理，后续事件会重新创建记录并生成新的 UUID。清理需要运行 `job` Worker，无需依赖 `@nest-boot/schedule`。

## 数据库历史和 GraphQL

数据库记录和 GraphQL 查询由可选的 `@nest-boot/queue-api` 提供。安装该包及 Database、GraphQL、GraphQL Connection、Auth peer 依赖，在应用配置对应的全局模块后导入 QueueApiModule。QueueApiModule 直接注入全局 EntityManager，复用已配置的 AuthModule，不重复注册数据库或认证模块；它不依赖 schedule。CLI 使用相同配置。

按普通实体方式注册 `JobEntity`，运行时和 MikroORM CLI 使用相同实体列表；表、字段和 schema 使用 ORM 默认命名。建表、索引与后续变更走标准应用迁移；Job 表不设置 RLS，由服务层限制查询范围。

```ts
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { DatabaseModule } from "@nest-boot/database";
import { QueueModule } from "@nest-boot/queue";
import { JobEntity, QueueApiModule } from "@nest-boot/queue-api";

const database = DatabaseModule.forRoot({
  driver: PostgreSqlDriver,
  clientUrl: process.env.DATABASE_URL,
  entities: [JobEntity],
});
const queues = QueueModule;
const jobApi = QueueApiModule;
```

Job 仅保存 `id`、`queue`、`jobId`、`name`、`data`、`status`、`progress`、`returnValue`、`failedReason`、`createdAt`、`startedAt`、`finishedAt`、`lastEventMs`、`lastEventSeq`。三个时间戳使用标准数据库日期字段；锁、调度、依赖和重试配置留在 Redis。

主键 UUID 由数据库 `gen_random_uuid()` 生成。BullMQ 原始 ID 保存在 jobId，`(queue, jobId)` 唯一约束识别同一任务。bigint 字段 `last_event_ms` 与 `last_event_seq` 保存流 ID，插入冲突时忽略，更新时原子比较二元组，仅接受严格更新的事件。重复和乱序事件不会覆盖新状态或改变 UUID，Redis 去重过期后同样成立。历史查询异步更新；删除 Redis 任务不会删除历史。

GraphQL 查询分为 `userJob` / `userJobs`、`workspaceJob` / `workspaceJobs`、`systemJob` / `systemJobs`，全部使用 AuthGuard。用户查询固定匹配当前用户的 data.userId；工作空间查询通过当前工作空间的有效成员和读取权限校验后，固定匹配 data.workspaceId。系统查询要求管理员身份（复用 auth 的 user.adminRoles 配置），且两个归属字段都不存在或为 JSON null；空字符串不属于系统任务。API Key 不会继承持有者的管理员访问权限。不提供通用 job / jobs 或管理员全量查询。

使用 `@nest-boot/queue-api` 导出的无参数 `@QueueVisible()` 标记允许通过 API 查询的队列。只有在 API 应用中注册、且具体类显式标记的队列才可见；子类需要重新标记。单条查询、分页和计数都会排除隐藏队列，客户端筛选条件不能绕过限制。没有可见队列时返回空结果。可见性不替代身份授权；未标记的队列仍然同步和清理数据库记录。

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";
import { QueueVisible } from "@nest-boot/queue-api";

@QueueVisible()
@Queue()
export class EmailQueue extends BaseQueue {}
```

JobService 直接注入 EntityManager，提供 getUserJob、getWorkspaceJob、getSystemJob 及对应的 get\*JobConnection，不暴露通用 CRUD 方法。单条记录、分页节点和计数都将固定身份条件与客户端筛选条件相交；缺少身份或工作空间权限时拒绝访问。一个 GraphQL 请求可以并行查询多个范围，无需切换数据库上下文。Job 表不启用 RLS，也不使用数据库 session 身份变量；直接 ORM 属于可信内部 API，不提供归属隔离，对外处理器只能调用这些限定范围的方法。

公开字段仍只有 ID、queue、name、status、数值进度和时间；原始参数、结果、错误与内部 ID 不公开。支持队列、名称、状态、创建时间筛选，仅允许 CREATED_AT 排序，默认创建时间倒序，ID 仅在内部打破同时间戳的并列。用户和工作空间索引分别以身份表达式开头，后接 created_at、id；无归属的系统任务使用 (created_at, id) 部分索引。

已有 PostgreSQL 队列在切换前应排空或迁移运行中的任务，并保留所需历史；数据库迁移不会自动将待处理任务搬入 Redis。客户端历史 ID 需切换为 UUID。Redis prefix 与 ORM 数据库配置独立。

---
title: "队列"
description: "通过 BullMQ 提供可注入的队列类、后台消费者与可选的任务持久化。"
---

`@nest-boot/queue` 直接基于 [BullMQ](https://docs.bullmq.io/) 集成 Nest。队列类是可注入的 provider，消费者引用同一个队列类，不再依赖 `@nestjs/bullmq`。

## 安装

```bash
pnpm add @nest-boot/queue @nest-boot/request-context bullmq
```

## 定义与注入队列

```ts
import { BaseQueue, Queue } from "@nest-boot/queue";

export interface EmailData {
  to: string;
  subject: string;
}

@Queue({
  name: "email",
  defaultJobOptions: { attempts: 3, removeOnComplete: { age: 3600 } },
})
export class EmailQueue extends BaseQueue<EmailData> {}
```

把队列类加入 `providers`，直接通过构造函数注入：

```ts
import { QueueModule } from "@nest-boot/queue";
import { Injectable, Module } from "@nestjs/common";
import { EmailQueue, type EmailData } from "./email.queue";

@Injectable()
export class EmailService {
  constructor(private readonly queue: EmailQueue) {}

  async send(data: EmailData) {
    return await this.queue.add("send", data);
  }
}

@Module({
  imports: [QueueModule],
  providers: [EmailQueue, EmailService],
  exports: [EmailQueue],
})
export class EmailModule {}
```

不需要 `registerQueue()` 或 `@InjectQueue()`。`QueueModule` 自动读取 `REDIS_URL`；通过 `forRoot()` / `forRootAsync()` 可以指定连接和共享默认配置，根配置只注册一次。队列类继承 BullMQ 的方法，也可以添加业务方法。

队列 provider 必须保持单例，队列名称在应用内必须唯一。需要跨模块使用时，导出队列类并导入所属模块，不要重复创建实例。应用关闭时会关闭队列连接。

队列类需要在构造函数中注入业务依赖时，注入 `QueueFactory` 并调用 `super(factory)`。`QueueFactory.create()` 用于保留继承构造函数的队列类。

## 消费任务

```ts
import { BaseProcessor, OnWorkerEvent, Processor } from "@nest-boot/queue";
import { Job } from "bullmq";
import { EmailQueue, type EmailData } from "./email.queue";
import { NotificationService } from "./notification.service";

@Processor(EmailQueue, { concurrency: 5 })
export class EmailProcessor extends BaseProcessor {
  constructor(private readonly notifications: NotificationService) {
    super();
  }

  async process(job: Job<EmailData>) {
    await this.notifications.send(job.data);
  }

  @OnWorkerEvent("completed")
  onCompleted(job: Job<EmailData>) {
    console.log(`Completed ${job.id}`);
  }
}
```

将 `EmailProcessor` 与 `EmailQueue` 都注册为 provider，或者导入导出队列的模块。纯消费者部署也必须注册队列类。注册只创建客户端，不会自动入队；缺少队列 provider 时会在启动任何 worker 前报错。消费者的连接、prefix 和 telemetry 都来自队列实例，worker 配置不能指向不同的 Redis 命名空间。使用 `BaseProcessor` 替代已移除的 `WorkerHost` 导出。

### Scope 与 RequestContext

每次任务执行都创建独立的 `RequestContext`，类型为 `"queue"`，并绑定 `JOB_REF`。上下文及其中间件会在 Nest **解析消费者依赖之前**建立。`process()` 的错误继续交给 BullMQ 重试。

支持单例、REQUEST 和 TRANSIENT 消费者。注入 request-scoped 服务时，作用域会沿依赖链传递；框架会通过 `ContextIdFactory.getByRequest()` 和消费者所属模块的 `ModuleRef.resolve()` 为任务解析实例，也支持应用定义的 durable context 策略。

导入 `RequestContextModule` 后可以直接注入 `RequestContext`。该 provider 使用 REQUEST 作用域，返回当前已有的上下文，因此注入它也会让消费者变为 request-scoped：

```ts
import {
  BaseProcessor,
  JOB_REF,
  Processor,
  QueueModule,
} from "@nest-boot/queue";
import {
  RequestContext,
  RequestContextModule,
} from "@nest-boot/request-context";
import { Inject, Module } from "@nestjs/common";
import { Job } from "bullmq";
import { EmailQueue, type EmailData } from "./email.queue";

@Processor(EmailQueue)
export class EmailProcessor extends BaseProcessor {
  constructor(
    private readonly context: RequestContext,
    @Inject(JOB_REF) private readonly job: Job<EmailData>,
  ) {
    super();
  }

  async process() {
    return { contextId: this.context.id, recipient: this.job.data.to };
  }
}

@Module({
  imports: [QueueModule, RequestContextModule],
  providers: [EmailQueue, EmailProcessor],
})
export class EmailWorkerModule {}
```

单例服务可以继续在方法中使用 `RequestContext.current()` 或 `RequestContext.get(JOB_REF)`，不要在单例构造函数中捕获任务上下文。durable 依赖只适合有意共享的状态，不能保存当前任务数据。`worker` getter 可在模块初始化后及 scoped 消费者的 `process()` 中使用。

## 动态队列配置

配置依赖其他服务或异步读取时，使用普通 Nest factory provider。`QueueFactory.create()` 保留声明中的队列名称，用运行时配置覆盖装饰器配置，并逐字段合并 `persistence`。返回的队列实例仍由 Nest 管理生命周期。

```ts
import { QueueFactory, QueueModule } from "@nest-boot/queue";
import { Module } from "@nestjs/common";
import { EmailQueue } from "./email.queue";
import { SettingsService } from "./settings.service";

@Module({
  imports: [QueueModule],
  providers: [
    SettingsService,
    {
      provide: EmailQueue,
      inject: [QueueFactory, SettingsService],
      useFactory: async (factory: QueueFactory, settings: SettingsService) =>
        factory.create(EmailQueue, await settings.getEmailQueueOptions()),
    },
  ],
  exports: [EmailQueue],
})
export class EmailModule {}
```

## 队列事件

`@OnWorkerEvent()` 监听本地 worker。显式监听 Redis 事件流时使用独立的单例 `QueueEventsHost`：

```ts
import {
  OnQueueEvent,
  QueueEventsHost,
  QueueEventsListener,
} from "@nest-boot/queue";
import { RequestContext } from "@nest-boot/request-context";
import { EmailQueue } from "./email.queue";

@QueueEventsListener(EmailQueue)
export class EmailEvents extends QueueEventsHost {
  @OnQueueEvent("completed")
  completed(event: { jobId: string }) {
    console.log(event.jobId, RequestContext.id);
  }
}
```

将 `EmailEvents` 及其队列注册为 provider。Worker 事件仅绑定单例消费者，scoped 消费者的事件方法会被跳过；QueueEvents listener 必须是单例。持久化使用本地 Queue/Worker 事件，不创建 QueueEvents 读取器。

每个事件回调都有独立上下文并运行上下文中间件。携带 Job 的 worker 事件绑定 `JOB_REF`；`stalled` 只有任务 ID。QueueEvents 使用 payload 中的 `jobId`，不绑定 `JOB_REF`。其他事件生成上下文 ID。事件处理器及中间件的错误会记录并抑制，因为 BullMQ 不等待异步监听器。直接调用 `.on()` 时，需要自行处理上下文及异步错误。

## 内置任务持久化与 GraphQL

`QueueModule` 自动发现应用已注册的集成。每个队列通过 `persistence.enabled: true` 开启持久化，默认关闭；只设置队列 TTL 不会自动开启。模块配置的 `persistence.ttl` 提供默认保留时间，默认 30 天，单位毫秒；各队列可覆盖。`graphql` 默认为 `true`，设为 `false` 可关闭内置任务查询。

| 应用配置                                                      | 行为                                                         |
| ------------------------------------------------------------- | ------------------------------------------------------------ |
| 未配置数据库集成，且没有队列开启持久化                        | 仅运行 BullMQ 队列和 worker                                  |
| 已注册 `DatabaseModule` 和内置 `Job` 实体                     | 提供 `JobService`，仅监听 `persistence.enabled: true` 的队列 |
| 已配置数据库集成和 `GraphQLModule`，且未设置 `graphql: false` | 同时提供 `job(id)` 和 `jobs` 分页查询                        |

`@nest-boot/database`、`@nest-boot/graphql` 和 `@nest-boot/graphql-connection` 都是可选 peer dependency。按需在应用中安装，并补齐各自文档列出的对等依赖：

| 功能              | 额外需要的 Nest Boot 包                                                      |
| ----------------- | ---------------------------------------------------------------------------- |
| 纯队列            | 无                                                                           |
| 任务持久化        | `@nest-boot/database`                                                        |
| 任务 GraphQL 查询 | `@nest-boot/database`、`@nest-boot/graphql`、`@nest-boot/graphql-connection` |

仅安装包不会启用功能，还需在应用中注册相应模块及内置实体。只使用持久化时，默认的 `graphql: true` 不会要求安装 GraphQL。若任务查询已满足其他启用条件，但缺少 `graphql-connection`，启动会明确报错；可设置 `graphql: false` 关闭任务查询。

| 配置                  | 设置位置                                             | 默认值           |
| --------------------- | ---------------------------------------------------- | ---------------- |
| `persistence.enabled` | `@Queue()` 参数或 `QueueFactory.create()` 的最终配置 | `false`          |
| `persistence.ttl`     | `@Queue()` 参数或 `QueueFactory.create()` 的最终配置 | 继承模块默认 TTL |
| `persistence.ttl`     | `forRoot` / `forRootAsync` 参数                      | 30 天，单位毫秒  |
| `graphql`             | `forRoot` / `forRootAsync` 参数                      | `true`           |
| `getJobReadFilter`    | `forRoot` / `forRootAsync` 参数                      | 拒绝读取         |

```typescript
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { DatabaseModule } from "@nest-boot/database";
import { GraphQLModule } from "@nest-boot/graphql";
import { BaseQueue, Queue, QueueModule } from "@nest-boot/queue";
import { entities as queueEntities } from "@nest-boot/queue/persistence";
import { Module } from "@nestjs/common";

@Queue({ name: "export", persistence: { enabled: true, ttl: 7 * 86400000 } })
class ExportQueue extends BaseQueue {}

@Module({
  imports: [
    DatabaseModule.forRoot({
      driver: PostgreSqlDriver,
      entities: [...queueEntities, "dist/**/*.entity.js"],
      entitiesTs: [...queueEntities, "src/**/*.entity.ts"],
    }),
    GraphQLModule,
    QueueModule.forRoot({
      graphql: true, // 默认开启；false 仅关闭内置任务查询。
      persistence: { ttl: 30 * 24 * 60 * 60 * 1000 },
      // Authorize this request using your application's verified identity.
      // Return a MikroORM filter for visible jobs, or null to deny access.
      getJobReadFilter: () => null,
    }),
  ],
  providers: [ExportQueue],
})
export class JobsModule {}
```

将 `queueEntities` 同时加入**运行时数据库配置和 MikroORM CLI 配置**。启动 worker 前生成、审核并执行迁移；自动发现不会创建或修改数据库表。内置表名是 `job`，ID 格式为 `queueName:jobId`。

`getJobReadFilter` 在每次读取时执行，将授权范围同时应用于单条任务、分页结果及总数。未配置回调、返回 `null` 或 `undefined` 都会拒绝访问。返回 `{}` 明确允许访问全部任务，必须先校验调用者权限。任务参数和返回值可能含有敏感数据；入队时可靠地写入归属信息，以及配置需要的 RLS 策略，仍由应用负责。示例服务端通过 MikroORM 的 `discovery.onMetadata` 保留原有用户/工作区 RLS 策略。

异步注册时，将 `graphql`、默认 `persistence.ttl` 和 `getJobReadFilter` 放在 `forRootAsync` 的工厂返回值中；队列自己的 `persistence` 放在 `@Queue()` 或传入 `QueueFactory.create()` 的运行时配置中。实体和服务从 `@nest-boot/queue/persistence` 导入；GraphQL 连接类型和 Resolver 从 `@nest-boot/queue/graphql` 导入。这些是同一个包的入口，分开导出以避免纯队列加载可选依赖。只在安装相应依赖的应用中导入 GraphQL 入口。

`jobs` 支持队列、名称、状态、日期筛选，名称搜索、游标分页和排序。`job(id)` 对不存在或超出授权范围的记录返回 `null`。授权范围由 `JobService` 执行，直接调用服务也同样受限。

`JobService` 监听**本地** Queue 和 Worker 事件，每个任务保存一条记录，持续更新其最近已知状态。这是尽力而为的状态同步，不是逐条事件历史或可靠审计日志，也不能替代 BullMQ 状态。所有被监听的 Queue 和 Worker 事件统一按 `queueName:jobId` 执行 upsert，覆盖已有字段。BullMQ 任务移除后复用相同 ID 时，新的入队写入会替换旧任务数据并清空旧执行结果。每次写入都会 fork EntityManager，失败仅记录日志，不使 worker 失败。同一进程中，同一任务的写入按事件顺序执行，避免较早的慢写入覆盖后续结果；不同任务仍可并发写入。这不保证独立生产者和 worker 进程之间的写入顺序：最后完成的数据库写入生效，因此迟到的生产者写入可能覆盖 Worker 结果。未开启持久化的普通队列和定时任务默认不落库。模块自己的每小时定时器仅清理当前应用开启了持久化的队列，按各队列实际 TTL 和记录最后更新时间判断过期；未注册或关闭持久化的队列不参与清理。TTL 优先级为队列配置、模块默认值、30 天。没有队列开启持久化时不启动清理定时器；关闭应用时停止定时器，无需 `ScheduleModule`。

队列开启 `persistence.enabled` 时，必须注册 `QueueModule`、`DatabaseModule`，并将内置 `Job` 加入 ORM 实体发现。缺少条件会在创建该队列前导致启动失败。生产者和消费者应用都必须注册同一个队列类，并复用一致的持久化配置，包括 TTL；配置只作用于本地应用，不会通过 Redis 自动传播。生产者仅记录本地入队事件，消费者仅记录本地执行事件；开启持久化的两侧都需数据库集成。`persistence` 仅配置在队列注册参数中，不放在 `@Processor()` 上。内置持久化不使用 `QueueEvents` 写库，也不保证 `queue.add()` 返回时数据库写入已完成。

### 从 queue-database 迁移

`@nest-boot/queue-database` 已从仓库移除。迁移到同一个 `@nest-boot/queue` 包；已发布的旧版本仍保留在 npm，但不会随本次变更更新。

使用内置 API 时，移除 `QueueDatabaseModule`，以内置 `Job` 替换应用的旧实体，将默认 TTL 移至 `QueueModuleOptions.persistence.ttl`，用各队列的 `persistence: { enabled: true }` 和可选 TTL 覆盖替代 include/exclude 列表，并配置 `getJobReadFilter`。删除应用原有的 `JobResolver`、`JobService` 和分页定义，避免重复 GraphQL 字段。审核迁移时注意保留既有任务数据、自定义字段和 RLS 策略。

## 最佳实践

1. **独立队列** — 为不同的任务类型使用独立队列（邮件、文件操作等），配置适当的并发数。

2. **任务 ID** — 使用确定性或 Sonyflake 的任务 ID 实现幂等性和可追踪性。

3. **结构化日志** — 在处理器中使用 `Logger.assign()` 将任务上下文附加到日志条目。

4. **自动清理** — 设置 `removeOnComplete` 和 `removeOnFail` 自动清理旧任务。

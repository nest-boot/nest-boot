Nest Boot uses [MikroORM 7.2's native row-level security](https://mikro-orm.io/docs/row-level-security). There is no separate Nest Boot RLS package or custom database driver.

## Installation

Keep all MikroORM packages on the same version, **7.2 or later**. Use the official driver for your database:

```bash
pnpm add @nest-boot/mikro-orm @nest-boot/request-context @mikro-orm/core @mikro-orm/decorators @mikro-orm/nestjs @mikro-orm/reflection @mikro-orm/postgresql
```

For PGlite, install `@mikro-orm/pglite` instead of `@mikro-orm/postgresql` and use `PgliteDriver`. Both drivers support the native transaction-based session strategy.

## Declare policies on entities

Declare policies in `@Entity({ policies })`. Policies imply that RLS is enabled. SQL expressions reference physical column names; this example uses SQL strings so its policies also survive metadata cache serialization.

```ts
import { Entity, PrimaryKey, Property } from "@mikro-orm/decorators/legacy";

@Entity({
  policies: [
    {
      name: "document_workspace",
      roles: ["authenticated"],
      using: "workspace_id = nullif(current_setting('app.workspace', true), '')::uuid",
      check: "workspace_id = nullif(current_setting('app.workspace', true), '')::uuid",
    },
  ],
})
export class Document {
  @PrimaryKey({ type: "uuid" })
  id!: string;

  @Property({ type: "uuid", fieldName: "workspace_id" })
  workspaceId!: string;

  @Property({ type: "string" })
  title!: string;
}
```

The setting name and SQL cast must match your session configuration and column type. Missing or empty workspace values above do not match any row.

Policies use `command: "select" | "insert" | "update" | "delete" | "all"` and `type: "permissive" | "restrictive"`. Use `check` for writes, not the removed `withCheck` option. Restrictive policies narrow an existing permissive grant; they do not grant access by themselves.

## Provision database roles and privileges

Native policy generation does **not** create roles or grant privileges. Provision these explicitly before applying policy migrations, with credentials authorized to manage the database:

```sql
create role anonymous nologin;
create role authenticated nologin;
grant anonymous, authenticated to app_connection;

grant usage on schema public to anonymous, authenticated;
grant select, insert, update, delete on document to authenticated;
```

Replace `app_connection` with the actual connection role. Grant sequence usage when inserts use sequences. Only grant anonymous access to the tables and operations intended to be public, and declare matching policies on those tables.

Table owners normally bypass RLS; superusers and roles with `BYPASSRLS` bypass it even with `rowLevelSecurity: "force"`. A restricted runtime role must actually be selected for policies to apply. Do not accept a database role name from an untrusted request.

## Initialize the request session

`MikroOrmModuleOptions.session` is a synchronous factory returning the native `ForkOptions["session"]` type. It runs once for each request-context EntityManager fork, inside Nest Boot's `RequestContext`.

```ts
import { PostgreSqlDriver } from "@mikro-orm/postgresql";
import { MikroOrmModule } from "@nest-boot/mikro-orm";
import { headers, RequestContext } from "@nest-boot/request-context";

MikroOrmModule.forRoot({
  driver: PostgreSqlDriver,
  session: () => {
    if (RequestContext.current().type !== "http") return undefined;

    return {
      role: "anonymous",
      variables: {
        "app.workspace": headers().get("x-workspace-id") ?? "",
      },
    };
  },
});
```

The same option works with `forRootAsync()`. Omitting the factory leaves native session behavior unchanged. Returning `undefined` does not override an inherited session; return an empty object to explicitly replace it.

The initial `app.workspace` selects a workspace while the database role remains `anonymous`. This factory runs **before authentication middleware** and must not query the not-yet-created request EntityManager. Background jobs can return their own session instead of reading HTTP headers.

### After authentication

Once identity and workspace access have been verified, use the request EntityManager to stage the authenticated database role and variables:

```ts
em.setSessionContext({
  role: "authenticated",
  variables: {
    "app.workspace": authorizedWorkspace.id,
    "app.user_id": user.id,
  },
});
```

A selected workspace alone does not grant membership. The example server validates membership or workspace-key ownership before enabling workspace-scoped access. It keeps anonymous workspace selection in the same `app.workspace` variable.

`setSessionContext()` merges variables. Replace obsolete values explicitly or call `clearSessionContext()` before staging a replacement. Clearing restores the base connection role, so it is **not** equivalent to switching to `anonymous`.

Both setting and clearing must happen **before a transaction starts**; native MikroORM rejects changing an active transaction's context.

## Queries and transactions

The default `sessionContext: "transaction"` strategy applies roles and variables transaction-locally. With a staged session, supported EntityManager operations outside explicit transactions receive an implicit transaction. Without a session, this RLS transaction wrapper is not added.

Use EntityManager operations, including `em.execute()`, for context-aware SQL. **`em.getConnection().execute()` bypasses the EntityManager session** and is reserved for explicitly privileged infrastructure work.

Use an explicit transaction for streaming with a staged session. Do not disable transactions while relying on transaction-local RLS.

The optional `sessionContext: "connection"` strategy is PostgreSQL-only and has different connection-reservation and request-context requirements. Prefer the default strategy, especially with PGlite or transaction-pooling proxies.

## Schema and migrations

Use the official `@mikro-orm/migrations` package, `Migrator`, and `Migration`. Native schema tooling manages policy creation, changes, removal, RLS enablement, and migration snapshots. No custom generator or migrator is required.

For existing databases, declare the existing policy names and expressions in entity metadata **before** running schema diffs. Undeclared existing policies can otherwise be removed. `schemaGenerator.ignorePolicies: true` is an explicit alternative when policy ownership remains external; see the official adoption guide for its limitations.

The example retains its baseline role/grant SQL and adds a normal migration changing `app.workspace_id` policies to `app.workspace`.

## Migrating from the removed package

| Previous API                                  | Native replacement                              |
| --------------------------------------------- | ----------------------------------------------- |
| `RowLevelSecurityDriver`                      | `PostgreSqlDriver` from `@mikro-orm/postgresql` |
| `PgliteRowLevelSecurityDriver`                | `PgliteDriver` from `@mikro-orm/pglite`         |
| `@Policy()`                                   | `@Entity({ policies: [...] })`                  |
| `property` / `context` shorthand              | Explicit `using` / `check` column callbacks     |
| `PolicyMode`, `PolicyCommand`                 | Native string-literal options                   |
| `RowLevelSecurity.setContext()` / `setRole()` | `em.setSessionContext()`                        |
| Custom migration classes                      | Official `Migration` / `Migrator`               |
| `AUTO` / `ENABLED` / `DISABLED`               | Explicit native session configuration           |

Auth service-authorized persistence uses a separate, session-free EntityManager when necessary. It does not clear the caller's session or flush unrelated pending writes. Such operations reject an already active scoped transaction instead of silently committing outside it; perform them before opening that business transaction.

## Testing

Use in-memory PGlite for isolated policy and request-session tests. Keep real PostgreSQL tests for its network driver and connection behavior. The integration suite covers anonymous sessions, workspace isolation, reads/writes, rollback, result-cache separation, and native policy diffs.

---
title: "定时任务"
description: "使用 BullMQ Job Scheduler 为 NestJS 提供持久化 Cron 和间隔调度。"
---

`@nest-boot/schedule` 模块会发现带装饰器的 provider 和 controller，注册持久化的 [BullMQ Job Scheduler](https://docs.bullmq.io/guide/job-schedulers)，并通过专用的 `schedule` worker 执行处理器。它同时支持 Cron 表达式和毫秒间隔。

## 安装

```bash
pnpm add @nest-boot/schedule @nest-boot/queue bullmq zod
```

## 模块注册

```typescript
import { QueueModule } from "@nest-boot/queue";
import { ScheduleModule } from "@nest-boot/schedule";
import { Module } from "@nestjs/common";

@Module({
  imports: [
    QueueModule,
    ScheduleModule.forRoot({
      concurrency: 5,
    }),
  ],
})
export class AppModule {}
```

`QueueModule` 在模块树中注册一次，例如放在 `CommonModule` 中。`ScheduleModule` 使用其全局服务，支持 `connection` 和 `concurrency`。定时任务在应用初始化时注册，此时不会创建 worker；运行 `nb queue:start --queue schedule` 后才启动消费者。队列名称固定为 `schedule`；不传 `--queue` 时也会启动定时任务队列。不需要消费定时任务时，只选择要启动的业务消费者。队列存储和调度登记使用 Redis 的 `REDIS_URL`，不依赖数据库或迁移。

共享 Redis 连接的不同应用应使用不同的 `prefix`；同一应用的副本使用相同 prefix。Worker 和旧 scheduler 清理都只作用于该命名空间的 schedule 队列：

```ts
ScheduleModule.forRoot({ prefix: "billing" });
```

## 定义定时任务

使用 `@Cron()` 定义 Cron 表达式，使用 `@Interval()` 定义毫秒间隔。Cron 默认使用 `UTC` 时区。

```typescript
import { Cron, Interval } from "@nest-boot/schedule";
import { Injectable, Logger } from "@nestjs/common";

@Injectable()
export class CleanupService {
  private readonly logger = new Logger(CleanupService.name);

  @Cron("0 0 * * *", { timezone: "UTC", removeOnComplete: true })
  async cleanupExpiredSessions(): Promise<void> {
    this.logger.log("Cleaning up expired sessions");
    // ...清理逻辑
  }

  @Interval(5 * 60 * 1000, { removeOnComplete: true })
  async syncMetrics(): Promise<void> {
    this.logger.log("Syncing metrics");
    // ...同步逻辑
  }
}
```

每个 scheduler 的 ID 为 `<类名>.<方法名>`。它们统一提交 run 任务，data 为 `{ name: "<类名>.<方法名>" }`，由 `ScheduleProcessor.processRun` 执行对应处理器。旧 scheduler 按 ID 清理，与统一的 job name 独立。应用启动时，注册器会更新所有已发现的调度，并移除代码中已不存在的旧 scheduler。其他装饰器选项会作为 BullMQ job template 选项传递。

## 长耗时任务

所有定时处理器都通过共享的 `schedule` 队列执行，并竞争该队列的 worker 并发额度。长时间运行的处理器会持续占用并发槽位，使其他已到期的任务排队，实际执行频率可能低于配置值。当该队列存在多个可用 worker 槽位时（例如配置 `concurrency > 1` 或部署多个应用实例），如果处理器运行时间超过调度间隔，同一定时任务的不同执行实例还可能重叠。BullMQ 的 job lock 只防止同一个 job 实例被重复处理，不会强制同一个 Job Scheduler 生成的不同 job 串行执行。

建议让定时处理器保持轻量、短时，主要承担触发职责。对于长时间运行、资源密集，或需要独立的并发、重试、退避和扩缩容策略的工作，应创建[专用 BullMQ 队列和 worker](/docs/tutorial/queue)，并在定时处理器中仅向该队列投递任务。

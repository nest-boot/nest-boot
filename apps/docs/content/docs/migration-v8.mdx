---
title: "Migrate to version 8"
description: "Upgrade Nest Boot applications to NestJS 12 and native ESM."
---

Version 8 is the NestJS 12 release line for all `@nest-boot/*` packages. It is
published as native ESM and requires Node.js 24.21.0 or newer.

## Upgrade dependencies

Upgrade Nest Boot and NestJS packages together:

```bash
pnpm up "@nest-boot/*@^8" "@nestjs/common@^12" "@nestjs/core@^12"
```

GraphQL applications should also use `@nestjs/graphql@^14` and
`@nestjs/apollo@^14`; queue applications use `bullmq` directly without `@nestjs/bullmq`.
Packages integrating MikroORM require MikroORM 7.

Follow the upstream [NestJS migration guide](https://docs.nestjs.com/migration-guide)
for application-level NestJS breaking changes.

## Rename database packages

Replace these dependencies and their import paths:

| Previous package             | Version 8 package           |
| ---------------------------- | --------------------------- |
| `@nest-boot/mikro-orm`       | `@nest-boot/database`       |
| `@nest-boot/mikro-orm-crypt` | `@nest-boot/database-crypt` |
| `@nest-boot/mikro-orm-hash`  | `@nest-boot/database-hash`  |

Rename database configuration imports and calls from `loadConfigFromEnv()` to
`getDatabaseConfig()`. The old export is removed.

Import `DatabaseModule` and `DatabaseModuleOptions` instead of
`MikroOrmModule` and `MikroOrmModuleOptions`. The database integration continues
using MikroORM; its upstream dependencies and CLI configuration stay named
`@mikro-orm/*` and `mikro-orm.config.ts`.

Custom request-context middleware must depend on `"database"` instead of
`"mikro-orm"`. Update dependency strings passed to
`RequestContext.registerMiddleware()` to preserve EntityManager initialization
order.

Remove the old ESLint import migration rules: `@nest-boot/import-mikro-orm`,
`@nest-boot/import-database`, `@nest-boot/import-graphql`, `@nest-boot/import-bullmq`
and `@nest-boot/import-queue`, including disabled entries. Import paths and APIs
must be migrated manually. Entity field rules no longer migrate old MikroORM
imports or re-exports; they continue checking current field configuration.

## Enable ESM

Add `"type": "module"` to the application `package.json`. Compile with
`module` and `moduleResolution` set to `NodeNext`, and target ES2023 or newer:

```json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "target": "ES2023"
  }
}
```

Use explicit `.js` extensions for relative imports in TypeScript source. Replace
CommonJS `require()` and `module.exports` usage with ESM imports and exports.
Version 8 package exports intentionally provide an `import` entry and do not
provide a CommonJS `require` entry.

## Rename queue packages

Replace `@nest-boot/bullmq` with `@nest-boot/queue`. Use `QueueModule`, `@Queue(name)` and `BaseQueue`; consumers extend `BaseProcessor` with `@Processor(QueueClass)` and register the queue class. Processors must be singletons; Workers stay managed by BaseProcessor. Move runtime settings to constructor `super(options)`, import QueueModule directly, and remove forRoot/forRootAsync and module option tokens. Worker and QueueEvents references use read-only getters backed by internal Symbols; remove event decorators, QueueEventsHost and Processor `.on()` subscriptions. Remove `@nestjs/bullmq`, `BullMQMikroORMModule` and `QueueDatabaseModule`. Queue rules use the @nest-boot/queue namespace; processor-name is enabled by the shared config.

Queues use Redis through `REDIS_URL` or explicit `connection` options. Keep `bullmq`; remove `queue:migrate`. `nb queue:start` starts consumers, with optional `--queue` selection.

Every registered Queue starts native QueueEvents without database dependencies. To persist records and expose authenticated GraphQL queries, install `@nest-boot/queue-api`, import `QueueApiModule`, and import `JobEntity`, `JobStatus` and `JobService` from that package. Configure the application's global DatabaseModule, GraphQLModule and AuthModule. Register JobEntity as an ordinary entity and use standard application migrations. The extension forwards events to the deduplicated `job` queue and schedules daily cleanup directly through BullMQ; it does not depend on schedule. Job UUIDs are database-generated; bigint last_event_ms and last_event_seq prevent out-of-order overwrites. QueueModule alone needs no EntityManager or API modules. Remove withQueueDatabaseConfig and separate queue schema configuration.

Replace the `expose` option with the parameterless `@QueueVisible()` decorator from `@nest-boot/queue-api`. Register each source queue provider in the API application and explicitly mark its concrete class to allow history queries. Unmarked or unregistered queues remain hidden from single-record reads, pagination and counts, while their records still synchronize and clean up. Replace job/jobs with userJob/userJobs and workspaceJob/workspaceJobs, scoped by JobService using trusted auth identity. systemJob/systemJobs require a configured administrator and return only records with neither owner. Remove the Job RLS policy through an ordinary application migration; Job reads no longer switch database scope. Single rows, lists and counts use the same service filter. GraphQL exposes only ID, queue, name, status, numeric progress and timestamps. History IDs are UUIDs; statuses include `PRIORITIZED` and `UNKNOWN`. Drain or migrate PostgreSQL jobs and preserve needed history before switching transports. See the [queue tutorial](/docs/tutorial/queue).

Queue job contracts now live in `readonly jobSchemas`, replacing BaseQueue's Data/Result/Name generics. Each entry requires a Zod object data schema and may declare a result schema; omission means void. Processors declare a method for every job, such as `async processSend(job: Job<EmailQueue, "send">)`, with a checked parameter and Promise result. Remove generic process(job) methods; processors require concrete jobSchemas. Hyphenated names map to PascalCase methods (`send-email` → `processSendEmail`); colliding names are rejected. Unknown jobs and missing handlers fail at runtime without automatic retries. Queue names use `@Queue(name)` or the generated default `@Queue()`.

## Update related integrations

- Upgrade `nodemailer` to `^10.0.16` when using `@nest-boot/mailer`.
  Nodemailer now includes TypeScript declarations; remove `@types/nodemailer`.
- Replace Apollo Playground configuration with `graphiql`.
- When using MikroORM, upgrade to version 7.2 and import SQL types and drivers
  from the supported package entry points such as `@mikro-orm/sql` and
  `@mikro-orm/sqlite`.
- Replace `@nest-boot/file-upload` with `@nest-boot/staged-upload`. The core
  module is now global and transport-independent. GraphQL applications must
  also install and import `@nest-boot/staged-upload-graphql` to keep the
  `createStagedUploads` mutation. Import `StagedUploadInput`, `StagedUpload`,
  and `StagedUploadField` from the GraphQL package; use `StagedUploadRequest`
  and `StagedUploadResult` for transport-independent service types.
- If you already use the v8 beta GraphQL adapter, replace
  `@nest-boot/graphql-staged-upload` with `@nest-boot/staged-upload-graphql`
  and rename `GraphQLStagedUploadModule` to `StagedUploadGraphQLModule`.
- Remove `@nest-boot/row-level-security`. Use the upstream PostgreSQL or PGlite
  driver, `@Entity({ policies })`, and `em.setSessionContext()` instead of the
  custom drivers, decorators, runtime state, and `AuthTransactionContext`.
  Replace custom migration classes with official `Migration` / `Migrator`.
  Adopt existing policies into entity metadata before generating schema diffs;
  roles and privileges must be provisioned explicitly. Configure the initial
  request session with `DatabaseModuleOptions.session` and update it before
  starting business transactions. See the [MikroORM RLS documentation](https://mikro-orm.io/docs/row-level-security).
- Auth permission identifiers are application-defined, case-sensitive strings,
  independent of CASL subject types. Catalogs, grant ceilings and API-key
  intersections compare exact strings without changing case. The built-in
  catalogs use `user:*`, `session:*`, `workspace:*`, `member:*` and
  `invitation:*` and `api-key:*`. Custom role and permission names follow the
  lowercase naming contract; invalid names are rejected, not normalized.
  Role grants, direct/API-key permissions and business rules must use the same spelling.
- Auth owns built-in ability mappings. Remove application callbacks that rebuild
  auth rules. Business callbacks now receive `AbilityRules`, return nothing, and
  grant through `can(permission, action, subject, conditions?)`. Built-in subjects
  and `all` cannot receive custom grants; `cannot` can add restrictions. API-key
  CRUD permissions are built into both scope catalogs. Frontends still consume
  serialized final rules. See [authorization](./tutorial/auth/authorization).
- User/workspace permission catalogs and role maps now extend built-in defaults.
  Same-name role grants are merged and deduplicated; empty additions do not
  remove defaults. Custom permissions require explicit role grants. Use a new
  role for a restricted grant set. Entity `set*` mutations still replace stored
  values. API-key `allowedPermissions` remains a ceiling, not an additive list.
- Rename database request identity variables to `app.user.id` and
  `app.workspace.id`, and add `app.member.id` for the active member. Application permissions are no longer sent to the database;
  Services enforce Ability checks and API-key ceilings. RLS retains ownership
  and workspace boundaries, not application permission-name checks.
- Auth sessions now use the primary database exclusively; remove any
  `AuthModuleOptions.secondaryStorage` configuration.
- Move API-key `defaultPermissions` and `allowedPermissions` under `apiKey.user`
  and `apiKey.member`. The old flat options are rejected at startup; the two
  scopes do not inherit from each other. User keys may use user and workspace
  permissions; member keys accept only workspace permissions and use
  `member:invite` for invitation management. Their grants are bounded by both
  the target member and the issuer, and intersected with the member at runtime. For example:

  ```ts
  apiKey: {
    user: {
      defaultPermissions: ["user:read"],
      allowedPermissions: ["user:read", "workspace:update"],
    },
    member: {
      defaultPermissions: ["workspace:update"],
      allowedPermissions: ["workspace:update", "workspace:delete"],
    },
  }
  ```

  Omitted defaults are empty; an omitted allowlist permits the scope catalog,
  while `allowedPermissions: []` permits no grants. Defaults must fit the
  corresponding allowlist. See [API keys](./tutorial/auth/api-keys).

- Rebuild generated files and migrations after switching TypeScript module
  resolution so generated imports include valid ESM extensions.

The server example keeps a two-step baseline:
handwritten infrastructure initialization followed by a schema generated from the
current entities. Use a fresh database for this example; the
new baseline is not an upgrade path for databases that ran the removed migrations.
Back up any data you need before rebuilding an existing development database.

## Repository tests

Nest Boot version 8 uses Vitest with SWC instead of Jest. Contributors can run
unit and end-to-end suites with `pnpm test` and `pnpm test:e2e`.

### API-key ownership and database cascades

Run `Migration00000000000000_Initial` before the MikroORM-generated
`Migration20261024072513`. Initialization grants schema `USAGE` and sets default
`ALL` privileges on tables, functions, and sequences in `public` for both
`anonymous` and `authenticated`. These defaults apply only to future objects
created by the same migration role, not existing objects or objects created by
another role.

Neither request role is read-only or CRUD-limited. Table privileges include
`TRUNCATE`, `REFERENCES`, and `TRIGGER`; both roles can execute functions and use,
read, and update sequences. RLS does not protect `TRUNCATE` or `REFERENCES`, and
table policies do not restrict sequence operations. Do not expose unrestricted
SQL execution under either role. Review `SECURITY DEFINER` functions separately:
they execute with their owner's privileges. See PostgreSQL's
[row security documentation](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

Application tables declare RLS policies; Job history is an explicit exception with service-enforced scoped queries. `Verification`
explicitly denies request roles. Services and GraphQL control credential fields
and writable properties; database column-level protection is no longer configured.

`BaseApiKey.owner` is removed. `UserApiKey` and `MemberApiKey` use separate
tables, each with one required owner foreign key (`user` or `member`). There
is no exclusive-owner CHECK. Update entity imports, filters and fixtures for
the two key types. User deletion cascades through foreign keys without custom
cleanup functions or triggers; workspaces, service accounts and other members'
keys survive, while keys owned by deleted memberships cascade. User SELECT
permits authenticated roles; Services enforce profile access through Ability,
including custom permission names. User writes and Session reads likewise rely
on Service authorization; database request variables no longer carry application
permissions. Do not expose direct User queries without Service authorization.

The beta example retains init and regenerates its schema migration from the final
model, creating `member_api_key` and service account constraints directly. The old
workspace-key conversion and rename migrations are removed. Existing application
databases require their own data-preserving migration.

Workspace deletion is now permanent. Remove `Workspace.deletedAt` selections,
filters and indexes; members, invitations and member keys are deleted by
foreign-key cascades. The workspace DELETE policy retains workspace isolation;
the old soft-delete policies and `app.operation` deletion context are removed.
Back up data and decide how to handle legacy soft-deleted workspaces before
writing a migration for an existing database. The example baseline only targets
empty databases and does not convert existing data.

## Unified Auth module

`@nest-boot/auth-graphql` is merged into `@nest-boot/auth`. Remove the old package
and `AuthGraphQLModule` import; import inputs, payloads, resolvers and connections
from `@nest-boot/auth` instead.

Auth owns the concrete `User`, `Account`, `Session`, `Verification`,
`Workspace`, `Member`, `Invitation`, `UserApiKey`, and `MemberApiKey` entities, their GraphQL
metadata, relations, RLS policies, and connections. There are no public auth
`Base*` classes or `AuthModuleOptions.entities` overrides.

Register the exported `entities` array in both your runtime MikroORM configuration
and the configuration loaded by the migration CLI. The CLI does not initialize Nest:

```typescript
import { entities as authEntities } from "@nest-boot/auth";
import { defineConfig } from "@mikro-orm/postgresql";

export default defineConfig({
  entities: [...authEntities, "dist/**/*.entity.js"],
  entitiesTs: [...authEntities, "src/**/*.entity.ts"],
  // Connection and migration options...
});
```

Use separate related business entities and additional field resolvers to extend
these models. Import the built-in classes directly for relation targets; do not
redeclare or register replacement auth entities. Role/permission catalogs, ability
builders, delivery callbacks, and provider settings remain configurable.

`CreateUserOptions.data` is removed: `UserService.createUser()` only persists
the built-in user fields. Store application-specific fields in a separate entity
related to `User` instead.

GraphQL `signUp` now returns `SignUpPayload { id, token }` instead of
`AuthSignUpResultType { user, token }`. Replace `signUp { user { id } }` with
`signUp { id }`; authenticated user relations must be queried after sign-in.
`AuthService.signUpPayload()` replaces `signUpEntity()`. The lower-level
`AuthService.signUp()` result is unchanged, and a null token never establishes
an authenticated identity.

Administrative `createUser`, `updateUser`, `setUserRoles`, `setUserPermissions`,
`banUser`, and `unbanUser` mutations now return operation-specific payloads
containing only `id`. Remove profile/relation selections from these mutations
and refetch the user separately after a successful write.
`acceptInvitation` returns `AcceptInvitationPayload { id, memberId, workspaceId }`;
select the returned workspace in a subsequent request to query its membership.
Domain Service return values and authorization checks are unchanged.

The generated baseline already permits shared member contact emails and keeps
membership unique by `(user, workspace)`; there is no separate migration removing
email uniqueness. Rolling back the schema baseline drops its tables and data.
The initial infrastructure migration has an empty `down()`. Restoring contact-email
uniqueness in an existing database requires a separate migration and an explicit
data-preserving reconciliation plan.

# 诊断与路由

## 证据包

从消费者项目提取能够公开分享的最小证据：

- `@nest-boot/*` 包名和精确版本；
- Node、pnpm、NestJS 及直接相关 peer dependency 版本；
- 最小模块配置、调用代码或 schema；
- 可重复的命令、输入和失败输出；
- 观察行为与期望行为；
- 当前 workaround，以及它为什么不能成为长期方案；
- 指向上游源码、测试、类型或正式文档的根因证据。

使用 `pnpm why <package>`、lockfile 和已安装 `package.json` 确认实际版本。删除 token、连接串、内部域名、客户数据、生产日志和业务实体名；必要时用 `Tenant`、`Resource` 等中性名称重写复现。

## 所有权判断

| 证据                                                                                  | 目标                  | 动作                                             |
| ------------------------------------------------------------------------------------- | --------------------- | ------------------------------------------------ |
| 最新 `main` 的 `packages/<name>` 仍存在运行时、类型、导出或生成结果错误               | `nest-boot/nest-boot` | 准备框架 Issue 或带回归测试的 PR                 |
| 官方教程、API 注释或 package README 与当前实现不符                                    | `nest-boot/nest-boot` | 提交最小文档 PR，必要时增加行为测试              |
| 需要新的通用能力或跨包 API，但设计和兼容策略未决                                      | `nest-boot/nest-boot` | 先提交带用例、约束和备选方案的 enhancement Issue |
| 框架行为正确，只有 `nest-boot/skills` 的规则、示例或 eval 错误                        | `nest-boot/skills`    | 改用 `$nest-boot-skill-maintainer`               |
| 只在业务项目的封装、目录、数据或部署环境中成立                                        | 当前业务项目          | 修复项目代码或本地说明，不提交框架 Issue         |
| 根因位于 NestJS、MikroORM、BullMQ、GraphQL、PostgreSQL 等依赖，Nest Boot 没有适配责任 | 对应依赖仓库          | 按依赖项目流程报告；说明 Nest Boot 侧验证结果    |
| 只在旧版出现，最新发布或 `main` 已修复                                                | 不新建重复 Issue      | 建议升级；必要时为仍受支持版本讨论 backport      |
| 涉及可利用漏洞、凭证或客户数据                                                        | 私密安全渠道          | 停止公开 Issue/PR 流程                           |

不要因为堆栈中出现 `@nest-boot/*` 就自动归因。先排除配置错误、生命周期误用、peer dependency 不兼容、数据库 schema 漂移和消费者代码违反公开契约。

## BUG 与改进建议

BUG 需要可观察契约：文档承诺、公开类型、既有测试、向后兼容行为或稳定 API。无法指出被破坏的契约时，把结论表述为待确认的改进建议。

改进建议应回答：

- 哪些真实用例目前困难或重复；
- 为什么现有扩展点不足；
- 最小可接受能力是什么；
- 是否会改变默认行为、公开类型或 peer dependencies；
- 有哪些兼容方案和迁移成本；
- 如何测试成功且避免回归。

优先描述问题和约束，不把第一版解决方案写成唯一答案。

## 复现质量

优先级从高到低：

1. 在目标 package 测试结构中可直接运行的失败测试；
2. 最小独立 NestJS 应用或仓库内 example；
3. 脱敏的消费者代码与确定性命令；
4. 日志、截图或文字描述。

后两类通常足以创建调查 Issue，但在提交修复 PR 前应尽量转化为自动化回归测试。
